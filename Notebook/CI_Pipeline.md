# CI stages and evidence

The implementation for #334 uses `source-checks.yml` as its orchestration workflow, reusable workflows for build, engine, shipping and CodeQL jobs, and shared setup/evidence composite actions. The preceding design is [[CI_Pipeline_Design]]. Follow-ups add [[Sparkle_Update_Simulation]], [[Commit_Gates]] and the measured parallel graph in [[CI_Run_Time]].

## Stages

Fast gates use `.venv/bin/python scripts/ci-checks.py`: Swift formatting, license headers, the #336 Notebook-link checker, actionlint, shellcheck, action/SwiftPM pins, sensitive-file/size checks, redacted Gitleaks, new-history scanning and all Python tests. CI and installed hooks share these commands; hooks check exact staged/outgoing content. Missing tools fail. Generated-directory exclusions apply only at repository root; nested source paths remain scanned. Gitleaks has exact-path/exact-value exceptions for the checked-in public extension identity and Sparkle verification keys; other content in those files remains scanned. The installer downloads fixed release assets verified against committed SHA256 digests; no remote shell script is executed. Python dependencies retain the existing hash-pinned requirements. Swift resolution uses the committed lockfile; unit checks also reject lockfile drift.

Swift CodeQL uses a separate stdlib-only Python cache; its helpers do not import release/signing libraries. Native checks and shipping synchronize their Python environment with `uv pip sync --python .venv/bin/python --require-hashes --only-binary=:all: scripts/release-requirements.txt`; the requirements file is a positional input to `sync`. The pinned Periphery ZIP supplies both its executable and `libIndexStore.dylib`; the installer retains that companion beside the executable rather than depending on a Homebrew installation or changing global loader paths.

The Swift stage starts after selection, parallel with fast/dependency review; the final gate requires all three. It explicitly builds test targets, then runs tests with coverage and per-test xUnit output. Native Swift Testing XML is retained. A stdlib converter produces XCTest JUnit from the same serial test log, validating start/end pairs and outer-suite totals and preserving failures/skips; incomplete logs or missing Swift Testing XML fail. This avoids changing test execution just to obtain reports. The rebased local unit run exposed the need: SwiftPM emitted 503 Swift Testing cases while 119 XCTest cases (17 skipped) appeared only in its console log. Python reports include failures, errors, skips and subtest failures. Other commands produce command-level JUnit and JSON recording exit status, arguments and duration. Stage summaries show results and commit identity; setup logs show Xcode, Swift and Python versions. Regression fixtures isolate `GITHUB_STEP_SUMMARY` so authored failure cases cannot pollute the live stage summary.

Coverage compares the candidate with an immutable event base, built from `git archive` using the same runner/toolchain; recorded toolchain identities must match. Cached coverage profiles are removed from the validated SwiftPM scratch path before each test run. Manual validation compares with the fetched production ref. The gate compares line ratios independently for `BrowserCore`, `ArcusisBrowser`, `ChromiumBridge`, `Shaar` and `ShaarVerification` wherever source coverage exists; core and app coverage must exist. Missing, invalid or duplicate coverage fails. Baseline build/test failure also fails. This does not measure Chromium internals or uninstrumented binary dependencies.

After stage selection, build the verification bundle once and bind its archive to the commit, toolchain, engine pin and digest. Each shard validates the transfer and signature. Baseline, Quit exit and interrupted-save recovery share one runner; every private-window repetition has its own runner. The four original modes and all iterations remain. The full fixture includes tabs, Spaces, profiles, extension storage, downloads, media, picture-in-picture, site controls and DevTools. Production integration at `3840c1f` preserves #363's lifecycle/readiness fixes and all merged probes. `scripts/engine_fixture.py` remains unchanged. Inspector probes await picker acknowledgement before input; see [[CI_Run_Time]]. Modes continue after an earlier failure, preserving all results. Private windows never retry. Private-window and Quit modes run at least three independent repetitions, retaining #363's coverage; baseline and recovery follow the requested count. Nightly requests three for every mode with fresh probe roots; manual dispatch accepts `probe_iterations` from 1 to 10 with the private/Quit minimum reported. Every iteration runs and any failure fails the stage. Evidence names include mode, iteration, run and attempt. Evidence collection validates the fixture-root marker/ownership and copies only top-level authored JSON/log/PNG files, plus the existing redacted private-window proof directory. Browser profile directories are never uploaded. Gitleaks findings are retained as redacted JSON with the fast-stage evidence.

Hebrew localization retains its fast catalog check, hosted English/Hebrew offscreen captures and real engine-locale fixture; the final gate requires this stage. Hosted visuals retain all six existing filters and their hosted-only environment gate. These tests must not be enabled on a developer Mac. The stage runner refuses native fixtures or hosted visual capture outside macOS Actions; local verification builds and tests with those flags absent.

Shipping starts after fast/dependency review success, parallel with unit tests and native checks; it consumes no unit output. `CI required` still waits for all of them and CodeQL. The existing `bundle-app.sh --with-engine` verification-code guard, pinned payload verification and deep signature check remain. CI produces `Shaar-unsigned-candidate.zip`, a SHA256 checksum, an SPDX 2.3 dependency/file inventory and a symlink inventory. The hash-pinned `spdx-tools` validator is installed only in the shipping environment and rejects invalid SBOM documents. File records include required SHA-1 metadata alongside SHA-256; the analyzed app package includes the SPDX package verification code over sorted file SHA-1 values. Integrity and provenance use SHA-256. The ZIP has an ad-hoc signature for integrity checks; it is not Developer ID signed, notarized or Sparkle signed. Only production push runs attest that workflow's CI-built ZIP, after verifying SHA-256 checksums for both the ZIP and SBOM. PR builds have no signing material, and the building job has read-only token permissions. Local release signing and the existing release/appcast workflow remain unchanged.

CodeQL covers Swift (fresh traced compiler commands), Python and Actions. PR-scope native SwiftPM planning runs before initialization; source/compiler hashes and an independent extracted-file gate prevent stale or partial runtime-module extraction. PR/merge-group analysis covers shipping modules plus support; production/nightly/deep manual analysis uses fresh SwiftPM compilation under tracing, including the package manifest and build plugins. Proven unrelated CI-only PR changes may skip Swift. Whole-module compiler commands preserve the native dependency order; the slower batch experiment was dropped. Details and measurements are in [[CI_Run_Time]]. Swift retains its 60-minute job budget. Python/Actions have 20-minute budgets. Dependency review checks PR, merge-group and manual-validation diffs at high severity. Scorecard is a separate production-push/weekly assessment with SARIF artifacts; it does not publish a badge or change repository settings. Nightly/manual validation also runs Address and Thread Sanitizer tests in distinct scratch directories and Periphery. Sanitizer findings fail. Periphery execution errors fail; existing unused-declaration findings are a report, with public API, Objective-C/runtime, SwiftUI preview and Codable retention options.

## Selection, caches and required check

PRs, production/native pushes, merge groups, nightly and manual runs use the same graph. The planner normalizes dispatch repetition values to integers from 1 to 10 and emits a numeric JSON value; the caller applies `fromJSON` before passing the typed reusable-workflow input. Invalid counts fail before builds. Known Notebook/root-document/site-only PR diffs skip native work. Empty/unknown diffs select full work; script/workflow changes retain native checks and Python/Actions analysis. Relevant website contracts run through the same required graph, including merge groups. Production and scheduled runs select full work. Manual `deep_checks` defaults true; timing runs may disable only the extra sanitizer/dead-code work and select the normal PR Swift scope.

Concurrency includes event/ref identity and cancels only superseded PR runs. SwiftPM cache keys include OS/architecture, toolchain, mode, manifest/lockfile and source hashes, with a same-mode/toolchain fallback for incremental builds. Commands always rebuild/test; cached products never count as a passing check. Engine archives use an independent pin key and are checked before extraction/use. Shipping, verification, coverage and sanitizer scratch paths stay separate.

`CI required` runs with `always()` and fails on failure, cancellation, missing prerequisites or unexpected skips. It requires sanitizers/dead-code reporting for nightly/deep manual runs. It is the intended single required status context. Artifacts retain seven days of command logs, JUnit, coverage and authored evidence; Scorecard retains fourteen days. Additional evidence directories use separate artifacts so their common ancestor cannot change the paths consumed by coverage or attestation jobs.

`.github/production-ruleset.json` retains the initial reviewed ruleset snapshot. Live repository ruleset `26350516` is owner-managed and now uses ALLGREEN groups up to five. Existing enterprise PR/signature/no-force-push rules remain authoritative. This change edits neither the ruleset file nor repository rulesets, and does not merge PRs. Merge-group execution and coverage baseline investigation are recorded in [[Test_Coverage]]; configured enforcement and green execution remain separate evidence.

## Update and verification boundaries

Shipping includes [[Sparkle_Update_Simulation]], using ephemeral fixture keys for real installer scenarios. Shared prior-schema upgrade fixtures and seeded randomized tests remain in the unit/Python gates. Local fixture preparation does not prove installation; hosted execution does. Real Developer ID, notarization and Sparkle release signing remain local, with credentials untouched. [[Releasing]] requires green full production Source checks before tagging.

Current before/after measurements, extraction counts, annotation audit and the retained-check matrix live in [[CI_Run_Time]]. The earlier production nightly run [41372340304](https://github.com/arcusis/shaar/actions/runs/41372340304) passed repeated probes, both sanitizers and Periphery; scheduled Scorecard run [41384743935](https://github.com/arcusis/shaar/actions/runs/41384743935) passed. These identify those runs' scope, not proof for a later head. Production-only provenance and a real green merge-group run require their own execution evidence. Signed-distribution provenance stays outside the approved unsigned-CI-candidate scope.
