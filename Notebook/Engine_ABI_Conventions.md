# Shaar engine ABI conventions

Shared contract for the 14 engine module specs in issue #418. This note fixes the cross-cutting shape of the proposed `chrome/browser/shaar/public/shaar_engine.h`; module notes propose their own operations, payloads and events within it. It is a design contract, not an implemented or tested engine. No Ardia code is reused. See [[Engine_Shaar_Layer_Design]] and [[Engine_Ardia_Inventory]].

## Version and naming

- Export C linkage only, with `shaar_` function/type names, `SHAAR_` constants, and default visibility limited to reviewed functions. Keep Chromium C++ and Objective-C types private. The macOS host view is the one opaque `void *` exception; the ObjC bridge treats it as a **borrowed** `NSView *`.
- Start at ABI major 1, minor 0. Major breaks layout or semantics; minor only appends struct fields, enum values, operations or event kinds. Never renumber or reuse published numeric IDs. Give every exposed enum member an explicit numeric value in the consolidated header.
- `shaar_config`, `shaar_scope`, `shaar_error`, `shaar_result`, and `shaar_event` carry a `uint32_t size` field. The caller supplies its known size; the engine checks the minimum known prefix and writes no more than the supplied size. Negotiate major/minor at engine creation before any handle is used. Reject an unsupported major with `SHAAR_UNSUPPORTED_ABI`; gate newer operations and fields by negotiated minor.
- All strings and JSON are UTF-8, length-delimited `shaar_bytes` with no reliance on NUL termination. Define per-operation JSON schemas and `schemaVersion` for payloads. Unknown fields that could change authorization, ownership or persistence must fail validation. Keep an explicit C enum dispatch or typed C function for each capability; do not use dynamic method-name strings.

## Handles and scope

- A process owns one `shaar_engine`; it owns many regular `shaar_profile` handles. Each profile is bound to one canonical directory and one Shaar UUID for its lifetime. Opening the same directory under a different ID, or rebinding an ID to a different directory, is a typed conflict. There is no default-profile fallback.
- A `shaar_private_session` is a first-class OTR handle created from exactly one regular profile, with its own Shaar UUID and explicit close. It is not a path alias, `offTheRecord` Boolean, or inferred tab property. The ABI v1 product contract permits one live private session per parent profile; its multiple private windows/tabs attach explicitly to that session, matching their shared OTR store. A different concurrent session ID is a conflict unless a later implementation provides a separately isolated OTR context. Closing the session destroys its OTR state after owned windows/tabs and pending requests finish or cancel.
- Every profile/session operation takes an explicit `shaar_scope` containing **exactly one** regular profile or private-session handle; engine creation and scope opening are lifecycle exceptions. A regular native window may host tab groups from several regular profiles and switch its active profile, while a private window stays bound to one private session. A tab's scope and the window's allowed binding are checked before work starts and again before asynchronous completion. A stale handle returns `SHAAR_NOT_FOUND`; a live handle in another scope returns `SHAAR_WRONG_PROFILE` or `SHAAR_WRONG_SESSION`. No lookup by a download, bookmark, extension or tab ID can silently choose a profile.
- Engine handles own child handles; `close` is explicit and idempotent only where the header says so. After a final close event, no callback may expose the closed handle. Shutdown cancels requests, emits final close events, invalidates children and detaches borrowed views before releasing callback contexts. State whether each per-module operation is legal for private sessions; persistence-sensitive operations should return `SHAAR_PRIVATE_DISALLOWED` unless explicitly designed for OTR.

## Errors and requests

- Every synchronous call returns `shaar_error_code` and can fill a size-checked `shaar_error`. Asynchronous calls report the same typed code in `shaar_result`; immediate argument/scope failure returns synchronously and must **not** later invoke the completion. Accepted requests receive one completion, including cancellation, unless engine shutdown explicitly invalidates the caller's callback context under a documented teardown rule.
- Core codes: `SHAAR_OK`, `SHAAR_INVALID_ARGUMENT`, `SHAAR_UNSUPPORTED_ABI`, `SHAAR_NOT_READY`, `SHAAR_NOT_FOUND`, `SHAAR_WRONG_PROFILE`, `SHAAR_WRONG_SESSION`, `SHAAR_PRIVATE_DISALLOWED`, `SHAAR_POLICY_BLOCKED`, `SHAAR_PERMISSION_DENIED`, `SHAAR_CONFLICT`, `SHAAR_CANCELLED`, `SHAAR_IO_ERROR`, `SHAAR_CHROMIUM_ERROR`, and `SHAAR_SHUTTING_DOWN`. Module specs may propose more codes with a concrete recovery distinction. `platform_code` is diagnostic; `message` is for logs, not localized UI copy. Never turn a malformed response or an empty payload into success.
- Caller-generated `shaar_request_id` values are unique among outstanding requests in one engine instance. Completion carries the same ID. Cancellation is best effort but yields one terminal completion; the Swift adapter rejects stale responses by request ID and scope/generation. Prompt events carry a request ID, target scope/handles and expiry, and only the matching live target may answer.

## Threading and one event stream

- Startup entry points run on the macOS main thread; after Chromium initializes its UI thread, engine operations, callbacks and borrowed view access stay serialized there. The adapter asserts the appropriate phase/thread. An accepted async request never calls its completion inline; events are emitted after the relevant state mutation, not while a tab strip observer is reenterable. Preserve the current deferred tab-strip reconciliation behavior.
- Register **one** `shaar_event_fn` at engine creation. All module events flow through it: engine, profile, private session, window, tab, navigation, find, permission, download, bookmark, history, site data, extension, DevTools and media. There are no second per-module sinks. Event `sequence` increases monotonically within the engine instance; the adapter copies borrowed payloads during callback and dispatches to existing Swift models afterward.
- Every profile-scoped event carries the parent regular profile UUID; a private event also carries its private-session UUID. Only engine-wide events may omit the profile UUID. Window/tab IDs are included when relevant. The dispatcher rejects mismatched ownership and never routes a private event into regular downloads, history, bookmarks or settings caches. Event payloads have a `kind` and `schemaVersion`, contain no secrets or raw profile paths, and distinguish change, removal, failure and final close.
- A result callback and event can arrive in either order unless a module contract explicitly defines the ordering. Module specs must state mutation acknowledgement, watch invalidation, cancellation, navigation/close race and restart behavior. Swift model updates coalesce invalidations and discard stale generations.

## Module-spec checklist

Each `Engine_Module_<area>.md` should name its C operations or typed functions, allowed regular/private scope, handles, request/result JSON schema, event kinds/payloads, typed errors, Chromium owners and required hooks, Swift adapter call sites, persistence/consent rules, and headless probe/CI gate. Flag any needed change to these conventions for reconciliation in the consolidated design; avoid defining a second ABI, event sink or default-profile path.
