# Shaar engine module: bookmarks (issue #418)

This module extends [[Engine_Shaar_Layer_Design]] for the bookmark tree, mutation and change-watch path. It follows that note's ABI v1: only `shaar_engine.h` crosses the C boundary; UTF-8 slices are length-delimited and borrowed for the documented duration; handles are opaque; calls and callbacks run on Chromium's UI thread; asynchronous replies are not inline; request IDs identify work; errors are typed; and events use the engine's single ordered stream. This is a proposal, not implementation or runtime evidence.

## Current Shaar behavior

Swift imports `ChromiumBridge` and reaches the pinned Ardia exports only through `ARCChromiumRuntime` and `ARCLibraryService`. The C service ABI itself is not imported into Swift.

Keep that behavior explicit for initial parity. Decide separately if product design later adopts more storage surfaces.

## Pinned Ardia implementation

Read-only sources are under `/Users/david/orca/workspaces/shaar/engine-333-364/build/EngineSource/source/ardia/engine/chromium/src/chrome/browser/ardia/`.

- `ac_bookmarks.cc` obtains the profile-owned model via `BookmarkModelFactory::GetForBrowserContext`; it returns null for OTR profiles. Its tree serializer emits UUID, title, creation time, URL/folder kind, optional sync metadata and recursive children, with a depth cap. `ac_bookmarks_tree` waits for asynchronous model load and serializes the `bookmark_bar_node()` and `other_node()` roots.
- The mutation helper resolves permanent tokens `bar`/`other` or a UUID through `GetNodeByUuid(kLocalOrSyncableNodes)`. It delegates add/update/move/remove to `BookmarkModel`, disallows permanent-node removal and ancestor cycles, clamps insertion positions and groups operations with `ScopedGroupBookmarkActions`. The endpoint replies with applied/skipped/invalid counts. The current Objective-C bridge sends one op per call and accepts success only when exactly one op applied with no skips/invalid IDs.
- `Watcher` implements `BookmarkModelObserver`, observing load, add, move, remove, title/URL change, child reorder and removal-all callbacks; it coalesces callbacks to a posted UI task. The per-profile watcher suppresses notifications while the endpoint applies operations, which explains Swift's explicit refresh after acknowledgement. Favicons are deliberately ignored.
- `ac_engine.cc` supplies the profile-directory call context, UI-thread dispatch, JSON reply and event emission. Ardia maps the regular profile to a loaded `Profile*`; bookmark operations reject private mode rather than redirecting it to persistent data.

No bookmark-specific Chromium patch appears in Ardia's ordered patch series or patch directory. The module relies on Chromium's existing bookmark implementation and factory. Do not port Ardia source; implement the behavior in Shaar-owned files under the design note's `chrome/browser/shaar/services/` tree.

## Chromium APIs for Shaar's implementation

Use these pinned Chromium 155 paths under `chromium_git/chromium/src/`:

- `chrome/browser/bookmarks/bookmark_model_factory.h/.cc`: `BookmarkModelFactory::GetForBrowserContext` and `GetForBrowserContextIfExists` bind the service to the correct `Profile`. Resolve only from the explicit `shaar_scope.profile`; never derive scope from a bookmark ID or active tab.
- `components/bookmarks/browser/bookmark_model.h`: `loaded()`, `bookmark_bar_node()`, `other_node()`, `is_permanent_node()`, `GetNodeByUuid(...kLocalOrSyncableNodes)`, `AddFolder`, `AddURL`, `SetTitle`, `SetURL`, `Move`, and `Remove` support the required snapshot and edits. Validate UUID scope and parent/cycle constraints before calling these APIs. Use Chromium's `GURL` validation and UTF-8 conversion helpers, with explicit input length/depth/node-count limits.
- `components/bookmarks/browser/bookmark_model_observer.h` and `base_bookmark_model_observer.h`: observe model load and mutations. Use scoped observation and weak/lifetime-safe posted work; detach on `BookmarkModelBeingDeleted` and profile shutdown. Coalesce bursts into one `SHAAR_EVENT_BOOKMARK` invalidation after model mutation.
- `components/bookmarks/browser/scoped_group_bookmark_actions.h`: group a requested batch for native undo/notification behavior, but do not claim transactionality unless implementation adds and verifies rollback. Report partial application with a typed conflict/result payload or fail before mutation when validation can establish the whole batch is valid.
- `components/bookmarks/browser/bookmark_node.h`: read child order, title, UUID, URL, creation date and metadata for the compatibility tree. Use model APIs for writes; never mutate `BookmarkNode` internals directly.

`BookmarkModelFactory` redirects ordinary OTR contexts to the original regular profile by design. Shaar must check the supplied scope before requesting the service: any bookmark read, mutation, or watch scoped to `private_session` returns `SHAAR_PRIVATE_DISALLOWED`; it must not silently expose or edit the parent's persistent tree. Private handles remain first-class in event/request envelopes for other services.

## Proposed ABI additions

Use the design note's existing `shaar_submit(engine, scope, ..., operation, args_json, request_id, ...)` and `shaar_result` contract. Extend the existing `shaar_operation` enum with `SHAAR_OP_BOOKMARK_WATCH` beside `SHAAR_OP_BOOKMARK_TREE` and `SHAAR_OP_BOOKMARK_APPLY`; do not add a second bookmark ABI or callback channel. All three operations require a valid profile handle and no window/tab handle. A private-session scope returns `SHAAR_PRIVATE_DISALLOWED`; unknown/closing profile, unloaded/closing engine, malformed arguments, foreign IDs, policy restrictions and Chromium failures map to the corresponding typed `shaar_error_code` (`NOT_FOUND`, `NOT_READY`, `INVALID_ARGUMENT`, `WRONG_PROFILE`, `POLICY_BLOCKED`, `CHROMIUM_ERROR`, etc.). Preserve diagnostic text separately from localized Swift UI copy.

Operation schemas and results:

| Operation | Contract |
| --- | --- |
| `BOOKMARK_TREE` | Args `{ "schemaVersion": 1 }`. Reply payload `{ "schemaVersion": 1, "bar": node, "other": node }`, with node fields matching the current adapter (`id`, `t`, `k`; URL nodes have `u`; folder nodes have ordered `c`). Wait asynchronously for `BookmarkModel::loaded()`; return `NOT_READY`/`SHUTTING_DOWN` if the profile/model closes before completion. Bound depth, total nodes and serialized size. |
| `BOOKMARK_APPLY` | Args `{ "schemaVersion": 1, "ops": [...] }`; preserve current operation vocabulary and semantics (`add`, `update`, `move`, `remove`; UUID IDs; `bar`/`other` permanent parent aliases; optional `index`, title `t`, URL `u`, kind `k`, creation time `a`, sync key `key`, and import idempotency `ifAbsent`). Reply includes `{ "schemaVersion": 1, "applied": n, "skipped": n, "invalid": [...] }`. Reject malformed/unsupported fields and cross-profile IDs with typed errors. The Swift adapter continues one-operation requests for interactive edits and may sequence import operations until batch semantics are proven. Own writes publish bookmark invalidation events; no implicit “events omitted during apply” rule. |
| `BOOKMARK_WATCH` | Args `{ "schemaVersion": 1, "enabled": true }`; idempotently attach one observer to this profile model. `enabled:false` detaches if no adapter client remains, or use profile close as the single teardown owner if engine watch references are intentionally profile-lifetime. Reply `{ "schemaVersion": 1, "watching": true }`. Watch starts after profile load and ends before profile handle invalidation. |

Publish changes only as `SHAAR_EVENT_BOOKMARK`, with the design note's monotonic `sequence`, `profile_id` as Shaar UUID, empty `session_id` for regular profiles, and payload such as `{ "schemaVersion": 1, "change": "invalidated" }`. This is an invalidation signal, not a partial tree. Include `profile_id` on every event; never include raw profile paths. Coalesce observer bursts on the UI sequence. Emit after own and external edits, including extension-created Chromium bookmarks. Ensure event dispatch after mutation and before a successful mutation reply when both are queued in order, or document/test the reverse order so Swift cannot miss a refresh. Watch setup/model-load failure reports through typed result/error, not an unscoped event.

## Swift adapter changes

Keep `ARCChromiumRuntime` as the Swift-facing facade during this module migration, as required by the design note. In `ChromiumEngineServices.mm`, add function/operation mapping to `shaar_submit` with generated request IDs, copy borrowed result/event bytes before returning from callbacks, and map typed errors to `NSError` codes. In `ChromiumLibrary.mm`, retain `bar`/`other` payload validation and existing method signatures while using the new operation IDs. Bind requests to the explicit profile handle rather than the current path dictionary; never infer it from a bookmark UUID.

At profile load, register the bookmark watch after the profile handle is ready. Route `SHAAR_EVENT_BOOKMARK` only when both profile and session scope match the expected regular UUID. In `BrowserRuntimeEvents.swift:197-209` and `BrowserLibraryModel.swift:132-153`, remove the Ardia-specific successful-write manual fanout only after the engine simulation proves own writes emit events to all attached clients; keep the post-ack refresh as a temporary compatibility fallback until the new adapter is the selected implementation. Preserve `BookmarkTree` parsing, profile-keyed caches, generation guards and stale-action rejection. Map typed private-disallowed/profile errors into localized library notices without converting them into empty trees.

## Parity tests and smoke checks

These are acceptance tests to add with implementation; none were run for this design note.

- **Unit tests:** serialization preserves root and child order, UUIDs, empty titles, folder/URL distinction and creation date; rejects invalid URLs/UUIDs, duplicate IDs, excessive depth/node count and unsupported fields. Apply covers add/update/move/remove, idempotent import, clamped ordering, permanent-root rejection, cycle rejection, foreign-profile IDs and partial-batch semantics. Observer tests cover load completion, coalescing, own-write events, external/extension writes, teardown during pending callbacks and profile destruction. Every operation rejects private scope without reading the regular profile's model.
- **Engine simulation:** headless temporary profiles A and B; tree/update/move/add/remove on A reflects through `chrome.bookmarks` in A only; B's tree and extension API remain unchanged. Assert stable IDs/hierarchy after engine restart; watch emits profile A UUID with empty regular session ID for extension and API changes, no profile path, no cross-profile cache invalidation, and a successful own write causes exactly the documented refresh. Exercise unknown/closed profile, private scope, malformed arguments, model-not-ready and shutdown races with typed errors. Confirm all attached library clients for A refresh and no private bookmark data is persisted or surfaced.
- **Smoke/parity checks:** reuse the existing `LibraryProbe` behaviors in `Sources/ShaarVerification/LibraryProbe.swift` (especially `:94-102`, `:112-129`, `:131-177`, `:196-210`, `:273-286`) against the Shaar service implementation. Verify UI snapshots, bookmark editor save/delete, import, command search, extension visibility, restart persistence, profile isolation and same-profile multi-window invalidation. Existing probes do not establish private-session bookmark policy; add an explicit private read/write/watch rejection assertion.

## Effort and risks

Estimate: **1–2 engineer-weeks** for the bookmarks module (excluding Chromium sync/build wall time and shared ABI scaffold). This includes implementation, adapter, focused unit tests, simulation fixture and the existing library smoke flow. It is a subset of the layer-design table's combined bookmarks/history estimate.

Key risks are event ordering and duplicate refreshes while the old/manual Swift invalidation path is retained; model/profile teardown during asynchronous load; tree size and recursion pressure; Chromium's bookmark UUID lookup/storage distinctions as account storage evolves; and preserving import behavior without promising transactional batches. The private-session check must happen before `BookmarkModelFactory` lookup because Chromium redirects ordinary OTR access to the original profile. Adding mobile/account roots changes the current Swift parser and product-visible hierarchy and is outside parity scope. A compile or simulation does not prove production framework integration; keep the normal CI lane on the pinned engine until the module simulation passes under the Shaar source engine.
