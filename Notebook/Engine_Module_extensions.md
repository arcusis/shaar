# Shaar engine module: extensions

Part of issue #418; implements the Extensions row in `Engine_Shaar_Layer_Design.md`. This is a new analysis against the pinned source and Chromium 155 tree, not a port of Ardia code. ABI proposals follow the shared versioned C ABI, opaque profile/private-session handles, typed errors, UI-thread callback rules, and single event stream. No engine build or runtime claim is made here.

## Current Shaar app behavior

There are no extension-specific `ac_*` exports resolved or called by the current bridge. `ChromiumEngineServices.mm:45-67` resolves the generic `ac_engine_abi_version` / `ac_engine_set_event_sink` and profile service calls for downloads, library and site controls; `:98-126` sends those calls and discards path-labeled private events. The extension adapter is instead backed by `ArdiaCoreProfile` and `ArdiaCoreTab` methods retained inside `ARCChromiumRuntime`.

| Current behavior | Swift and bridge routes |
| --- | --- |
| Per-profile installed list, toolbar list, action title and invoke | `BrowserEngine.swift:705-719,754-769`; `ExtensionManagerModel.swift:76-95`; `ChromiumBridge.h:182-194`; `ChromiumExtensions.mm:26-29,65-87`. The bridge reads `ArdiaCoreProfile.extensions`; action title/state and execution are queried on the selected `ArdiaCoreTab`. |
| Enable/disable, details and uninstall | `ExtensionManagerModel.swift:105-120`; `ChromiumBridge.h:14-20,187-192`; `ChromiumExtensions.mm:110-188`. A fixed switch builds scripts for the bundled extension manager's `chrome.management` API; values are JSON encoded, not interpolated as arbitrary method names. |
| Extension metadata and icon loading | `ExtensionManagerModel.swift:83-95,123-131`; `ChromiumBridge.h:193-194`; `ChromiumExtensions.mm:191-196`. Metadata comes from management API JSON; icon files are read from the profile's extensions directory. |
| Install consent | `ChromiumBridge.mm:1581-1601`; `BrowserEngine.swift:348-360,793-824`; `BrowserStore.swift:804-810,864-889`; `ExtensionConsent.swift:8-105`. The delegate request is bound to tab, window and profile, displayed with permission/host access, and accepted or denied only while the request still matches the active session. Unknown/incomplete permission details require a separate acknowledgement. |
| Action popup and popup lifecycle/size | `ChromiumBridge.mm:1602-1605`; `ChromiumExtensions.mm:32-63,198-216`; `BrowserRuntimeEvents.swift:68-92`; `BrowserEngine.swift:361-375,772-791`; `ChromiumBridge.h:77-80,195-197`. Popup identity is checked against window/profile/tab and the selected page before Swift presents its borrowed native view. |
| App-facing extension events and types | `ChromiumBridge.h:77-80` defines install request, popup open/close/size callbacks. `BrowserRuntimeEvents.swift:68-93,177-180` routes requests to the owning window and consumes install decisions. Swift value types include `BrowserExtension`, `ManagedExtension`, `ExtensionInstallRequest`, and `ExtensionPopupContext`; see `BrowserEngine.swift:772-818`, `ExtensionManagerModel.swift:24-33`, and `BrowserPresentation.swift:28-73`. |
| Scope today | Models are keyed by runtime + profile (`ExtensionManagerModel.swift:9-12,35-45`); install and management require a regular profile. No extension event has a first-class private-session identity in this path. `ExtensionConsent.swift:79` states install applies to Spaces sharing that profile. |

Issue #287 adds an app-wide install request: one install should appear in every profile while enablement remains per-profile. That fan-out is not present in the current adapter. Its further “sign in once works everywhere” requirement needs an explicit storage/account design; Chromium gives each profile its own extension context and storage.

## How pinned Ardia implements this area

The ObjC API surface Shaar calls is declared in pinned `source/ardia-build/engine/ardiacore/src/ardia/core/public/ArdiaCore.h`: `ArdiaCoreProfile` extension access and component load/unload around lines 106-107; `ArdiaCoreWindow` extension-view creation around 171; `ArdiaCoreTab` action methods around 317-318; delegate callbacks for install and action popup around 27-37. `ardiacore_api.mm:497-526,589-594,1167-1205,1306+,1903-1945` bridges these to the engine. Shaar's adapter-specific behavior is in `ChromiumExtensions.mm` and `ChromiumBridge.mm` cited above.

The copied Chromium-side implementation files are `source/ardia-build/engine/chromium/src/chrome/browser/ardia/ac_extensions.{cc,h}`, `ac_extensions_sync.{cc,h}`, and `ac_extension_actions.{cc,h}`. They attach extension management, install/update coordination and action state to Ardia's profile/tab model. The macOS layer includes `engine/ardiacore/src/ardia/core/ac_extension_view.{h,mm}`, `ac_extension_shortcuts.{h,mm}`, and `ac_installed_bubble.{h,mm}`. `ac_extension_view.mm` hosts extension contents as hidden native extension views; Ardia forwards popup creation and close/resize state through its delegate. The Chromium owners involved include `extensions::ExtensionService`, `ExtensionRegistry`, `ExtensionRegistrar`, `ExtensionHost` / `ExtensionHostRegistry`, and Chrome's `BrowserExtensionWindowController` / extension action routing.

The pinned series relies on these extension patches (all Ardia-authored in this pin; preserve behavior by independently designing and reviewing Shaar changes, not by copying patch text):

Use Chromium's per-`Profile` services and observers directly inside `chrome/browser/shaar/extensions/`; no Chromium object crosses the C ABI.

| Need | Chromium 155 API and source paths |

Use `extensions::Extension` metadata, not a page script. |
| Enable, disable and remove | `extensions::ExtensionRegistrar` in `extensions/browser/extension_registrar.{h,cc}` and `chrome/browser/extensions/extension_service.{h,cc}`. Preserve disable reasons, management policy and uninstall semantics; do not mutate extension prefs or files behind the registrar. |
| Web Store install and CRX validation | `extensions::WebstoreInstaller` in `extensions/browser/webstore_installer.{h,cc}`, `extensions::CrxInstaller` in `extensions/browser/crx_installer.{h,cc}`, and `chrome/browser/extensions/extension_install_prompt.{h,cc}`. Adapt the prompt client to a typed Shaar consent request; approval must be checked against the still-live tab, window, profile/session and request ID before installation continues. |
| Unpacked/component installs | `extensions::UnpackedInstaller` in `extensions/browser/unpacked_installer.{h,cc}` and component loading through Chrome's extension service. Keep developer-mode and source-path policy explicit; bundled component IDs/permissions must be allowlisted. |
| Per-profile enable and private-window visibility | `extensions::ExtensionPrefs` in `extensions/browser/extension_prefs.{h,cc}` and Chrome helpers in `chrome/browser/extensions/extension_util.{h,cc}` (`util::IsIncognitoEnabled` / `SetIsIncognitoEnabled`). | Action state, invocation and popup host | `extensions/browser/extension_action.{h,cc}`, `chrome/browser/extensions/extension_action_runner.{h,cc}`, `chrome/browser/extensions/extension_view_host_factory.{h,cc}`, `chrome/browser/extensions/extension_view.{h,cc}`, `extensions/browser/extension_host.{h,cc}`, and `chrome/browser/extensions/browser_extension_window_controller.{h,cc}`. Upstream APIs and class signatures are pinned to Chromium 155 here and must be checked when the Chromium pin changes.

## Proposed C ABI and Swift adapter

Keep the shared ABI's existing `shaar_scope`, `shaar_request_id`, `shaar_reply_fn`, `shaar_error_code`, `shaar_result`, `shaar_event_fn`, and one engine event stream. Every operation supplies exactly one profile or private-session scope. Validate extension ID format, owning profile, optional window/tab, and generation both at submission and async completion. Define stable explicit numeric values when consolidating operation/event enums; never renumber published values. UTF-8 JSON stays length-delimited, schemas have `schemaVersion`, and every accepted request completes once off-inline on the Chromium UI thread.

Keep the already proposed `SHAAR_OP_EXTENSION_LIST`, `SHAAR_OP_EXTENSION_MANAGE`, and `SHAAR_OP_EXTENSION_ACTION` symbols in `Engine_Shaar_Layer_Design.md`, and define their operation-specific schemas below. Add the remaining proposed operations as new, explicitly numbered enum members when the consolidated header is authored; do not duplicate or renumber existing members:

| Operation | Arguments and result contract |
| --- | --- |
| Existing `SHAAR_OP_EXTENSION_LIST` | `args {schemaVersion:1}`; returns installed extension summaries: id, name, version, description, enabled, mayDisable, permissions, hostPermissions, incognitoEnabled, source/management state. Profile/session scope required; private list may be omitted or read-only by explicit policy. |
| Existing `SHAAR_OP_EXTENSION_MANAGE` | Define a closed `action` enum in JSON (`setEnabled`, `setIncognitoEnabled`, `uninstall`, `install`) with per-action required fields and result. Enable/disable and incognito visibility mutate only the scoped regular profile; uninstall is profile-local. For `install`, verify source/ID and fan out to each targeted regular profile with a per-profile outcome list and idempotent retries. Never silently count partial fan-out as success. Private-session scope is disallowed for mutations/install. |
| New `SHAAR_OP_EXTENSION_INSTALL_DECISION` | Request ID plus accepted/denied, answered only for the matching live consent event and exact target window/tab/scope. This completes the prompt without an arbitrary extension method string. |
| Existing `SHAAR_OP_EXTENSION_ACTION` | `extensionId`, action verb `invoke` (future verbs require new schema); window/tab handles must belong to scope. Returns route (`none`, `popup`, or supported hosted surface). |
| New `SHAAR_OP_EXTENSION_POPUP_CLOSE` | Popup/window identity bound to scope; idempotent close contract explicit in implementation. |

Keep the existing `shaar_submit` dispatch shape, with operation-specific JSON validation and typed result schemas. Use existing errors where they distinguish recovery: `SHAAR_INVALID_ARGUMENT`, `SHAAR_NOT_FOUND`, `SHAAR_WRONG_PROFILE`, `SHAAR_WRONG_SESSION`, `SHAAR_PRIVATE_DISALLOWED`, `SHAAR_POLICY_BLOCKED`, `SHAAR_PERMISSION_DENIED`, `SHAAR_CONFLICT`, `SHAAR_CANCELLED`, `SHAAR_IO_ERROR`, and `SHAAR_CHROMIUM_ERROR`. Add a module error only if a distinct recovery action requires it (for example a typed partial-install result may be better than a new error). Results must distinguish a blocked install, user denial, malformed/changed Web Store identity, update/network failure, and per-profile partial failure; do not put localized UI strings in `message`.

Use `SHAAR_EVENT_EXTENSION` payloads with `kind` and `schemaVersion`, including `installed/updated/removed`, `enabledChanged`, `incognitoVisibilityChanged`, `installConsentRequested`, `installProgress/installCompleted/installFailed`, `actionPopupOpened/actionPopupClosed/actionPopupSizeChanged`, and `extensionWindowRequested/extensionWindowClosed`. Every event includes parent `profile_id`; private events also include their distinct `session_id`; relevant events include window/tab IDs. Consent events carry the request ID, target scope/window/tab, extension identity and a deadline, never filesystem paths or permission secrets. Close final extension/popup/window events before invalidating handles. All payload slices are copied by Swift during callback. If replies and events race, the adapter uses request ID and scope generation and reloads authoritative list state.

Swift migration stays behind `ChromiumBridge` as in the layer design. Add opaque profile/private-session handles and typed extension methods to the ObjC++ adapter; remove its dynamic `ac_*` service route for extension work (none exists now), manager-extension JavaScript, `ArdiaCore*` calls and request callback translations after parity gates pass. Map `shaar_error_code` to localized Swift errors. Retain `ExtensionManagerModel`'s profile-keyed cache and pin preferences, but source records/enable state from typed operations and refresh on extension events. Change install consent to hold engine request ID + exact scope/window/tab generation and resolve via `SHAAR_OP_EXTENSION_INSTALL_DECISION`; preserve unknown-permission acknowledgement. Present hosted popup `NSView *` as borrowed, and close on tab/window/profile/session teardown. Route extension-created windows through normal Swift window/tab adoption. Do not imply that profile-local extension storage is shared merely because code is installed in each profile.

### Issue #287 storage decision

The compatible initial design is one browser-level install intent/package identity with an idempotent install operation applied to each existing regular profile and every newly opened profile, while each profile retains its own Chromium extension instance, enable flag, incognito grant, and storage. This meets install visibility and per-profile enablement without merging profile stores. It does **not** establish “sign in once works everywhere.” That behavior requires an explicit mechanism supported by the extension (account sync/login) or a separately threat-modeled shared broker for narrowly selected extension data. Sharing an extension storage directory or Chromium `Profile` across profiles is unsafe and is not proposed. Treat the single-sign-in criterion as a release blocker until #287 chooses and verifies the storage contract.

## Tests and parity gates

- **C++ unit tests:** operation schema and extension-ID validation; exact scope/handle ownership; registry event ordering; enable/disable and incognito grant persistence; policy/component protections; per-profile install ledger idempotency, retries, rollback/partial result; consent expiration, denial and duplicate decision; popup origin/tab binding and close races; callback exactly-once behavior.
- **Engine simulation:** two regular profiles plus two private sessions. Approve one install intent and verify list in both profiles and a newly opened third profile; independently toggle enable and private visibility; verify storage/enable state remain scoped; reject wrong-profile/session calls and stale consent; deny install and verify no profile mutates; exercise update, uninstall, component protection, action popup open/resize/close, tab/window destruction, and extension-created window adoption. Assert every private event carries the unique session ID and never updates regular-only caches.
- **Swift adapter tests:** typed result/error decoding; copied borrowed event payloads; profile/session/window/tab routing; stale request and generation rejection; consent sheet cancellation/expiry; event-driven manager refresh; pin/icon state stays profile keyed; popup host closure and wrong-window rejection. Keep the current consent unknown-access and extension management UI behavior.
- **Headless smoke/probe:** extend `ShaarVerification/ExtensionProbe.swift` and `BitwardenProbe.swift` with install consent, profile fan-out, independent enable state, authenticated behavior across profiles per the settled #287 contract, shortcut/action execution, popup view lifecycle/size, update, restart persistence, and profile/private isolation. Include a component-extension and denied-permission case. Run in the source-engine CI lane; keep the regular prebuilt-engine CI lane on its current adapter until native parity passes. No local full build is required for this spec.

## Effort and risks

Use the shared plan estimate of **4–7 engineer-weeks** for install/list/manage, consent, update/policy, per-profile fan-out, action windows/popups, Swift adapter migration and native probes, excluding Chromium sync/build wall time. The #287 shared sign-in/storage decision could add substantial design and security review and is not covered by that estimate.

Highest risks are extension update endpoint/policy correctness; Web Store identity and permission changes between prompt and install; multi-profile fan-out with partial failure/retry; whether sharing authenticated state is safe and supported; OTR access grants and event/cache isolation; preserving component/unpacked restrictions; and hidden popup/extension-created window ownership under macOS AppKit. A passing compile or list UI alone does not establish update security, cross-profile sign-in parity, or popup/window lifecycle correctness.
