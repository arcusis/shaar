# Shaar engine module: history

Issue: [#418](https://github.com/arcusis/shaar/issues/418), with imported-history insertion for [#299](https://github.com/arcusis/shaar/issues/299). This extends [[Engine_Shaar_Layer_Design]] for the history module; it does not redefine the ABI or propose reusing Ardia implementation code. Chromium paths below are relative to the pinned `chromium_git/chromium/src` tree (Chromium 155.0.8059.84). The Ardia pin was inspected read-only at `source/ardia/engine/chromium/src`.

## Current Shaar app contract

Swift imports `ChromiumBridge`, not the `ac_engine.h` C types. `ChromiumEngineServices.mm` resolves the strings `history.query`, `history.delete_urls`, and `history.watch` to `ac_history_query`, `ac_history_delete_urls`, and `ac_history_watch` (`Sources/ChromiumBridge/ChromiumEngineServices.mm:47-56`). It binds each regular profile UUID to its canonical directory and sends that path to the Ardia call (`:82-110`). The current engine-service event envelope identifies a profile by directory and discards off-the-record events (`:118-126`); the new adapter must instead use the design's profile UUID plus explicit private session UUID. There is no Swift call today to `ac_history_add` or `ac_history_import`.

## Pinned Ardia behavior observed (description only)

`source/ardia/engine/chromium/src/chrome/browser/ardia/ac_history.cc` contains query, watch, and insertion handlers. It obtains `HistoryService` only for a regular `Profile`, explicitly rejecting null and off-the-record profiles, via `HistoryServiceFactory::GetForProfile(..., ServiceAccessType::EXPLICIT_ACCESS)` (lines 50-56). Query uses `QueryHistory` with all duplicates, groups by URL, caps URL and visit counts (defaults 5000 URLs and 50 visits), and returns newest visits first (240-294). URL deletion validates `GURL`s and calls `HistoryService::DeleteURLs` (404-422).

The watcher implements `history::HistoryServiceObserver`: it forwards eligible visible visits, modified URL rows and deletion summaries, batches them for 20 ms or 2000 changes, and observes one service per `Profile*` in a process-static map (80-164, 424-439). Preserve notifications for external changes, but replace the process-global raw-profile-keyed registry with a service owned by the Shaar profile/service lifecycle, explicit watch tokens and deterministic unwatch/teardown. Current app invalidation only needs a coarse changed notification; Swift can re-query rather than consume private visit data in the event.

The source also has two insertion paths which are not currently resolved by the app: `ac_history_add` accepts URLs, titles and individual epoch-ms visits, checks `CanAddURLToHistory`, compares existing visits in a DB task using a default 1000 ms tolerance, and adds only unmatched visits through `HistoryService::AddPage(HistoryAddPageArgs)` (296-368). `ac_history_import` accepts URL summary rows and calls `AddPagesWithDetails` with `SOURCE_BROWSED` (370-402). Fresh implementation should preserve the product behavior needed by #299—valid web history rows, title/timestamp, visit counts or individual visits, duplicate-safe repeat import, and accurate per-row outcome—without porting the old helper or its DB task. Prefer public `HistoryService` operations over direct `HistoryDatabase` access.

Chromium patch audit: no patch in the pinned `engine/patches/series` is required for these handlers or alters `HistoryService` query/add/delete/observer behavior. `chromium-background-features-off.patch` changes `components/history_clusters/core/features.cc` only; it disables History Clusters and is not a prerequisite for history storage or the APIs above. Do not treat that unrelated patch as an insertion dependency.

## Chromium-native APIs for Shaar implementation

Use the already-present Chromium interfaces in the pinned tree; no history-specific Chromium patch is indicated by this inventory.

| Need | Chromium API / source path |
| --- | --- |
| Service for the exact regular profile | `chrome/browser/history/history_service_factory.h` (`HistoryServiceFactory::GetForProfile`) and `components/history/core/browser/history_service.h`; require the profile handle in the submitted `shaar_scope`, use explicit service access, and reject OTR for persistence. |
| Bounded history query and visits | `components/history/core/browser/history_service.h` (`HistoryService::QueryHistory`, `QueryOptions`) and `components/history/core/browser/history_types.h` (`URLResult`, `QueryResults`). Use Chromium query options, cap and validate in the service layer, group URL rows deterministically, and serialize timestamps in epoch milliseconds for the adapter. Use `QueryURL` from the same header for a specific URL when needed; do not scan the raw database for ordinary queries. |
| Delete URLs | `components/history/core/browser/history_service.h` (`HistoryService::DeleteURLs`); validate every URL. The Chromium API is fire-and-forget, so do not claim a deletion count from its immediate return: correlate the observer deletion notification and/or query the affected URLs before completing, with cancellation/timeout mapped to typed errors. Still guarantee the initiating adapter sees a refresh after acknowledged success. |
| Insert imported individual visits | `components/history/core/browser/history_service.h` (`HistoryService::AddPage(HistoryAddPageArgs)`) and `components/history/core/browser/history_types.h` (`HistoryAddPageArgs`, `URLRow`, `QueryOptions`); validate `GURL`, `CanAddURLToHistory` from `chrome/browser/history/history_utils.h`, source/transition and timestamps. For URL-summary-only imports, `HistoryService::AddPagesWithDetails` is available in `history_service.h`, but it does not carry each original visit time; use `AddPage` when source data has individual visits. |
| Watch and own teardown | `components/history/core/browser/history_service_observer.h` (`HistoryServiceObserver::OnURLVisited`, `OnURLsModified`, `OnHistoryDeletions`, `HistoryServiceBeingDeleted`) and `components/history/core/browser/history_service.h` (`AddObserver`, `RemoveObserver`). Use a profile-owned observer/service with scoped observation, weak/cancellable asynchronous replies and handle invalidation on close. Filter hidden/subframe transitions for user-visible visit events; history mutation events may simply carry a change kind and affected URL set/count. |
| Existing importer writer precedent | `chrome/browser/importer/profile_writer.cc` uses `HistoryService::AddPagesWithDetails`; consult for expected importer source and URL-row write behavior, not as an ABI or implementation dependency. |

`HistoryService` callbacks and observer notifications are asynchronous. Bind/validate the scope on the Chromium UI thread, copy caller buffers before returning, marshal completion through the ABI dispatcher, and prevent callbacks after request cancellation, profile close, or engine shutdown. Avoid issuing one unbounded all-history query: use a validated cap compatible with the app's limit growth, and define an explicit cursor/continuation if history beyond that cap is required.

## `shaar_engine.h` additions and operation schemas

Follow [[Engine_Shaar_Layer_Design]] ABI v1 verbatim for export visibility, `shaar_submit`, `shaar_scope`, request IDs, async callback lifetime, typed `shaar_error_code`, and event identity. Add operation enum members to the design's existing `shaar_operation`; do not add a second transport or export Chromium C++ types. The existing `SHAAR_OP_HISTORY_INSERT` is the #299 insertion operation. Add `SHAAR_OP_HISTORY_WATCH` and `SHAAR_OP_HISTORY_UNWATCH` so subscriptions have explicit cancellation and teardown. Keep all three operations in the history module target under `chrome/browser/shaar/services/`.

All history operations require exactly one explicit scope as defined by `shaar_scope`, a live profile handle, no window/tab handle, and a request ID. Initially query, delete, insert and watch are supported only for the regular profile. If the scope contains a private session, return `SHAAR_PRIVATE_DISALLOWED` (not an empty list, ignored write, or parent-profile fallback). This makes private-session behavior explicit and ensures OTR events are never mislabeled as regular history. Watch handles are engine-owned opaque subscription IDs returned in the result; unwatch is idempotent for a subscription owned by the supplied profile and rejects a cross-profile token with `SHAAR_WRONG_PROFILE`.

| `shaar_operation` | Versioned `args_json` / async result |
| --- | --- |
| `SHAAR_OP_HISTORY_QUERY` | Args `{schemaVersion:1, maxUrls:<1..5000>, maxVisitsPerUrl:<1..50>, search?:<UTF-8 string>, cursor?:<opaque string>}`. Result `{schemaVersion:1, entries:[{url,title,visitCount,visits:[<epoch-ms>...]}], nextCursor?:<opaque string>}`. For the existing screen the adapter requests `maxVisitsPerUrl:1`; validate URL and numeric ranges before Swift model construction. Search is optional server-side; local filtering may remain initially. Cursor is ordered and bound to the profile, and should be omitted from ABI v1 if a stable Chromium query continuation cannot be implemented safely; in that case document the hard cap and return a typed `SHAAR_POLICY_BLOCKED`/range error rather than silently claiming complete history. |
| `SHAAR_OP_HISTORY_DELETE` | Args `{schemaVersion:1, urls:[<1..500 validated URLs>]}`; result `{schemaVersion:1, deleted:<count>}`. `HistoryService::DeleteURLs` has no completion callback; acknowledge only after observing completion/querying affected URLs, otherwise return a typed timeout/service error. Invalid rows fail validation instead of being silently dropped. |
| `SHAAR_OP_HISTORY_INSERT` | Args `{schemaVersion:1, source:<safari|chrome|arc|firefox>, pages:[{url,title?,visits:[<epoch-ms>...]}]}`. Apply to the explicitly selected regular profile only. Validate the whole batch, enforce count/byte/time bounds and `CanAddURLToHistory`, then insert preserving supplied visit timestamps. Define idempotence against existing visits with a documented tolerance (initial parity target 1000 ms) and return `{schemaVersion:1, accepted, insertedVisits, duplicateVisits, rejected:[{index,code}]}`. Partial-row rejection is visible to preview/results; malformed top-level input fails with `SHAAR_INVALID_ARGUMENT`. Empty or all-invalid imports are not success-shaped no-ops. |
| `SHAAR_OP_HISTORY_WATCH` | Args `{schemaVersion:1}`; result `{schemaVersion:1, subscriptionId:<opaque token>}`. Attach a profile-owned observer once per service and fan out notifications to active subscriptions. |
| `SHAAR_OP_HISTORY_UNWATCH` | Args `{schemaVersion:1, subscriptionId:<opaque token>}`; result `{schemaVersion:1}`. Remove the caller's subscription; profile close automatically removes all its subscriptions. |

All calls produce the design's normal `shaar_result` with typed errors: `SHAAR_INVALID_ARGUMENT` for invalid schemas/ranges/URLs, `SHAAR_NOT_READY` before profile/history service initialization, `SHAAR_NOT_FOUND` for a missing profile or subscription, `SHAAR_WRONG_PROFILE` for cross-profile handles/tokens, `SHAAR_PRIVATE_DISALLOWED` for private-scope persistence, `SHAAR_CANCELLED` for cancellation before completion, `SHAAR_IO_ERROR` or `SHAAR_CHROMIUM_ERROR` for service failures, and `SHAAR_SHUTTING_DOWN` during teardown. Never encode a failure only as a JSON `{error:...}` payload.

Add `SHAAR_EVENT_HISTORY` to the existing event stream (already present in the shared design enum). Each history event carries `profile_id` as the Shaar profile UUID, empty `session_id` for regular scope, empty window/tab IDs, sequence, and payload `{schemaVersion:1, kind:changed|visit|modified|deleted|watchError, urls?:[...], all?:bool}`. Coalesce observer bursts with a bounded timer/queue. Do not include raw profile paths. For private scope no history events are emitted. Event delivery follows mutation ordering and occurs only after the relevant Chromium state change; retain the design's monotonic sequence and no-inline-callback rules.

## Swift adapter changes

Keep the Objective-C `ARCChromiumRuntime` facade consumed by SwiftUI during migration. In `ChromiumEngineServices.mm` replace the `ac_*` symbols, profile-path cache and legacy `offTheRecord` parsing with a Shaar engine/profile handle table and `shaar_submit`; translate typed engine errors to stable localized `NSError` values. Copy borrowed result/event buffers before returning from callbacks. Route history events only when both the known profile UUID and expected empty regular `session_id` match; invalidation remains `onLibraryChanged(profileID, "history")`.

In `ChromiumLibrary.mm`, retain the current facade selectors but map query/delete to the new operations and strictly validate the result schema and typed completion. Add private-session rejection to the bridge instead of falling back to the parent. Move history watch start/stop with profile binding/teardown and deliver observer failure to `onLibraryError`. On successful insert/delete, invalidate all windows for that profile after acknowledged mutation until tests prove event-only refresh is race-free; keep `BrowserRuntimeEvents.swift:212-222`'s explicit post-delete refresh during the transition.

In `BrowserEngine.swift`, keep library request generation/stale-result handling and localized failures. Extend `BrowserImportPreviewView` and its importer model to preview history rows and visit counts, bind import to the chosen `profileID`, call `SHAAR_OP_HISTORY_INSERT`, and show inserted/duplicate/rejected counts only after the typed result arrives. `BrowserHistoryEntry` can keep its public shape for current UI; add a source-import history value type that preserves individual visit timestamps until engine submission. Do not treat source browser access or a successful preview as authorization to import private browsing records; import only history the user selected from readable source data.

## Tests and parity gates

**Unit tests (Chromium service layer and Swift bridge/model):** validate scope exclusivity, profile/session identity, OTR rejection, URL schemes/lengths, timestamp finite/range checks, batch and reply limits, ordering, duplicate URLs/visits, insert idempotence and tolerance boundaries, title precedence, delete validation, unknown schema/version, stale/cancelled callbacks, event coalescing/sequence, observer destruction and subscription ownership. Add Swift tests that decode query rows, reject malformed/duplicate results, map typed errors and ensure import targets the selected profile.

**Engine simulation (headless, no Chromium build in this module-spec task):** with two temporary regular profiles and one private session, seed visits with distinct timestamps/titles, query each profile and prove isolation; delete one URL and all-history through batches; hold a watch while adding, modifying and deleting rows and assert one correctly scoped invalidation stream; close a profile while query/insert/watch callbacks are pending and prove cancellation and no use-after-close. Attempt every history operation with a private scope and assert `SHAAR_PRIVATE_DISALLOWED` and no persistent writes/events. Import the same Safari/Chrome/Arc/Firefox fixture twice and prove the second pass reports duplicates, timestamps and profile isolation remain correct, and malformed rows are counted/reported rather than silently accepted.

**Smoke checks in the source-engine CI lane:** launch the Shaar framework against a clean profile, open History and load more than 500 rows using continuation/cap semantics, search locally, delete one entry and clear the profile history, then verify a second profile is unchanged. Import a small fixture into the selected profile from each supported source adapter, confirm preview and post-import row/visit counts, restart and verify persistence. Open private windows and verify their history is absent from regular query/import and that no private history event enters regular Swift caches. Run the existing Swift library/settings/importer tests and the focused native history probe; keep the normal prebuilt-engine CI lane green during migration.

Acceptance is current UI query/delete/watch parity plus #299 selected-profile, previewed, duplicate-safe insertion. A successful compile or mocked service test alone does not prove Chromium persistence, observer teardown, or private isolation; source-engine smoke evidence is required before switching the adapter default.

## Effort and risks

Estimate: **2–3 engineer-weeks**, matching the shared design's bookmarks/history module band, excluding Chromium sync/build wall time. Includes native service, adapter compatibility, import model/preview, CI fixture/probe and review. The extra import UX/data shaping for #299 can add 1–2 weeks if source readers do not currently expose visit-level timestamps consistently.

Key risks: Chromium history service readiness and async cancellation/profile teardown; `DeleteURLs` acknowledgement versus observer timing; preserving distinct visit timestamps without direct database access; importer differences across Safari, Chrome, Arc and Firefox; duplicate detection tolerance that may collapse legitimate close visits; privacy mistakes that bind OTR data to parent-profile events; high-volume imports/queries causing UI or memory pressure; and a capped query that appears complete when older rows exist. Keep limits explicit, test source-format mapping per browser, make partial import counts visible, never persist private history, and do not remove the Ardia adapter until the source-engine fixture and smoke gates pass.
