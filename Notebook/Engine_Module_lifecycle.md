# Shaar engine module: lifecycle

Issue #418 module specification. This extends [[Engine_Shaar_Layer_Design]] (ABI v1 and placement) with the lifecycle, framework, app-host, profile and private-session boundary; it does not define a second ABI. The design agent owns the overall public header. Keep its opaque handles, size-versioned structs, major/minor negotiation, profile/session scope, typed `shaar_error_code`, request IDs, single sequenced event stream and borrowed `NSView *` convention. Chromium source paths below are relative to the read-only pinned checkout `engine-333-364/build/EngineSource/chromium_git/chromium/src` (Chromium 155.0.8059.84); Ardia paths refer only to the read-only pin for behavioral inventory.

## A. What Shaar uses today

There are no lifecycle `ac_*` calls. `ac_*` is dynamically loaded only for profile services. Startup, run-loop ownership, quit and window hosting cross the Objective-C adapter through `ArdiaCoreEngine` and its delegate instead. The Swift app imports `ChromiumBridge`, not Ardia headers.

## B. Ardia behavior and hooks to replace

Ardia’s macOS entry is an Objective-C façade over Chromium’s `ChromeMain`. `packages/ardiacore/ios/ArdiaCoreStartup.mm` enters the framework; `engine/ardiacore/src/ardia/core/ardiacore_api.mm` implements `+[ArdiaCoreEngine runWithArgc:argv:delegate:]`, installs hooks and callbacks, calls `ChromeMain`, exposes `sharedEngine`, profile loading and `quit`. Its delegate lifecycle is `engineDidStart`, `engineWillShutDown`, and `engineQuitCancelled` (`engine/ardiacore/src/ardia/core/public/ArdiaCore.h`). `ac_main_delegate.cc` wraps `ChromeBrowserMainParts`, posts its started callback on the UI task runner, and runs shutdown cleanup from `PostMainMessageLoopRun`. The run-loop wrapper supplies a `base::RunLoop` and wires `BrowserProcessImpl::SetQuitClosure` when Chrome has no loop.

Quit is staged in `ac_lifetime.mm`: ask the app host, check blocking downloads, set Chromium’s trying-to-quit state, close browsers, then quit the run loop. A generation token rejects stale prompt answers; cancellation resets close state and notifies the app. `ac_browser.mm` and `ac_browser_window.mm` provide close coordination. `ac_host_visibility.mm` and `ac_lifetime.mm` also address native-host visibility and process exit behavior. The Objective-C wrapper installs a five-second repeated shutdown stop and a 30-second failure bound because Chromium may lose its AppKit loop stop after `NSApplicationWillTerminateNotification`; Shaar separately disables Chromium background mode and guards loop shutdown (`ChromiumBridge.mm:233-237`; see [[Quit_Exit_Verification]]).

Ardia profile loading uses `ProfileManager::CreateProfileAsync`/existing profile lookup (`ardiacore_api.mm`); its Swift/ObjC wrapper owns object wrappers and profile waiters. OTR windows share a primary OTR profile acquired from the original profile; that lease is implemented in `ChromiumPrivateBrowsing.mm` and Ardia’s browser/window wrappers. The Shaar ABI should instead require an explicit `shaar_profile` or `shaar_private_session` scope on every operation and event.

**#333 pending-navigation quit fix:** the pinned Chromium call path can find a tab’s `BrowserWindowInterface` through the tab association after the browser has already left the live browser collection. `ExtensionTabUtil::GetWindowControllerOfTab` then reads unowned window user data during teardown when a non-network response reaches commit, causing the observed SIGSEGV. The existing Shaar patch `quit-pending-navigation-window-controller.patch` changes that lookup to `GlobalBrowserCollection::GetInstance()->FindBrowserWithTab(web_contents)` and returns no controller when the browser is no longer live. This fixes the stale ownership lookup; stopping loading tabs alone did not. Port and test this guard in Shaar-owned Chromium source; do not copy Ardia code. Patch target in Chromium 155: `chrome/browser/extensions/extension_tab_util.cc`, function `ExtensionTabUtil::GetWindowControllerOfTab`.

## D. ABI and Swift adapter changes

Continue the exact `shaar_engine.h` ABI v1 sketch in [[Engine_Shaar_Layer_Design]]; do not create lifecycle-specific reply/event structs or a parallel version system. Proposed exported lifecycle surface:

```c
uint32_t shaar_abi_major(void);
uint32_t shaar_abi_minor(void);
shaar_error_code shaar_engine_create(const shaar_config *, shaar_engine **out,
                                     shaar_error *error);
shaar_error_code shaar_engine_run(shaar_engine *, shaar_error *error);
shaar_error_code shaar_engine_request_quit(shaar_engine *, shaar_error *error);
void shaar_engine_release(shaar_engine *);
shaar_error_code shaar_profile_open(shaar_engine *, shaar_bytes profile_id,
                                    shaar_bytes directory, shaar_profile **out,
                                    shaar_error *error);
shaar_error_code shaar_profile_close(shaar_profile *, shaar_error *error);
shaar_error_code shaar_private_session_open(shaar_profile *, shaar_bytes session_id,
                                            shaar_private_session **out,
                                            shaar_error *error);
shaar_error_code shaar_private_session_close(shaar_private_session *,
                                             shaar_error *error);
shaar_error_code shaar_window_open(shaar_scope, shaar_bytes window_id,
                                   shaar_window **out, shaar_error *error);
shaar_error_code shaar_window_close(shaar_window *, shaar_error *error);
void *shaar_window_host_view(shaar_window *); /* borrowed NSView * */
```

The create call negotiates requested major/minor and all struct sizes before launching Chromium. Missing symbols, major mismatch, undersized required structs, and bad config fail before Swift restores a workspace. A minor-compatible framework may append fields; callers pass `size`, and the engine reads only fields negotiated for that minor. Record loaded ABI major/minor and required exports in the source-build receipt. Return `SHAAR_UNSUPPORTED_ABI`, `SHAAR_INVALID_ARGUMENT`, `SHAAR_NOT_READY`, `SHAAR_NOT_FOUND`, `SHAAR_WRONG_PROFILE`, `SHAAR_WRONG_SESSION`, `SHAAR_PRIVATE_DISALLOWED`, `SHAAR_CANCELLED`, `SHAAR_IO_ERROR`, or `SHAAR_SHUTTING_DOWN` as applicable; preserve diagnostic text in `shaar_error.message`, never encode failure as an empty success payload.

Emit lifecycle transitions through the existing one event stream: `SHAAR_EVENT_ENGINE` (`engine.ready`, `engine.quitRequested`, `engine.quitCancelled`, `engine.willShutDown`, `engine.stopped`, `engine.startupFailed`) and `SHAAR_EVENT_PROFILE`, `SHAAR_EVENT_PRIVATE_SESSION`, and `SHAAR_EVENT_WINDOW` (`opened`, `closeRequested`, `closed`, `invalidated`). Keep monotonic sequence numbers and explicit profile/session/window IDs. The event stream carries no filesystem paths. A shutdown that is cancelled emits `quitCancelled`, resets closing state and preserves valid handles; a committed shutdown cancels outstanding requests, emits final close/invalidation events, detaches borrowed views, invalidates handles, releases callback context, then returns from `shaar_engine_run`. Keep prompt request IDs and expiry for any engine-owned blocking download/close confirmation; add the dedicated typed prompt-response operation described by the parent design rather than a generic unvalidated JSON response.

`shaar_profile_open` binds one caller-owned UUID to one canonical directory for the handle lifetime and refuses duplicate/conflicting bindings. `shaar_private_session_open` returns a distinct opaque OTR handle with the parent profile and session UUID attached. `shaar_scope` must set exactly one profile or private-session pointer; windows, tabs, events and service operations must match it. Private events carry both IDs and must reach Swift instead of being dropped. Engine process lifetime is single-run; profile/window close is explicit and idempotency/error behavior must be documented for stale handles.

Swift adapter work stays inside `ChromiumBridge`: replace `dlopen`/Ardia class-name lookup with `dlopen` and `dlsym` of required `shaar_*` symbols; validate ABI before constructing runtime; own opaque handles and copy all borrowed bytes/events before callback return; translate `shaar_error_code` into stable `NSError`/Swift errors; marshal event delivery onto `MainActor`; adapt current `onReady`, `onQuitCancelled`, window-close, and window-request callbacks to the typed sequenced event stream. Keep `ARCChromiumRuntime` as the migration façade while `NativeBrowserHost`, `BrowserRuntimeEvents`, `BrowserEngine`, and private host move module-by-module. On run return, detach host callbacks and flush `BrowserWorkspaceStore` before returning from `NativeBrowserHost.run`. Release the framework only after engine handles/callbacks are invalid and borrowed views detached; avoid calling `dlclose` while Chromium process-global state or framework-owned callbacks remain.

## F. Effort and risks

Estimate **2–3 engineer-weeks** for lifecycle and regular profiles, plus **2–4 engineer-weeks** for first-class private sessions (matches module rows 1 and 4 in the parent plan). The shared ABI scaffold is estimated separately at 1–2 weeks. These estimates exclude Chromium sync/build wall time and CI queue time.

Primary risks: Chromium’s browser startup and run loop are process-global and not a supported embedding API; the AppKit host ownership and shutdown ordering must survive updates to Chrome browser internals; stale observer callbacks or delayed prompt replies can race handle invalidation; profile UUID-to-path mistakes can cross data boundaries; OTR lifecycle is parent-profile-bound but must remain a distinct event and operation scope; a lost AppKit loop stop or background keep-alive can leave helpers alive; and the #333 fix must query live browser ownership on shutdown instead of relying on tab association. Preserve the old Safe Storage identity and the existing workspace snapshot/flush order. A green ABI unit suite or successful launch does not prove pending-navigation safety, private isolation, app-host parity, or complete process exit.
