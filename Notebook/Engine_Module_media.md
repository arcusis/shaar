# Engine module: media

Issue: [#418](https://github.com/arcusis/shaar/issues/418). This note extends migration row 13 (Media) in [[Engine_Shaar_Layer_Design]] for playback state and controls, media capture, picture-in-picture, screen/window sharing, and video dimensions. It follows [[Engine_ABI_Conventions]] and the design's ABI v1: one exported `shaar_engine.h`, opaque handles, `shaar_scope`, one event stream, borrowed length-delimited UTF-8, asynchronous replies, typed `shaar_error_code`, copied Swift payloads, UI-thread serialization, and no Chromium C++ types across C. This is fresh replacement analysis; no Ardia implementation is proposed for reuse.

## A. Shaar app behavior today

The Swift app calls `ARCChromiumRuntime` through `ChromiumBridge`; it imports no `ac_*` symbol for media. The adapter still owns Ardia objects internally, especially `ArdiaCoreTab` callbacks and per-tab WebContents calls. The inventory's global event sink filters private events, so media callbacks currently lack the new ABI's required profile/session identity.

| Behavior | Current app and bridge route |
| --- | --- |
| Playback state / media session | `BrowserEngine.swift:330-331` receives `onMediaSessionChanged`; `BrowserEngineMedia.swift:11-18` validates owned live-tab identity and updates `MediaPlaybackModel`; `MediaSession.swift:7-19,39-120` defines playback states, supported actions and typed parsed fields; `MediaPlaybackModel.swift:10-48` keeps the active and recently-playing tab state; `SidebarMediaPlayer.swift` renders controls. The page report includes playback state, title, artist, album, HTTP(S) artwork, supported actions, `hasVideo`, `canSeek`, tab mute, silence, optional page volume, and PiP video playing/live state. No video width/height is currently exposed to Swift.
| Media commands | `BrowserEngineMedia.swift:20-29,121-133` maps Swift actions to `ARCMediaSessionAction`; it calls `sendMediaSessionAction`, `setMuted`, and `setMediaVolume`. Volume is page element volume; mute is Chromium tab audio mute. PiP control commands are separate at `:62-77`.
| PiP | `AutoPictureInPicture.swift:7-83` opens for an audible playing video leaving visible pages and closes on return; the site allow/deny is persisted per profile/site (`BrowserStorePictureInPicture.swift:11-29`). `BrowserEngineMedia.swift:39-60,91-109,135-141` asks Chromium to enter/exit PiP, applies site policy, attaches/detaches controls, and observes active state. `PictureInPictureControls.swift:7-207` adds Swift close/back-to-tab, play/pause, skip, minimize, move/resize controls over Chromium's video window. `ChromiumBridge.h:225-246` declares the present runtime calls, including a direct `NSWindow *` getter. PiP active callbacks currently have only tab ID and active bool; the bridge tracks the video-PiP owner separately.
| Sharing picker / capture | The engine sends `desktopCaptureRequested` on the permission event once ABI minor is 14. `ChromiumShaarBackend.mm` accepts that event only for a live tab in its own window and profile, then `BrowserEngine` asks `BrowserStore` to present `DesktopCapturePicker`. `DesktopCaptureRequest` validates the secure origin, profile, tab, page, and frame. A page title cannot open the picker. The picker uses ScreenCaptureKit for on-screen windows and displays and lists only tabs in the requesting profile. The app replies with `SHAAR_OP_MEDIA_CAPTURE_REPLY`. The same engine also reports active camera, microphone, and screen capture state via `onMediaAccess`.
| Swift/test coverage | Existing unit suites include `MediaPlaybackModelTests`, `AutoPictureInPictureTests`, `PictureInPictureControlsTests`, and `DesktopCaptureConsentTests`; `MediaSessionReadinessTests` covers readiness parsing. `Sources/ShaarVerification/MediaSessionProbe.swift` exercises playback, sidebar, PiP transitions and controls; `MediaPermissionProbe.swift` exercises media permissions; `EngineProbe.swift:676-681` runs these probes in the engine simulation. These are parity assets to keep, not proof of the new C++ layer until the source-engine lane runs them against it.

Media state and prompt payloads are page/frame-derived input, not trusted engine facts. Preserve validation and ownership checks in the adapter, and put authoritative Chromium observations in the new engine events. Use the design's `profile_id` and `session_id` on every event and request, with private session IDs present for OTR. Never put filesystem profile paths or Chromium frame/process IDs in public event identity fields.

## D. C ABI and Swift adapter proposal

Add this as the media-module extension to the existing header sketch, not as another ABI or event channel. Keep `SHAAR_OP_MEDIA_CONTROL` and `shaar_submit` from `Engine_Shaar_Layer_Design`; document strict, versioned JSON schemas for `getState`, `control`, `setAutoPictureInPicture`, `enterPictureInPicture`, `exitPictureInPicture`, `listCaptureSources`, and `captureReply`. For typed call sites, prefer the following narrow functions (or make them typed wrappers over `shaar_submit`) with the design's size-checked `shaar_scope`, `shaar_request_id`, `shaar_reply_fn`, and `shaar_error` conventions. Every exposed enum value has an explicit stable numeric value in the consolidated header:

```c
typedef enum {
  SHAAR_MEDIA_PLAY = 0, SHAAR_MEDIA_PAUSE = 1,
  SHAAR_MEDIA_PREVIOUS_TRACK = 2, SHAAR_MEDIA_NEXT_TRACK = 3,
  SHAAR_MEDIA_SEEK_BACKWARD = 4, SHAAR_MEDIA_SEEK_FORWARD = 5,
  SHAAR_MEDIA_SEEK_TO = 6, SHAAR_MEDIA_SET_TAB_MUTED = 7,
  SHAAR_MEDIA_SET_ELEMENT_VOLUME = 8, SHAAR_MEDIA_PIP_PLAY = 9,
  SHAAR_MEDIA_PIP_PAUSE = 10, SHAAR_MEDIA_PIP_SKIP = 11,
  SHAAR_MEDIA_PIP_ENTER = 12, SHAAR_MEDIA_PIP_EXIT = 13
} shaar_media_command;
typedef enum { SHAAR_CAPTURE_CANCEL = 0, SHAAR_CAPTURE_APPROVE = 1 }
    shaar_capture_decision;

SHAAR_EXPORT shaar_error_code shaar_media_get_state(
    shaar_scope, shaar_tab *, shaar_request_id, shaar_reply_fn, void *, shaar_error *);
SHAAR_EXPORT shaar_error_code shaar_media_control(
    shaar_scope, shaar_tab *, shaar_media_command, double value,
    shaar_request_id, shaar_reply_fn, void *, shaar_error *);
SHAAR_EXPORT shaar_error_code shaar_media_set_auto_pip(
    shaar_scope, shaar_tab *, int allowed, shaar_request_id,
    shaar_reply_fn, void *, shaar_error *);
SHAAR_EXPORT shaar_error_code shaar_media_list_capture_sources(
    shaar_scope, shaar_tab *, shaar_request_id, shaar_reply_fn, void *, shaar_error *);
SHAAR_EXPORT shaar_error_code shaar_media_capture_reply(
    shaar_scope, shaar_request_id prompt_id, shaar_capture_decision,
    shaar_bytes opaque_source_token, shaar_error *);
SHAAR_EXPORT shaar_error_code shaar_media_pip_window(
    shaar_scope, shaar_tab *, shaar_window **out, shaar_error *);
```

All results and events use the existing typed error envelope. Return `SHAAR_WRONG_PROFILE` / `SHAAR_WRONG_SESSION` for scope mismatch, `SHAAR_PRIVATE_DISALLOWED` for persistence or policy forbidden in OTR, `SHAAR_PERMISSION_DENIED` for a rejected/expired capture or PiP policy, `SHAAR_NOT_FOUND` for closed tabs/prompts, `SHAAR_INVALID_ARGUMENT` for invalid finite/range values, and `SHAAR_POLICY_BLOCKED` for unsupported-by-policy capture/device types. If a platform operation is unavailable with a distinct recovery action, propose a new module error code with that distinction for ABI reconciliation. Immediate validation failure returns synchronously and does not call completion; accepted async requests complete once, with result/event ordering unspecified as defined by the shared convention. A boolean `false` must never ambiguously mean permission denied, unsupported, or stale tab.

Emit existing `SHAAR_EVENT_MEDIA` records with `profile_id`, `session_id`, `window_id`, `tab_id`, sequence, payload `kind`, `schemaVersion`, and subtype: `state_changed`, `pip_changed`, `capture_request`, `capture_dismissed`, `capture_state_changed`, and optional `video_dimensions_changed`. Media state includes playback state, title/artist/album/artwork, supported action enum values, seekability, has-video, tab mute, optional page volume/silent, and optional PiP video state. Dimensions are nullable unsigned intrinsic pixel width/height, with zero/unknown represented as absent; never substitute display or PiP window bounds. Capture source listing returns Swift-picker labels plus expiring opaque engine tokens. A `capture_request` carries prompt UUID, requesting origin, page URL, frame/document identity needed for freshness checks, and expiry. Capture replies use only a token issued for that prompt. On navigation, tab close, profile/private-session close, renderer loss, or expiry, dismiss the prompt and cancel the pending media request. Revalidate profile/session/tab/frame/document/origin at reply time. Do not echo raw ScreenCaptureKit source IDs into page script or event logs.

Represent Chromium's PiP window as a `shaar_window` owned by the engine and reachable through `shaar_media_pip_window`; Swift then uses the existing `shaar_window_host_view` borrowed-`NSView *` exception. Reuse or add documented typed window-bounds operations so the Swift overlay can move/resize it without exporting `NSWindow *`, `VideoOverlayWindow *`, controller pointers, or a C++ handle. The view is valid only for the documented handle lifetime; window recreation emits detach/attach and invalidates the old handle/view before the replacement is delivered. This keeps the ABI's single native-view exception rather than creating a media-specific one.

Swift adapter work stays in `ChromiumBridge` and `ArcusisBrowser`: translate typed events and errors in the existing router/event path; key caches by `(profileID, sessionID, tabID)` so private media state cannot collide with or populate regular-profile state; preserve existing Swift models and controls where semantics match; replace `ARCMediaSessionAction`, `NSWindow *` PiP lookup and `resolveDesktopCaptureRequestID` internals with the new wrapper calls; retain the ScreenCaptureKit consent UI while populating it from engine-enumerated source labels/tokens; update `MediaSessionState` only if dimensions become a UI requirement. Map engine errors to `LocalizedError`, never success-shaped empty state. Private-session events stay first-class and private media state is removed on session close without persistence.

## F. Effort and risks

Rough estimate: **4–7 engineer-weeks**, excluding Chromium sync/build time, matching the design's phase-11 estimate. A likely split is 1–2 weeks playback session observation and typed controls; 1–2 weeks capture consent and picker bridge; 1–2 weeks PiP window ownership/Swift host controls; 0.5–1 week dimensions and contract tests; plus integration/CI fixes. Reuse existing Swift UI/model behavior where semantics match, but implement all engine code independently.

Main risks: Chromium's media session is per-WebContents but PiP manager is process-global; mixed regular/private sessions and multiple windows can misroute events if ownership is inferred. The existing custom picker passes OS identifiers through script glue, so source tokens must become opaque and engine-validated. Native MediaSession does not fully match frame-specific JS action handlers or page element volume. Chromium's PiP public controller has no supported native window getter, so host/view and geometry need a deliberate Shaar-owned seam that survives recreation and still follows the ABI's borrowed-view rule. Intrinsic dimensions are not surfaced by `MediaSessionPlayerObserver`; exposing them may require a small renderer companion and therefore expands the interface. Existing rendering/performance patches may affect playback smoothness but are separate from the module API; each must be independently reimplemented or explicitly removed by the design/build work.

Acceptance for this module is C ABI and Swift parity across regular and private session scopes, passing CI simulation and smoke gates, with event ownership and capture/PiP teardown verified. This is not a source-engine build or release claim.
