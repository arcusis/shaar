# Shaar engine module: private sessions

Issue #418 module analysis; extends [[Engine_Shaar_Layer_Design]] ABI v1 and its phase 4 plan. This is a fresh design for Chromium 155. It does not reuse Ardia implementation. Chromium and pinned Ardia source references below are read-only references under `engine-333-364/build/EngineSource`.

## Current Shaar behavior and boundary

Shaar presents one or more private windows per regular profile. Windows for a profile share Chromium's primary off-the-record (OTR) profile, so their cookies/storage are shared for that profile. The bridge leases the OTR profile while any context uses it and releases it after the last private window closes. Private tabs, private windows, and context IDs are in-memory UUIDs; they are not restored from workspace state. OTR preferences disable credential saving and both Autofill save flows before the first private window opens. See `Notebook/Private_Browsing.md` for current product policy.

`Sources/ArcusisBrowser/PrivateBrowserHost.swift:55-76,105-150,182-260,262-352` creates the private context/window/tab, owns AppKit and SwiftUI windows, and consumes navigation/selection/close callbacks. `Sources/ArcusisBrowser/PrivateBrowserWindow.swift:179-191,225-247` embeds the selected private tab view and sends focus back to Chromium. The store is held by the native window owner; the view and callbacks use weak store references (`PrivateBrowserHost.swift:10-20,90-103`).

The current adapter methods and callbacks are Objective-C facade methods on `ARCChromiumRuntime`, not direct `ac_*` exports:

Private site controls are the private-specific use of the current `ac_*` service ABI. `ChromiumPrivatePrivacy.mm:38-44,60-100` calls `ac_site_settings_set` and `ac_site_settings_get` through `ARCEngineServices`, using the regular profile ID/path plus JSON `offTheRecord: true`; `Sources/ChromiumBridge/ChromiumEngineServices.mm:47-67,98-110` resolves and dispatches `ac_site_settings_get/set`. Swift exposes the control through `Sources/ArcusisBrowser/PrivateBrowserWindow.swift:160` and the `PrivateSiteControlsButton` route; the private UI remains on the bridge facade. Other relevant `ac_*` functions are the shared engine ABI calls `ac_engine_abi_version`, `ac_engine_set_event_sink`, and service calls that may receive OTR notifications. There are no private-window-specific `ac_*` exports currently called by Swift.

The event types today are Objective-C blocks on `ARCChromiumRuntime` with string `contextID`, `windowID`, and `tabID`; tab changes additionally carry URL/title/loading/back/forward state, and errors carry a display message. The separate `ac_engine_event_t` stream is decoded as topic plus JSON payload. It identifies an OTR service event only by the parent profile path and an `offTheRecord` flag: `ChromiumEngineServices.mm:118-126` discards true or malformed private flags. Consequently private service changes do not update regular-profile Swift caches, but the event loses its private-session identity and cannot drive first-class private UI state. The new stream must preserve the parent `profile_id` **and** a distinct `session_id` for every private event.

## Ardia implementation and implicit Chromium dependency

The inspected pin is Ardia `91e17a5655519d2dc385ec8452432469232ff9af` and Chromium `155.0.8059.84` (see `Engine_Ardia_Inventory.md`). Ardia's app layer obtains the primary OTR `Profile` from the source profile, wraps it as `ArdiaCoreProfile`, and returns/release-manages that wrapper. `source/ardia/engine/ardiacore/src/ardia/core/ardiacore_api.mm` implements the profile wrappers and OTR creation; `ac_lifetime.mm` handles Chromium profile lifetime; `ac_browser.mm` wraps `content::WebContents` as `ArdiaCoreTab`; `ac_browser_window.mm` wraps the Chrome `Browser`, native `NSWindow`/host view, tab creation, and tab activation. `ChromiumPrivateBrowsing.mm` layers Shaar's context/window/tab UUID ownership and asynchronous lease checks over those wrappers. `ChromiumPrivatePrivacy.mm` applies OTR site settings before loading each page.

Relevant pinned Chromium patches are `source/ardia/engine/patches/chromium-window-hosted.patch` (Ardia's embedded native view hit testing/accessibility and keep-window-with-empty-tab behavior) and `chromium-cef-carryover.patch` (the inventory calls out private-profile teardown safety among the carried host behavior). The patches are build inputs, not APIs to copy. `chromium-window-hosted.patch` modifies `components/remote_cocoa/app_shim/bridged_content_view.{h,mm}` and `chrome/browser/ui/browser.cc` / `unload_controller.cc`; it does not establish a second-tab rendering guarantee. The Chromium tree also has macOS native view and visibility behavior in `content/browser/web_contents/web_contents_view_mac.mm` and `content/browser/renderer_host/render_widget_host_view_mac.mm`.

### #417 black second tab: diagnosis and evidence boundary

The visible failure is specifically reported in the #364 preview engine and is not yet classified as a production-pin regression or a #364-only regression; the issue text gives no production comparison. The code identifies a high-confidence boundary to test: initial private-window creation opens a tab with `foreground:YES`, attaches its native view to Ardia's host, and activates it (`ChromiumPrivateBrowsing.mm:197-269`). Later tabs use `foreground:NO`, are attached and hidden by the adapter, and are selected by changing both `NSView.hidden` and `ArdiaCoreWindow.activateTab:` (`ChromiumPrivateBrowsing.mm:332-364,367-379`). Swift then reparents the selected view into a `ChromiumPageContainerView` with `attach` (`PrivateBrowserWindow.swift:225-243`; `ChromiumPage.swift:84-105`). This means AppKit visibility/reparenting and Chromium's active `WebContents`/compositor visibility have separate state transitions.

The proposed root cause is a missing or incorrectly ordered activation/visibility handoff for a background-created OTR `WebContents`: the native view can be selected in Swift while Chromium has not made its renderer/compositor visible and producing frames, yielding the black surface. This is a diagnosis from the ownership/activation paths, not a proven runtime finding. Confirm by recording, for each tab switch, selected tab ID, `WebContents` active/visible state, native view parent/bounds/hidden state, renderer frame arrival, and screenshot pixels. Run the same two-tab repro against production's pinned engine and the #364 preview artifact before attributing the defect to app or engine. The new layer must own one authoritative tab activation transition that updates both tab selection and WebContents visibility, and only publish selection after the native view has been attached, sized, shown, and received a compositor frame (or fail with a typed timeout/error).

## Chromium APIs for Shaar's own implementation

Use Chromium's OTR and `WebContents` APIs directly; keep the C ABI handles and all Shaar IDs in `chrome/browser/shaar/`. Paths are relative to the synced Chromium 155 tree at `build/EngineSource/chromium_git/chromium/src/`.

| Need | API and source path | Use in Shaar |
| --- | --- | --- |
| Resolve primary OTR profile and prove scope | `Profile::GetPrimaryOTRProfile(bool create_if_needed)`, `GetOriginalProfile()`, `IsOffTheRecord()`, `GetOTRProfileID()` in `chrome/browser/profiles/profile.h`; implementation `chrome/browser/profiles/profile_impl.cc` | One OTR profile per parent regular profile, keyed in engine state by parent profile handle plus generated private session ID. Never accept a filesystem path for OTR. Validate that the supplied parent is open and regular. |
| Observe OTR lifecycle | `ProfileObserver` and `ProfileManagerObserver` in `chrome/browser/profiles/profile_observer.h` and `profile_manager_observer.h`; `Profile::GetAllOffTheRecordProfiles()` / `HasOffTheRecordProfile()` in `profile.h` | Observe creation/destruction and invalidate session/tab handles before teardown. Keep the OTR lease until all Shaar private-session owners, windows, and tabs close; don't release a shared OTR profile from a stale callback. |
| Create/own page contents | `content::WebContents::Create`, `GetBrowserContext`, `GetNativeView`, `WasShown`, `WasHidden` in `content/public/browser/web_contents.h`; macOS native implementation in `content/browser/web_contents/web_contents_view_mac.mm` and `content/browser/renderer_host/render_widget_host_view_mac.mm` | Construct each private tab with the OTR `BrowserContext`; keep a `unique_ptr<WebContents>` per tab; use `GetNativeView()` as a borrowed AppKit view. On tab switch, hide/`WasHidden` the old contents and size/show/`WasShown` the selected contents as one UI-thread transaction. | Optional Chromium tab model | `Browser::Create` and `BrowserWindowCreateParams` in `chrome/browser/ui/browser.h`; `TabStripModel::AddWebContents`, `ActivateTabAt`, `GetActiveWebContents` in `chrome/browser/ui/tabs/tab_strip_model.h` | Only use if Shaar deliberately wants Chrome's tab activation/visibility lifecycle. Do not maintain a separate active-tab index in Swift and another one in Browser without a single commit point. For Shaar-owned NSWindow chrome, direct `WebContents` ownership may be simpler; verify that required Browser services still work before choosing. |
| Renderer/view state diagnosis | `RenderWidgetHostViewMac::SetActive`, `WasShown`/`WasHidden` handling in `content/browser/renderer_host/render_widget_host_view_mac.{h,mm}` and `WebContentsViewMac` in `content/browser/web_contents/web_contents_view_mac.{h,mm}` | Avoid calling internal renderer view methods from Swift. Use public `WebContents` visibility methods and native view lifecycle; add diagnostics in the engine to relate selected tab IDs to frame readiness. |

Chromium's standard `Browser`/`TabStripModel` may bring Chrome window assumptions. The implementation decision is therefore explicit: either make it the sole tab-selection authority or let Shaar's `shaar_window` own a WebContents collection and reproduce the required visibility/lifecycle calls. Do not combine partial `Browser` selection with independent Swift view selection.

## `shaar_engine.h` extension for this module

Keep the design document's ABI v1 rules: opaque handles, length-delimited UTF-8, UI-thread serialization, async replies delivered later, borrowed callback payloads, and typed `shaar_error_code`. Reuse `shaar_profile`, `shaar_private_session`, `shaar_scope`, `shaar_window`, `shaar_tab`, `shaar_submit`, and the global event callback already sketched there. Add no parallel private-only event sink.

The required functions are the design's `shaar_private_session_open(profile, session_id, out, error)` and `shaar_private_session_close(session, error)`, plus scope-based `shaar_window_open`, `shaar_tab_open`, `shaar_tab_close`, and operations dispatched by `shaar_submit`. Use the existing `SHAAR_OP_WINDOW_ACTIVATE_TAB` operation as the single activation call, and reply only after the engine commits selection and visibility; do not add a second activation function. `shaar_private_session_open` is idempotent only for the same live session ID and parent profile; another parent or a retired/reused ID returns `SHAAR_CONFLICT`/`SHAAR_WRONG_PROFILE`. A window/tab handle must match the supplied `shaar_scope`; mismatches return `SHAAR_WRONG_SESSION`, `SHAAR_WRONG_PROFILE`, or `SHAAR_NOT_FOUND`. Persistence-sensitive private operations (history insertion/query persistence, bookmarks, restore, durable download listing, workspace mutation) return `SHAAR_PRIVATE_DISALLOWED`; permissions/settings that Chromium supports in OTR must explicitly take the OTR `BrowserContext` and never silently fall back to the parent.

Use events from the existing `shaar_event` envelope. For every profile-scoped private event, set `profile_id` to the parent Shaar profile UUID and `session_id` to the private session UUID; include `window_id`/`tab_id` where applicable. Emit `SHAAR_EVENT_PRIVATE_SESSION` opened/closing/closed events, and ordinary `WINDOW`, `TAB`, `NAVIGATION`, `PERMISSION`, `DOWNLOAD`, `SITE_DATA`, and `MEDIA` events with the same private scope fields. Never use only the parent profile to label private activity, never infer the session from the tab ID, and never expose the profile directory. Sequence events after the state change; emit final tab/window/session close events before invalidating their handles. Event payloads include `schemaVersion` and stable IDs, not raw URL credentials or secrets. Use existing typed failures including `SHAAR_PRIVATE_DISALLOWED`, `SHAAR_WRONG_SESSION`, `SHAAR_WRONG_PROFILE`, `SHAAR_NOT_FOUND`, `SHAAR_POLICY_BLOCKED`, `SHAAR_CANCELLED`, and `SHAAR_CHROMIUM_ERROR`; no `false`/empty result that looks like success.

Swift adapter migration stays behind `ARCChromiumRuntime` during the compatibility period. Add a private-session handle map keyed by `(profileID, sessionID)`, carry the opaque session/window/tab handles through `PrivateBrowserHost`, and route the single C event stream to the existing private callbacks only after validating all four IDs. Map typed failures to `WorkspaceError`/localized private navigation errors. Remove the old `ac_*` `offTheRecord` JSON selector from private paths once OTR calls use a scoped handle. Ensure private state is never passed to `BrowserStore`, workspace persistence, regular profile download/library caches, or restart restoration. Preserve the current weak-store lifetime rule and close-before-release ordering.

| Layer | Required cases |
| --- | --- |

Event builder always emits parent profile plus session ID for private events and empty session ID only for regular events. Persistence-blocked operations reject before touching regular services. |
| Engine simulation | Extend the existing private fixture (`PrivateWindowProbe`, `PrivateProductHostProbe`, `PrivatePrivacyProbe`, and `scripts/engine_fixture.py`) to open two private tabs in one window and multiple windows under one profile; navigate distinct loopback origins; switch repeatedly in both directions; verify selected ID, visible native view, nonzero bounds, renderer frame/screenshot content, navigation/back/forward, close/reopen behavior, shared OTR cookies, and cleanup after last close. Do not call #417 fixed from compilation or an engine simulation alone: require native rendering evidence for the second tab and the production-vs-preview comparison. Existing `PrivateWindowProbe.swift` and `ProfilePrivacyProbe.swift` remain parity references; keep their privacy assertions and add render-frame assertions rather than weakening them.

## Effort and risks

Estimate **3–5 engineer-weeks** for this module including C ABI/Swift adapter, private OTR lifecycle, the multi-tab rendering fix, simulation coverage, and paired engine smoke evidence; this excludes Chromium source build/sync wall time and release work. Most work depends on phases 0–2 of the layer plan.

The main risks are OTR teardown racing windows or callbacks; accidentally treating a private event as regular profile state; `WebContents` native view attachment without correct visibility/size/frame scheduling; diverging activation state between Swift and Chromium; Chrome `Browser` APIs assuming Chrome-owned windows; and inheriting profile-level cookies/settings across private windows when the product expects this documented behavior. The production-versus-preview comparison is still outstanding, so the exact #417 trigger remains an implementation hypothesis pending the stated smoke evidence.
