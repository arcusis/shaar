# Shaar engine module: site settings, permissions and site data

Issue #418 module proposal for phase 2 design. This extends [[Engine_Shaar_Layer_Design]] migration row 9 and uses its `chrome/browser/shaar/` placement, `public/shaar_engine.h` export boundary, `shaar_submit` operation dispatch, opaque `shaar_profile` / `shaar_private_session` scopes, typed `shaar_error`, and single event stream. It does not add a second ABI or copy Ardia implementation. Source references were inspected read-only in the pinned Ardia and Chromium 155 trees.

## Current Shaar behavior

Swift imports `ChromiumBridge`; its `ARCChromiumRuntime` adapter owns the site controls calls. The current backend behaviors and call sites are:

| Behavior | Swift app route (file:line) | Current engine call / semantics |
| --- | --- | --- |
| Current-page permission display and toggle | `Sources/ArcusisBrowser/BrowserEngineSiteControls.swift:42-64`; names/values in `Sources/BrowserCore/SiteControls.swift:7-37` | `ac_site_settings_get` / `ac_site_settings_set` through `site_settings.get` / `.set`; origin is HTTP(S), types are `microphone`, `camera`, `location`, `notifications`, `popups`, `sound`, and `midi`; values `allow`, `block`, `ask`. `protocolHandlers` is listed and reset with those settings and is not assigned through set. Swift also displays per-site auto-PiP from its own profile-scoped store because Chromium has no corresponding setting in this engine. |
| Clear current site's data | `BrowserEngineSiteControls.swift:77-79` | `ac_site_data_clear`, called with origin; cookies plus supported web storage; adapter requires positive completion fields. |
| Clear current site's cookies and reload | `BrowserEngineSiteControls.swift:74-76` | Adapter uses the selected tab's DevTools `Network.getCookies` then cookie deletion calls; it must revalidate selected tab/profile after async completion. This is distinct from full site-data clear. |
| Clear profile cache and reload | `BrowserEngineSiteControls.swift:71-73` | `ac_browsing_data_clear` with `cache`, then bypass-cache reload. |
| Settings: clear profile cache or all site data | `Sources/ArcusisBrowser/ProfilePrivacyModel.swift:11-20,27-32,132-140` | `ac_browsing_data_clear` with `cache` or `siteData`, explicitly bound to selected regular profile. |
| Enumerate and reset permission exceptions | `ProfilePrivacyModel.swift:15-17,34-42,141-154` | `ac_site_settings_origins`, `.get`, `.reset`; list only non-default saved exceptions and reset all registered site setting types for an origin. |
| Third-party cookie policy | `ProfilePrivacyModel.swift:18-19,44-49` | direct profile preference read/write (`profile.block_third_party_cookies`); unavailable is represented as `nil`, not false. |
| Private cookie allow exception | `Sources/ArcusisBrowser/SiteControlsPrivate.swift:9-20,22-47`; adapter in `Sources/ChromiumBridge/ChromiumPrivatePrivacy.mm:60-112` | `ac_site_settings_get` / `.set` against OTR profile. Current call also carries tab/window/context IDs and revalidates current selected origin. Grant is shared across private windows of that session/profile; a deny revokes it across those windows. Closing the last private window erases the OTR exception/data. |

The engine service bridge resolves the site calls at `Sources/ChromiumBridge/ChromiumEngineServices.mm:49,63`; ObjC call mapping and origin validation are in `Sources/ChromiumBridge/ChromiumSiteControls.mm:9-19,24-56,114-159`. Website permission prompts for geolocation, notifications, MIDI, and protocol-handler registration use the same Shaar consent sheet as camera and microphone. Patch `0070-shaar-website-permission-prompt.patch` asks that sheet from `CreatePermissionPrompt` when `--shaar-embedder` is set, and the decision reuses the website media permission operation. The sheet is app-owned. The event names the frame token, and the grant is accepted only while that frame is still current. A same-URL reload or a detached frame dismisses the request before Allow can apply. A private-profile grant is for this visit only. A private protocol handler is accepted onto the off-the-record registry, which does not write the parent profile. A regular profile still stores a durable grant in Chromium.

## Pinned Ardia behavior and Chromium patch dependencies

The read-only implementation is `engine/chromium/src/chrome/browser/ardia/ac_site_settings.cc` (settings map, supported setting registry, origin exception listing/change observer, cookie/site-data deletion) and `ac_browsing_data.cc` (named type masks and remover completion). Its service routes these calls through `Profile` and can explicitly select `Profile::GetPrimaryOTRProfile()` for `offTheRecord` operations. `engine/chromium/src/chrome/browser/ardia/ac_engine.cc` owns the service/profile dispatch; `engine/chromium/src/chrome/browser/ardia/ac_permissions.cc` is not present in the pinned browser layer (the permission helper is `engine/ardiacore/src/ardia/core/ac_permissions.mm`). The latter integrates Chromium permission UI/system permission callbacks; it is separate from storing per-origin content settings.

The implementation hooks these Chromium classes/APIs:

- `HostContentSettingsMap` via `HostContentSettingsMapFactory::GetForProfile` for `GetContentSetting`, `SetContentSettingDefaultScope`, `GetSettingsForOneType`, observer notifications, and removal by setting `CONTENT_SETTING_DEFAULT`.
- `content::BrowsingDataRemover` and `chrome_browsing_data_remover` masks for profile cache and site-data clearing, with `RemoveAndReply` / `RemoveWithFilterAndReply` completion.
- `network::mojom::CookieManager` from the profile's default `StoragePartition` for cookie deletion; partitioned cookies are separately included. Site data removal then covers both protected and unprotected web origins for its site filter.
- `Profile` OTR storage partition/content settings for the private exception. That setting is transient to the OTR profile, not a regular-profile exception.

For selected-origin site-data deletion, the current code derives a registrable domain and removes first-party cookies for that domain and partitioned cookies under it, then removes site data with an origin filter. This is broader than a strict serialized-origin cookie filter for sibling subdomains; parity tests should capture existing behavior and the API schema must make scope explicit. Do not report success if Chromium returns failed data types or the profile disappears during async removal.

No patch in the pinned 39-entry Chromium patch series directly implements site-settings, permission-exception, browsing-data-clear, or third-party-cookie behavior. These are Ardia service code over Chromium APIs. Third-party cookie blocking today is a profile boolean preference, not a site-settings service call. Chromium's cookie-controls/content-settings implementation is upstream; Shaar must verify which registered pref and mode implement the app's boolean on this pin. Do not assume a similarly named preference is registered or writable. The unrelated Safe Storage identity patch must remain unchanged as a separate data-compatibility requirement.

## Chromium APIs for the Shaar layer

Use the pinned Chromium APIs directly from `chrome/browser/shaar/services/`, profile-selected before any work:

| Need | Chromium 155 paths / API |
| --- | --- |
| Read, write, enumerate, reset origin exceptions; observe changes | `components/content_settings/core/browser/host_content_settings_map.h` (`HostContentSettingsMap`); `chrome/browser/content_settings/host_content_settings_map_factory.h`; `components/content_settings/core/common/content_settings.h` / `content_settings_type.h`; registry `components/content_settings/core/browser/content_settings_registry.h`. Enumerate provider-backed exceptions and canonicalize only HTTP(S) origins. Use `ContentSettingsRegistry` to reject unsupported types/values and preserve defaults distinctly from explicit ask/allow/block. |
| Permission request UI event integration | `components/permissions/permission_request_manager.h`, `components/permissions/permission_request.h`, plus the browser client permission delegate as needed. Preserve Chromium's prompt decision/gesture/security checks; do not synthesize grants in the ABI or equate prompt resolution with stored setting state. |
| Clear cache, site data, cookies/storage for profile or filtered site | `content/public/browser/browsing_data_remover.h`; `chrome/browser/browsing_data/chrome_browsing_data_remover_constants.h`; `content/public/browser/browsing_data_filter_builder.h`; `content/public/browser/storage_partition.h`; `services/network/public/mojom/cookie_manager.mojom.h`. Use the profile's remover for supported type masks and filter APIs, and await completion/failure mask. Use the selected profile's `StoragePartition` only where direct cookie operations are required. |
| Cookie policy state | Profile `PrefService` (`chrome/browser/profiles/profile.h`, `components/prefs/pref_service.h`) and registered cookie controls pref definitions in `components/content_settings/core/common/pref_names.h`; cookie enforcement in `components/content_settings/core/browser/cookie_settings.h` and `components/content_settings/core/common/cookie_settings_base.h`. Confirm the effective mode and managed/policy state on Chromium 155 before mapping the existing boolean; return `SHAAR_POLICY_BLOCKED` for managed changes. |
| Storage and session ownership | `Profile` / OTR `Profile` and its `StoragePartition`; do not accept filesystem paths from operation JSON. Select the profile or `shaar_private_session` handle from `shaar_scope` before accessing any above API. |

The upstream Chromium checkout used for these paths is `engine-333-364/build/EngineSource/chromium_git/chromium/src`; it remains read-only. Chromium APIs are implementation targets to verify against the pinned GN graph during the module implementation, not an assertion that the future Shaar GN target already has those dependencies.

## ABI and Swift adapter proposal

Retain the shared design ABI exactly: `shaar_submit(engine, scope, window, tab, operation, args_json, request_id, reply, context, immediate_error)`, version/size negotiation, UI-thread serialization, async reply, copied Swift payloads, one sequenced event stream, typed `shaar_error_code`, and the rule that supplied window/tab handles must belong to the explicit scope. Keep existing `SHAAR_OP_SITE_SETTINGS_GET/SET/RESET`, `SHAAR_OP_SITE_DATA_CLEAR`, and `SHAAR_OP_BROWSING_DATA_CLEAR` IDs; add schema details here for consolidation into the shared header. New operation enum members are appended, never inserted/reordered.

| Operation | Scope and JSON request | Async result / typed failures |
| --- | --- | --- |
| `SHAAR_OP_SITE_SETTINGS_GET` | Profile or private-session scope; `{ "origin": "https://host[:port]" }`. Private scope resolves only to that OTR profile. | `{ "settings": { "camera": {"value":"ask", "isDefault":true} } }`; malformed/non-origin input `SHAAR_INVALID_ARGUMENT`, unknown session `SHAAR_WRONG_SESSION`, profile mismatch `SHAAR_WRONG_PROFILE`. |
| `SHAAR_OP_SITE_SETTINGS_SET` | Profile or private-session; `{ "origin", "type", "value" }`. Type and values are registry-validated. Set `default` to remove the exception; accept `ask` only when the Chromium type supports it. | Success returns normalized value/default state. Managed/locked setting `SHAAR_POLICY_BLOCKED`; unsupported type/value `SHAAR_INVALID_ARGUMENT`; storage failure `SHAAR_CHROMIUM_ERROR`. |
| `SHAAR_OP_SITE_SETTINGS_RESET` | Profile or private-session; `{ "origin" }`. Reset only registered, user-controllable exceptions for that origin. | `{ "resetCount": n }`; distinguish no exceptions from failure, and reject policy-owned rules instead of claiming reset. |
| `SHAAR_OP_SITE_SETTINGS_ORIGINS` (append) | Profile or private-session; `{}`. Return exact canonical origins with user exceptions only; private list is never merged with regular list. | `{ "origins": [...] }`, sorted/deduplicated. |
| `SHAAR_OP_SITE_DATA_CLEAR` | Profile or private-session; `{ "origin": "https://host[:port]", "includeCookies": true, "includeStorage": true }`; omitted booleans mean true for current full-site-data parity. | `{ "cookiesDeleted": n, "storageCleared": true }`. `SHAAR_CHROMIUM_ERROR` if any requested class fails; never success-shaped partial completion. Session close during work yields `SHAAR_WRONG_SESSION`/cancelled result. |
| `SHAAR_OP_BROWSING_DATA_CLEAR` | Regular profile only; `{ "types": ["siteData"|"cache"], "sinceUnixMs": optional }`. For current surface use one type per call; validate nonempty known types. Reject private scope with `SHAAR_PRIVATE_DISALLOWED` to avoid implying durable private clearing. | `{ "clearedTypes": [...], "complete": true }`; failed remover mask is `SHAAR_CHROMIUM_ERROR`. |
| `SHAAR_OP_SITE_COOKIES_CLEAR` (append) | Profile or private-session plus selected tab; `{ "origin": "https://host[:port]" }`. Require supplied tab to still be selected and its canonical origin to match before mutation and completion. | `{ "cookiesDeleted": n }`; stale/mismatched handles return `SHAAR_WRONG_SESSION`/`SHAAR_WRONG_PROFILE`, invalid origin `SHAAR_INVALID_ARGUMENT`. |
| `SHAAR_OP_THIRD_PARTY_COOKIES_GET/SET` (append) | Regular profile only; GET `{}`, SET `{ "blocked": true }`. No inferred current profile. | GET `{ "blocked": bool, "managed": bool }`; SET returns effective state. OTR `SHAAR_PRIVATE_DISALLOWED`; managed/policy-controlled pref `SHAAR_POLICY_BLOCKED`; absent/unregistered pref `SHAAR_UNSUPPORTED_CAPABILITY` (never silently return false). |

`SHAAR_EVENT_SITE_DATA` payloads use `schemaVersion`, a narrow `kind` (`settingsChanged`, `thirdPartyCookiePolicyChanged`, `clearCompleted`), and operation/result metadata. The shared event envelope always carries profile UUID and, for OTR, a distinct private `session_id`; never expose profile paths or cookie contents. `HostContentSettingsMap` changes must emit after Chromium mutation. Include request ID for clear completion; coalesce or bound high-volume change notifications. No private event may be emitted as a regular-only event. Prompt events remain in the shared `SHAAR_EVENT_PERMISSION` family and resolve through that module's typed reply path.

Swift adapter changes: replace `ARCChromiumRuntime` dynamic `ac_*` lookup/calls with typed wrappers in `Sources/ChromiumBridge` that supply `shaar_scope`; keep `BrowserEngineSiteControls` and the site-control models/UI stable behind their existing protocols. Map errors to `LocalizedError` by typed code, preserve timeout/cancellation and stale-target checks, decode the versioned settings result strictly, and use event invalidations to refresh affected profile/settings models. Change `PrivateSiteControlsModel` to pass an explicit private-session handle rather than tab/window/context IDs packed into service JSON. Keep auto-PiP in its current Swift store until a separate Chromium capability is specified. `ProfilePrivacyModel` remains regular-profile-only for the third-party cookie control and browsing-data clear.

## Tests and parity gates

- **Unit:** C++ service tests for canonical origin validation, content-setting registry mapping and defaults, exception enumeration/provider filtering, managed policy errors, request scope/ownership checks, type-mask/schema validation, result decoding, event payload versioning and OTR ID attribution. Cookie-policy tests cover unmanaged true/false, managed, missing pref, restart persistence and private disallow. Clear tests assert callback fires once and failure masks never report complete.
- **Engine simulation:** extend `Tests/BrowserAppTests/SiteControlsTests.swift` and `ProfilePrivacyTests.swift` with typed adapter fakes and out-of-order/stale results; extend `Sources/ShaarVerification/SiteControlsProbe.swift` and `ProfilePrivacyProbe.swift` as the engine-backed parity probes. Cover get/set/reset/reload persistence, all shown permissions and default `ask`, exact origin list and two-profile isolation, private cookie grant sharing/revocation/last-window cleanup, stale selected tab rejection, and cookie-only versus full site-data deletion. Seed sibling subdomain and partitioned cookies so the current domain breadth is an explicit tested/decided contract.
- **Smoke:** headless native probe opens two regular profiles plus one private session, changes a permission and third-party-cookie policy, verifies regular/private/profile isolation, clears cache and site data independently, checks callback/event sequence and exact IDs, closes/reopens regular profile to prove persistent state, closes last private window to prove OTR cleanup. Run through Shaar engine simulation/CI against Chromium 155; no local engine build is required for this design task.
- Existing evidence already present: `SiteControlsProbe.swift:104-127,148-150` checks permission read/write/default and actions; `ProfilePrivacyProbe.swift:54-92` checks profile isolation and cache/site-data clearing. These do not yet prove private-session ABI events, managed cookie policy, origin-filter edge cases, or the new typed error surface.

## Effort and risks

Estimate: **2–3 engineer-weeks**, matching migration row 9 in [[Engine_Shaar_Layer_Design]], excluding Chromium sync/build wall time. Approximate work: service API and profile/private scoping 4–6 days; Swift adapter/model migration 2–3 days; Chromium unit, engine simulation and focused smoke coverage 4–6 days; edge-case/CI integration 1–2 days.

Main risks are (1) Chromium's cookie-controls pref/mode and enterprise management semantics may not map one-to-one to the old boolean; (2) OTR `HostContentSettingsMap` and cookie access must remain session scoped, while private events need distinct IDs; (3) browsing-data removal is asynchronous and can partially fail; (4) Chromium's origin filters, registrable-domain cookies, partitioned cookies and storage-key behavior can diverge from the existing Ardia behavior; (5) broad setting enumeration must not expose policy/default entries as user exceptions. Gate adapter cutover on the private/profile isolation and data-removal probes, and keep auto-PiP outside this module's Chromium ABI until specified.
