# Engine module: storage and keychain

Issue: [#418](https://github.com/arcusis/shaar/issues/418). Scope: macOS Safe Storage identity and cookie encryption; cookie/site controls; component and extension updater policy; eMudhra distrust; video super resolution; extension window visibility; and CEF carryover relevant to storage/window lifetime. Source inventory was read from the pinned Ardia checkout and Chromium 155 tree in `engine-333-364/build/EngineSource`; those trees remain read-only. This is fresh design analysis, not a port of Ardia source.

## Relationship to the layer design

Follow [[Engine_Shaar_Layer_Design]]: the only exported C surface is `chrome/browser/shaar/public/shaar_engine.h`; Chromium objects stay inside the engine; Swift uses `ChromiumBridge` as the adapter; all operations carry an explicit profile/private-session scope; events use the single ordered stream and UUID IDs, never filesystem paths; errors use the design's typed `shaar_error_code`; callbacks and borrowed data follow the design's lifetime rules. Append new enum values without renumbering existing ones. The existing `SHAAR_OP_SITE_SETTINGS_GET/SET`, `SHAAR_OP_SITE_DATA_CLEAR`, and `SHAAR_OP_BROWSING_DATA_CLEAR` are the base for this module.

Plan detail for the design table: this work adds gates under row 7 (site settings/data) for cookie encryption continuity and direct cookie APIs, row 8 (extensions) for updater and hidden-window behavior, and row 12 (final packaging) for certificate distrust and updater-policy review. These details refine those rows; they do not add a second ABI or another module sequence. The component updater and certificate policy are engine configuration, not profile service calls.

## What Shaar uses today

The app does not call a keychain API or encrypt cookie bytes itself. Chromium owns cookie persistence and OSCrypt/keychain access. `Sources/ChromiumBridge/ChromiumBridge.mm:216-220` uses `--use-mock-keychain` only for disposable test fixtures and disables background/component updates in that fixture; normal profiles use the OS keychain. Existing profile paths are bound to UUIDs by `ChromiumEngineServices.mm:82-95`, but the legacy service ABI passes the filesystem path to `ac_*` calls at `:98-110`.

| Existing app behavior | Swift/bridge route |
| --- | --- |
| Read/write third-party cookie preference for a regular profile | `ProfilePrivacyModel.swift:44-48` → `ChromiumSiteControls.mm:59-73` (`profile.block_third_party_cookies`); unavailable values remain `nil`. |
| Clear all site data for a selected origin, or clear cookies used by the selected page and reload | `BrowserEngineSiteControls.swift:74-79` → `ChromiumSiteControls.mm:145-152,161-199`. Page cookie deletion currently calls DevTools `Network.getCookies` then `Network.deleteCookies` for each name/domain/path/partition. |
| Read and change a private-session origin's cookie exception | `SiteControlsPrivate.swift:33-50` → `ChromiumPrivatePrivacy.mm:60-113`; private scope is currently reconstructed from tab/window/context IDs and sent to the regular-profile `site_settings.get/set` service with `offTheRecord:true`. |
| Inspect/edit page cookies in the Inspector | `InspectorPageToolsModel.swift:324-344,391-420` uses the existing developer protocol-call route (`Network.getCookies`, `Network.deleteCookies`). Keep that explicitly developer-authorized UI separate from normal site controls. |
| Read/update extension state, action popups and management | `ExtensionManagement.swift:130-139`, `ChromiumExtensions.mm:26-80,110-165`; the bridge uses Chromium extension manager APIs plus a fixed set of `chrome.management` scripts. |
| Receive engine service events | `ChromiumEngineServices.mm:45-67,73-79,118-126`; no keychain, updater, certificate or video-super-resolution `ac_*` export is resolved. The adapter drops legacy private events because they carry the parent profile path and `offTheRecord` marker (`:118-126`). |

There is no Swift switch for component updater, eMudhra distrust, video super resolution, CEF carryover, or extension-window hiding. They are implicit engine behavior. Extension update behavior does reach user-visible installed extensions; updater policy must remain enabled for those updates even when unrelated component downloads are restricted.

## Current Ardia implementation and dependencies

Ardia's patch series modifies Chromium directly; the implementation hooks are in the patch targets, not an `ac_*` service. The separate Ardia service layer implements cookie/site operations in `engine/chromium/src/chrome/browser/ardia/ac_site_settings.cc` and `ac_cookies.cc`; `ArdiaCoreTab` exposes DevTools calls used by Shaar's ObjC bridge. Private cookie exceptions are applied against a parent profile plus OTR selection in `ChromiumPrivatePrivacy.mm`, while private windows share Chromium's primary OTR profile. The new layer should bind the actual `shaar_private_session` handle throughout.

| Behavior | Ardia hook / Chromium code it changes | Contract to retain or consciously revise |

## Chromium 155 APIs for the Shaar layer

Paths below are relative to the synced Chromium `src/` directory. Use the checked-out revision in the issue's source pin and verify signatures while implementing.

* **Keychain and encryption:** `components/os_crypt/common/keychain_password_mac.{h,mm}` owns the macOS item lookup and current service/account names. `components/os_crypt/async/browser/keychain_key_provider.mm` supplies key material; `components/os_crypt/async/browser/os_crypt_async.{h,cc}` and `components/os_crypt/async/common/encryptor.h` provide Chromium's profile-managed asynchronous encryptor and `EncryptString`/`DecryptString`. Keep cookie storage on Chromium's existing OSCrypt path; do not invent a parallel cipher or store secrets in the ABI.
* **Cookie storage and deletion:** `content/public/browser/storage_partition.h` exposes each `Profile`'s partition and `GetCookieManagerForBrowserProcess()`. Use that profile-owned `StoragePartition`'s `network::mojom::CookieManager` (`services/network/public/mojom/cookie_manager.mojom`) for `GetCookieList`, `GetAllCookies` where appropriate, and `DeleteCookies` with `network::mojom::CookieDeletionFilter` (defined in that mojom). `net/cookies/canonical_cookie.h` and `net/cookies/cookie_partition_key.h` retain canonical identity/partition details. `content/public/browser/browsing_data_remover.h` and `chrome/browser/browsing_data/chrome_browsing_data_remover_delegate.h` remain the broad site-data/cache deletion path. Prefer those typed APIs to DevTools for product cookie controls; CDP stays an explicit developer-tool interface.
* **Cookie policy:** `components/content_settings/core/browser/host_content_settings_map.h`, `components/content_settings/core/browser/cookie_settings.h`, and `chrome/browser/profiles/profile.h` are the origin exception and owning-profile surfaces. Use `PrefService` through the owning profile for the existing third-party preference only if the selected Chromium build exposes the intended pref and policy semantics; unsupported must remain typed `SHAAR_UNSUPPORTED`/policy error, not a fabricated value.
* **Component updates:** `chrome/browser/component_updater/chrome_component_updater_configurator.{h,cc}`, `components/component_updater/component_updater_service.h`, `components/update_client/update_checker.{h,cc}`, `components/update_client/protocol_serializer.{h,cc}`, `components/update_client/crx_downloader.{h,cc}`, and `chrome/browser/extensions/updater/chrome_update_client_config.{h,cc}` are the policy and channel seams. Keep endpoint validation, request-field reduction, cookie suppression and component registration in engine-owned C++ configuration; no runtime Swift method is needed.
* **Certificate distrust:** `net/cert/cert_verify_proc_blocklist.inc`, `net/cert/cert_verify_proc.{h,cc}`, and `net/data/ssl/blocklist/` are the blocklist implementation/data seams in this pin. Keep evidence and tests tied to SPKI hashes, not display names.
* **Extension visibility/hosting:** `chrome/browser/extensions/browser_extension_window_controller.{h,cc}`, `chrome/browser/extensions/api/tabs/tabs_event_router.{h,cc}`, `chrome/browser/extensions/api/web_navigation/web_navigation_api_helpers.{h,cc}`, and `chrome/browser/extensions/extension_view_host_factory.{h,cc}` cover visibility/event filtering and popup hosts. Use a Shaar-owned internal-window marker accessible to these seams.
* **Video super resolution:** `components/viz/service/display/{display.h,display.cc}`, `components/viz/service/display/direct_renderer.h`, `components/viz/service/frame_sinks/root_compositor_frame_sink_impl.{h,cc}`, and `gpu/ipc/service/image_transport_surface_overlay_mac.mm` carry the current per-frame macOS gate. If Chromium upstream exposes a stable equivalent at the chosen roll, prefer it over preserving a private frame-field patch.

## Proposed ABI and Swift adapter changes

Keep calls on the existing `shaar_submit(engine, scope, window, tab, operation, args_json, request_id, reply, context, error)` dispatch path from [[Engine_Shaar_Layer_Design]]. The caller must supply exactly one `shaar_scope`; engine validates every tab/window belongs to it. Extend the existing operation enum with:

* `SHAAR_OP_COOKIE_DELETE_FOR_TAB`: delete cookies sent to the selected tab's current origin, including partitioned cookies, using typed cookie-manager filters; async result reports deleted count and completeness. Empty cookie set succeeds. Tab navigation/close races return typed `SHAAR_NOT_FOUND`/`SHAAR_CONFLICT`, not success-shaped empty JSON.
* Keep `SHAAR_OP_SITE_SETTINGS_GET/SET` for third-party preference and per-origin cookie exceptions; `SHAAR_OP_SITE_DATA_CLEAR` for site-wide cookie+storage clear; `SHAAR_OP_BROWSING_DATA_CLEAR` for selected profile data classes. Validate origin and operation-specific fields in C++, and return the design's typed `SHAAR_PRIVATE_DISALLOWED`, `SHAAR_POLICY_BLOCKED`, `SHAAR_PERMISSION_DENIED`, or `SHAAR_CHROMIUM_ERROR` as applicable. If the selected Chromium build lacks a policy surface, return a typed error; do not invent a preference value.
* Do not add keychain read/write, arbitrary cookie plaintext, updater control, trust-store mutation, internal-window visibility, or compositor toggles to the public ABI. They are implementation/security policy. Existing Web Store and extension actions remain in the extension module's `SHAAR_OP_EXTENSION_*` family.

Use existing `SHAAR_EVENT_SITE_DATA` with payload schema for completed cookie/site mutations; attach `profile_id`, private `session_id` when scoped to OTR, and target `tab_id` when tab-bound. Emit only after mutation; no cookie values, keychain data, update request bodies, certificate material, or profile paths. No separate event is needed for keychain or internal updater configuration. The current design's `SHAAR_EVENT_EXTENSION` can report genuine profile-scoped extension install/update state, but must not expose internal host windows as extension tabs. Swift copies event data and maps typed errors to existing localized site-control/privacy errors. Do not silently swallow a failed service operation or infer regular scope from the parent profile.

Swift migration: replace the `ARCChromiumRuntime` service implementations behind the same product-facing methods in `ChromiumBridge`/`BrowserEngineSiteControls.swift`, `ProfilePrivacyModel.swift`, `SiteControlsPrivate.swift`, and `InspectorPageToolsModel.swift`. Normal clear-cookie UI should call `SHAAR_OP_COOKIE_DELETE_FOR_TAB`; Inspector cookie edits remain on the developer protocol allowlist and should not bypass its existing authorization. Once native private-session handles exist, pass the `shaar_private_session` scope rather than synthesizing `offTheRecord:true` against the parent profile. No UI change is required for keychain, updater, distrust or super resolution.

## Parity tests and smoke checks

**Unit tests (native Chromium target):**

1. Keychain name test asserts exact current Shaar service/account names; keychain-provider test reads an existing item without creating a second identity. OSCrypt encrypt/decrypt round-trip with both test keychain and retained profile fixture; corrupted/locked/missing-key paths report failure and do not overwrite existing ciphertext.
2. Cookie service tests cover exact origin, domain/path, partition key, expiry/session cookies, empty jar, deletion callback failure, profile A/B isolation, and both regular and OTR stores. Setting and reading third-party policy checks unsupported/policy-managed cases.
3. Component updater configurator tests assert only reviewed security component IDs and approved HTTPS check/download hosts/paths, filtered protocol fields, no ping, no cookies, no background downloader/cache, and separately assert Web Store extension updates still run via their approved endpoint. Unknown redirect/destination, HTTP, wrong port/path and extra credentials are rejected.
4. Certificate tests reject each affected eMudhra SPKI/cross-sign and the pinned root while allowing unrelated control chains; test data and expected hashes are versioned with the Chromium pin.
5. Extension-window tests verify internal Shaar popup/side-panel windows and their tabs/navigation do not appear in `tabs`/`windows` extension APIs or dispatch WebNavigation events; ordinary user windows still do. Video tests verify false-by-default and supported-policy frame propagation on macOS. CEF carryover lifecycle tests assert profile teardown follows host/contents detachment.

**Engine simulation (headless, two profiles plus OTR):** write cookie and site storage in profile A; read and delete only A's selected-origin cookies; prove B unchanged; verify a partitioned cookie is removed; apply/revoke a private origin exception and prove its cookie jar/session events remain private and disappear after session close. Restart A and confirm encrypted cookie continuity with the same keychain item. Inject updater policy and assert security components and extension updates take their distinct routes while telemetry/pings and disallowed payloads are absent. Create an internal extension popup and prove only the authorized host event reaches Swift. Feed a certificate control fixture through verification; exercise compositor policy false/true under a macOS-capable simulation.

**Smoke checks:** on a signed headless macOS CI runner, launch a disposable fixture with mock keychain and component updates disabled; launch a separate real-keychain profile only in the dedicated integration lane. Persist, restart and read an encrypted login cookie without a second Safe Storage item; clear one site's cookies and ensure another profile/site remains signed in. Open/close a private session and verify no cookie persistence or regular-profile event. With network stubs, check allowed component and extension update requests and blocked destinations; check certificate positives/negative controls and ensure extension internal windows stay hidden. Run supported/unsupported GPU checks where macOS hardware/CI permits and mark unavailable hardware as untested rather than passed. These probes establish behavior; compilation alone does not.

## Effort and risks

Estimate: 2–3 engineer-weeks for native cookie/settings services and Swift adapter, 1–2 weeks for keychain continuity/migration fixture, 2–4 weeks for updater policy, extension visibility and security regression tests, and 1–2 weeks for eMudhra/video/CEF behavior review and platform validation. Total focused effort: about 5–9 engineer-weeks, excluding Chromium source-build wall time and any key migration utility or certificate incident re-review.

Highest risks are silent cookie/password data loss from keychain item renaming; OTR data or events crossing into a regular profile; weakening updater destination/payload restrictions or starving security component refresh; breaking extension updates while constraining component updates; stale certificate distrust hashes or unrelated breakage; extension API event leaks from internal windows; and a compositor patch that regresses rendering or GPU compatibility. Gate rollout on profile-restart decryption, private-session isolation, updater negative tests, extension-update positive tests, and certificate negative controls. Do not make key migration or release-readiness claims from mock-keychain or unit evidence alone.
