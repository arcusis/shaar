# Shaar engine module: windows and tabs

Issue #418 module specification. Read with [[Engine_Ardia_Inventory]] and [[Engine_Shaar_Layer_Design]]. The phase two design remains the single source for ABI layout, ownership, threading, version negotiation, borrowed strings/views, and typed error rules. This note adds the windows/tabs contract and uses its existing `shaar_scope`, opaque handles, `shaar_submit`, and ordered event stream; it does not define a second ABI or add a parallel event sink.

## A. What Shaar uses today

### C ABI calls and native types

There are currently **no `ac_*` C exports for windows, tabs, selection, or host views**. The `ac_engine.h` ABI is used by `ChromiumBridge` for profile-scoped downloads, library and site-setting services (`Notebook/Engine_Ardia_Inventory.md`, “Explicit ABI and Swift routes”). Its `ac_engine_set_event_sink` delivers that service layer's events; it is not the window/tab lifecycle feed. The window/tab side is Objective-C++ and dynamically resolves `ArdiaCoreWindow` and retains `ArdiaCoreEngine`, `ArdiaCoreProfile`, `ArdiaCoreWindow`, and `ArdiaCoreTab` behind `ARCChromiumRuntime` (`Sources/ChromiumBridge/ChromiumRuntimeInternal.h:24-65`; `ChromiumBridge.mm:114-126`). Chromium C++ objects do not cross to Swift.

The adapter surface in `Sources/ChromiumBridge/include/ChromiumBridge.h` includes `createWindowID`, `closeWindowID`, `hostViewForWindowID`, `openTabID`, `activateTabID`, `closeTabID`, `placeTabIDs`, and window/tab lookup (`:128-153`). Private methods take an explicit `contextID`, `windowID`, and `tabID` for create/open/select/close and host view access (`:301-320`). Regular tab methods bind a `profileID` and `windowID`; a tab cannot silently change owners. Private windows use separate registries and OTR objects even though the old service ABI does not represent the private session as a first-class scope.

### Swift calls, events, and app-owned state

- `NativeBrowserHost.swift:661-684` creates or claims a native window, obtains its `NSWindow` and host `NSView`, and attaches the existing SwiftUI browser. `:164-171` routes engine window creation/show requests and prepares incoming tabs for adoption. The app decides when to show/key a window (`:183-184`, `:206-219`).
- `BrowserEngine.swift:628-643,657-672` opens materialized saved tabs/favorites with profile and window IDs; `:683-700` computes order/pinned IDs, calls `placeTabIDs`, activates the selected profile/tab, or clears active selection. `:380-386` requests tab close. `:419-449` consumes close/activation callbacks and defers reconciliation to the next main-queue turn because the native activation callback arrives during Chromium tab-strip notification.
- `BrowserRuntimeEvents.swift:12-25,30-51` forwards window-close, tab-change, tab-close, tab-activation, and new-tab events through `BrowserRuntimeRouter.swift:34-39,102,138`. Callback model types include string IDs, profile IDs, navigation/loading fields, opener ID, and foreground disposition; the router binds tab IDs to a native window before forwarding.
- `PrivateBrowserHost.swift:182-188,232-245,262-275,294-309` owns private window creation and private tab open/select/close flows. `PrivateBrowserStore` keeps private tab list and selection in memory (`PrivateBrowserStore.swift:23-58,111-124`); closing the final private tab closes its private window.
- `ChromiumBridge.mm:305-328,330-382` tracks regular native windows and close observers; `:507-545` opens tabs against an exact loaded profile/window; `:762-860` activates a tab and reconciles externally selected tabs; `:873-880,936-967` closes tabs and places ordered/pinned tabs. `:647-690` explicitly rejects an attempted live cross-window tab transfer and restores the original tab; same-window ordering is supported. `:706-734` adopts a newly-created popup/window tab into a newly-created app window. Closing a host-initiated tab is finalized after tab-strip removal because the pinned callback may suppress the direct will-close delegate (`:1107-1139`).

The public current event callbacks are `onWindowClosed(windowID, quitting)`, `onTabChanged(tabID, url, title, loading, canGoBack, canGoForward)`, `onTabClosed(tabID)`, `onTabActivated(tabID, profileID)`, `onNewTab(tabID, profileID, url, openerID?, foreground)`, `onWindowShowRequest(windowID, active)`, and `onWindowRequest(profileID, type)`. Private close and navigation-failure callbacks additionally carry context/window/tab IDs. Window/tab callbacks are delegate/callback events from `ArdiaCoreWindowDelegate` and `ArdiaCoreTabDelegate`, not `ac_engine_event_t` events.

## B. How pinned Ardia implements it

Reference tree (read-only): `engine-333-364/build/EngineSource/chromium_git/chromium/src/`.

- `ardia/core/ac_browser.mm` supplies `WindowHost`: it keeps a `Browser*` per `Profile*` in each host `NSWindow`, creates Browser instances through Chromium `CreateBrowserWindow(BrowserWindowCreateParams(...))`, selects the Browser for the active profile, attaches the BrowserWindow adapter, and observes each `TabStripModel`. It also adapts `WebContents` delegate/observer callbacks to Ardia tab/window delegate callbacks.
- `ardia/core/ac_browser_window.mm` implements `ACBrowserWindow`, a `BrowserWindow` subclass, and `WindowHost`. It creates a Chromium Views `Widget`/native `NSWindow`, adds an embedder `NSView` as host content, maps browser show/close/activate behavior to the app delegate, and hosts the browser's active `WebContents` view. A tabless browser window is retained for the app shell.
- `chrome/browser/ardia/ac_tabs.cc` observes `GlobalBrowserCollection` and `TabStripModelObserver`, maps tab-strip insert/remove/move/selection changes to service events, and captures tab IDs, active index/order, group state, and close-selection state. The ABI exposed there is watch/group oriented; it is not the app's window/tab control API.
- `ardia/core/ac_host_visibility.mm` keeps host-visible state as `WebContentsUserData` and updates permission prompt visibility, tab-dialog bounds, PiP inputs, and video-upscaling inputs when the app changes which tab is actually shown. This matters because one native host window can retain multiple profile Browsers while only one profile's selected tab is visible.
- `chrome/browser/ardia/ac_engine.cc` owns UI-thread engine startup/shutdown and service event sink delivery. It is separate from the Objective-C delegate callbacks used for window/tab ownership.

The pinned patch series has two relevant dependencies. `source/ardia/engine/patches/chromium-window-hosted.patch` changes `components/remote_cocoa/app_shim/bridged_content_view.{h,mm}` so the embedder's hosted view gets hit testing and accessibility precedence, and changes browser/unload behavior so a hosted shell can stay open with an empty tab strip. `chromium-hidden-window-current-window.patch` makes Ardia's hidden extension windows invisible to extension “current window” selection. These are source-build patches in the pinned series (alongside `chromium-hidden-window-current-window.patch`); they are not public Chromium APIs. The replacement must implement reviewed Shaar-owned host behavior without copying patch/source text. Inventory also records `chromium-cef-carryover.patch` as covering empty-strip/private teardown and native hosting behavior; test the specific lifecycle behavior before dropping or replacing it.

## C. Chromium 155 APIs for the Shaar layer

Use the pinned Chromium implementation APIs below from `chrome/browser/shaar/{windows,tabs,mac}`. Paths are relative to the synced Chromium root. Keep these C++ types inside the engine.

- Browser/window ownership and creation: `chrome/browser/ui/browser.h` (`Browser`, `GetTabStripModel`, `Browser::Create`), `chrome/browser/ui/browser_window/public/create_browser_window.h` (`BrowserWindowCreateParams`, `CreateBrowserWindow`), `chrome/browser/ui/browser_window/public/browser_window_interface.h` (`BrowserWindowInterface`), `chrome/browser/ui/browser_window/public/global_browser_collection.h` (`GlobalBrowserCollection`), and `chrome/browser/ui/browser_window/public/browser_window_interface_iterator.h` for ordered iteration/last-active lookup. Key by the supplied Shaar profile/window IDs; never find a profile by scanning the “last active” browser.
- Tab strip operations and observation: `chrome/browser/ui/tabs/tab_strip_model.h` (`InsertWebContentsAt`/`AddWebContents`, `CloseWebContentsAt`, `ActivateTabAt`, `MoveWebContentsAt`, `GetActiveWebContents`, detach/adopt operations) and `chrome/browser/ui/tabs/tab_strip_model_observer.h` (`OnTabStripModelChanged`, selection state, `WillCloseAllTabs`, `OnTabStripModelDestroyed`). Preserve Chromium's callback ordering: mutate native state and snapshot IDs/order first, then dispatch the ABI event after the observer stack unwinds.
- Content/view hosting: `content/public/browser/web_contents.h` (`WebContents`, native view and observer/delegate surfaces), `content/public/browser/web_contents_observer.h`, `chrome/browser/ui/views/frame/browser_view.h`, `chrome/browser/ui/browser_window.h`, and `components/remote_cocoa/app_shim/bridged_content_view.{h,mm}`. Implement the Shaar macOS host around Chromium's `BrowserWindow`/Views widget and a clearly borrowed host `NSView*`. Add a narrow Shaar patch only where Chromium 155 has no embedder hook for safe hit testing/accessibility or an empty app-owned host window; keep it independently authored and covered by native tests.
- Hidden internal windows: use the browser/window visibility and extension window-controller surfaces in `chrome/browser/ui/browser_window/public/` and `chrome/browser/extensions/browser_extension_window_controller.h`; mark Shaar-owned internal extension hosts explicitly and exclude them from extension current-window lookup without hiding a user's app window or leaking the internal host into activation/window lists. Host tab visibility changes must feed Chromium's existing visibility, permission, dialog, PiP, and media state machinery instead of only toggling `NSView.hidden`.

These APIs are pinned-tree-specific: verify signatures against this synced Chromium 155 tree when implementing; they are not ABI promises.

## D. Proposed C ABI additions and Swift adapter

Keep phase two ABI v1 conventions exactly: `shaar_engine.h` is the only exported C header; opaque handles own Chromium objects; calls/callbacks are serialized on the Chromium UI thread; output/event slices are borrowed for callback duration; operations check the explicit `shaar_scope`; errors use the shared `shaar_error_code`/`shaar_error`; asynchronous work uses `shaar_submit` request IDs and reply callbacks; one monotonic event stream is registered once per engine. All event payloads include `kind` and `schemaVersion` and do not contain filesystem paths.

The shared sketch already declares `shaar_window_open(scope, window_id, out, error)`, `shaar_window_close`, `shaar_window_host_view`, `shaar_tab_open(window, tab_id, url, out, error)`, `shaar_tab_close`, `SHAAR_OP_WINDOW_ACTIVATE_TAB`, and `SHAAR_OP_WINDOW_PLACE_TABS`. Define their module semantics as follows:

1. `shaar_window_open` creates the host for exactly one regular `shaar_profile` or one `shaar_private_session`; the returned `shaar_window` carries that scope for its entire life. It may be initially hidden. `shaar_window_close` is an idempotency-checked close request; report cancellation/failure rather than invalidating the handle until Chromium confirms closure. `shaar_window_host_view` returns a borrowed view valid only until close/release; Swift never retains ownership of it.
2. `shaar_tab_open` creates a new tab in the target window and binds the caller's tab ID. Add a `foreground` argument or a typed `SHAAR_OP_TAB_OPEN` so background creation does not accidentally activate. Add `SHAAR_OP_WINDOW_SET_ACTIVE_PROFILE` for the app's profile switching within a regular native window. `SHAAR_OP_WINDOW_ACTIVATE_TAB` changes the selected tab within the same scoped window. `SHAAR_OP_WINDOW_PLACE_TABS` takes a complete ordered tab-ID array plus pinned IDs; validate uniqueness, membership, pinned-prefix ordering, and exact scope before applying atomically.
3. Add `SHAAR_OP_TAB_MOVE` for same-scope moves between two app windows and in-window reorder if the operation schema is simpler than `WINDOW_PLACE_TABS`. Its source and destination handles must share the same profile or private session; cross-profile/session moves return `SHAAR_WRONG_PROFILE`/`SHAAR_WRONG_SESSION`. Preserve the current unsupported live-cross-window behavior until the native detach/adopt transaction and rollback are implemented; do not silently close/recreate a document. In-window move/reorder remains supported. Extension `tabs.move` requests follow the same ownership gate.
4. Add typed replies for browser-originated requests, e.g. `SHAAR_OP_WINDOW_REQUEST_RESOLVE` and a bounded `SHAAR_OP_TAB_ACTIVATION_RESOLVE`, using request IDs from events. A popup/new-window request includes requested profile/session scope, opener tab ID, disposition, initial URL, and foreground intent. The Swift host can create the Shaar window then resolve the request with the new window handle; timeout or rejection closes the unadopted contents. Do not send raw Chromium pointers or trust extension-supplied IDs as ownership.

Use existing event kinds `SHAAR_EVENT_WINDOW` and `SHAAR_EVENT_TAB`; no new enum family is needed. Define stable payload event names and fields:

| Event payload `kind` | Required identity and data | Consumer behavior |
| --- | --- | --- |
| `window_opened`, `window_close_requested`, `window_closed` | profile ID, optional private session ID, window ID; close reason/quitting where relevant | Route to the owning native window; emit final close before invalidating handles. |
| `window_show_requested`, `window_creation_requested` | same scope IDs, request ID, `active`, disposition, opener tab ID, URL | Let app policy decide visibility and create/adopt a host; replies are typed and expire. |
| `tab_opened`, `tab_closed` | profile/session, window ID, tab ID, opener ID, foreground; close reason | Bind/unbind router and persist only regular-session model state. `tab_closed` is emitted only after confirmed closure, including host initiated close. |
| `tab_activated` | scope IDs, window ID, selected tab ID, previous tab ID, activation source | Update the Swift model synchronously with the event, then schedule placement/reconciliation after delivery; never echo activation as a reentrant reorder. |
| `tab_strip_changed` | scope IDs, window ID, complete ordered tab IDs, pinned prefix or pinned IDs, active index/ID, change reason | Reconcile native order without replacing durable workspace ownership. |
| `tab_activation_requested` | scope IDs, window/tab IDs, request ID, reason, expiration | App may focus/reveal the correct host; reject stale or cross-scope requests. |

Every private event must carry the private session ID as well as its parent profile ID, window ID, and tab ID where applicable. Private windows/tabs use the same function family and validation path as regular windows/tabs; there is no “private callback” side channel and no event can be interpreted as regular because its session ID is absent. Reject regular-profile handles paired with private windows, or vice versa, with typed scope errors. Never persist private order, active selection, history, or tab metadata.

Swift adapter work stays in `Sources/ChromiumBridge`: load/check `shaar_abi_major/minor`, wrap opaque handles, copy callback data before return, map typed failures to localized `NSError`/Swift errors, and provide a borrowed `NSView` only to existing AppKit host objects. Retain the `ARCChromiumRuntime` facade initially so `NativeBrowserHost`, `BrowserEngine`, `BrowserRuntimeEvents`/`BrowserRuntimeRouter`, and `PrivateBrowserHost` can migrate incrementally. Replace `ChromiumBridge.mm`'s Ardia registries with handle registries and event-driven state, retaining caller-owned Shaar IDs and explicit router ownership. Remove the `ArdiaCore*` protocols/types from the adapter only after parity gates pass.

## E. Parity tests and smoke checks

### Unit tests

- ABI contract tests for supported major/minor and struct sizes, borrowed view/callback lifetime, monotonic sequence, copied Swift event strings, error-code mapping, duplicate/stale handles, and profile/session/window/tab mismatch rejection.
- Window/tab model tests for create/close lifecycle, exactly-once close, selected-tab fallback, background vs foreground creation, stable IDs, pinned-prefix ordering, uniqueness, reorder, profile switching, and stale activation after close.
- Private scope tests proving multiple private sessions under one profile remain disjoint, each emitted private event has `session_id`, and no private order/selection is persisted or sent to regular callbacks.
- Host policy tests for hidden extension hosts being excluded from current-window lookup, ordinary windows still being eligible, and view visibility changes updating page-visible state rather than just AppKit visibility.

### Engine simulation

Use a deterministic C++ harness with fake reply/event sinks and real Chromium `Browser`/`TabStripModel` objects under the existing test profile harness. Exercise regular and private scopes: open hidden host, create two tabs in foreground/background, select, reorder and pin, close selected/nonselected tabs, close the host, reject wrong scope, and ensure event sequence/state snapshots agree after each mutation. Exercise renderer/window popup request, app acceptance/rejection/timeout, opening on a hidden host then showing it, and tab close cancellation/beforeunload. Simulate activation during `OnTabStripModelChanged` and assert dispatch order avoids reentrant placement. For cross-window moves, assert rollback/typed refusal until transactional move support lands; then require tab identity and `WebContents` continuity, source fallback selection, destination ordering, and failure rollback. Include hidden extension-manager/popup windows in current-window selection tests.

### Headless smoke checks

- Use the existing `NativeWindowProbe`, `WindowClientProbe`, `EngineRequestedWindowProbe`, `PrivateWindowProbe`, `PrivateBrowserHostTests`, and `NativeTabSelectionTests` as the parity targets. Check multiple regular windows/profiles, popup adoption, window show activation flags, close notifications, selected-tab native view, and saved tab order/pinned state.
- Run the corresponding private-window and private multi-tab probes with two sessions sharing one parent profile; verify event IDs and no durable private state.
- Verify hidden extension/popup views are not surfaced as app windows and do not become extension “current window”; verify host show/hide updates visibility-dependent permission/PiP behavior.
- Run focused native engine smoke tests in source-engine CI and app tests in normal CI. A successful Swift compile alone does not prove Browser/AppKit integration; no local build or runtime claim is made by this specification.

## F. Effort and risks

Keep the design's migration row 3 estimate of **3–5 engineer-weeks** for AppKit host integration, Browser/TabStrip ownership, open/adopt/place/select/close, popup and extension-view requests, callback ordering, and window/tab probes. This spec keeps private sessions first-class in the ABI; full private lifecycle/teardown remains coupled to migration row 5's separate **2–4 engineer-week** work and should be validated early during window and tab implementation rather than postponed. Estimate includes focused implementation and validation but excludes Chromium sync/build wall time.

Highest risks are: the browser UI stack assumes Chrome-managed window/tab-strip behavior; macOS native view hit testing, accessibility, key routing, close prompts, and empty windows currently depend on patch hooks; hidden extension hosts can corrupt both focus and extension “current window” semantics; `TabStripModelObserver` callbacks are reentrant and removal does not always mean destruction; selected-tab visibility affects permission, dialogs, PiP and media; private ownership must remain explicit across every event/reply; and tab moves must preserve the original `WebContents` and Swift workspace identity or roll back cleanly. Keep C ABI/event contracts stable while these internals are proven; do not claim parity from compile success alone.
