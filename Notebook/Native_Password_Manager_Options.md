# Optional native password managers

Target: Settings enables/disables native integration for the selected browser Profile. Native UI, provider vault transport and Chromium form handling are separate responsibilities. Browser startup and ordinary browsing must work with integration off. Bitwarden is first provider; each additional manager needs its own verified contract.

Same Bitwarden vault may intentionally span browser Profiles. Website cookies and storage remain Profile-owned and isolated; changing Space must not silently change vault binding or merge website sessions.

## Current native SDK evidence

Issue [#52](https://github.com/arcusis/browser/issues/52) remains open. [PR #97](https://github.com/arcusis/browser/pull/97) and [PR #102](https://github.com/arcusis/browser/pull/102) are merged. PR #102 source [`f7c24fd`](https://github.com/arcusis/browser/commit/f7c24fd306d35af592918188ce89c9d54b2d32cf) passed both CI runs and merged as `41ebd852c09e81f437320d80b157cc9a7a889b4d`. Its committed proofs supersede older notes that Swift auth/MFA had not run or that the wrapper lacked MFA handling.

- Actual generated Swift auth proof exercised prelogin, MFA challenge, valid-MFA retry, invalid-MFA rejection and malformed-challenge rejection against an owned loopback HTTP mock. It also checked device identity, SDK-derived password hash and MainActor host publication fencing. [Proof scope and limits](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenAuthSpike/SwiftAuthProof.md); [runner](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/scripts/test-native-bitwarden-swift-auth.py).
- A second generated Swift proof composes password login with `initializeUserCrypto`, then encrypts and decrypts one synthetic cipher. Wrong-password and malformed wrapped-key setup reject without publishing a token or leaving a usable candidate key; independent client stays locked. [Proof README](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenSessionProbe/README.md); [Swift proof](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/NativeBitwardenSessionProbe/main.swift).
- The gate binds attempts to Profile, vault, account and authority; changed context, disable or successor attempt rejects stale publication. This fences host publication; it does not cancel the generated SDK future. [Gate](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Sources/BrowserCore/PasswordAuthenticationGate.swift); [ownership tests](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/BrowserCoreTests/PasswordAuthenticationGateTests.swift).

PR #102 reports combined-tree runs of 14 auth Python, 5 session Python and 7 Swift ownership tests, plus both native proofs. Those proofs ran on arm64 macOS 27.0.1 with macOS 26.0 minimum metadata; macOS 26 runtime was not exercised. Native Swift `Task` cancellation remains unsupported. [PR validation and scope](https://github.com/arcusis/browser/pull/102).

## Limits and choices

These synthetic SDK proofs do not establish TLS or real-server compatibility, fetched-vault sync, organization handling, refresh/logout/lock, Chromium autofill/save/update, vendor support or product/distribution acceptance. Host owns session publication and refresh policy; the Keychain store below supplies token persistence only.

## Profile-scoped Keychain token store

[PR #109](https://github.com/arcusis/browser/pull/109), source [`0e9a4ec`](https://github.com/arcusis/browser/commit/0e9a4ec0970b63bf761cef2d6012c54e083ba719), is merged as `63c113eb52356d4d39a3bd151c4bfb46c84b2e8c`; issue [#106](https://github.com/arcusis/browser/issues/106) is closed. Source adds `PasswordCredential` (`accessToken`, optional `refreshToken` and `expiresAt`) and `PasswordCredentialStore.read(for:)`, `write(_:for:)` and `delete(for:)`, keyed by `PasswordAuthenticationBinding`. Records are versioned and bounded; binding includes Profile, vault, account and canonical HTTPS authority. The store uses a fixed app-owned generic-password Keychain service, exact service/account lookup, `kSecAttrSynchronizable=false`, and `LAContext.interactionNotAllowed=true` on read/write/delete.

The parent native probe created, read, updated and deleted only synthetic entries in a random app-owned service namespace, without prompts or iCloud synchronization; PR #109 reports 17 focused behavior/ownership tests plus one native test. This proves token-persistence component behavior on arm64 macOS 27.0.1, with macOS 26 runtime and signed-distribution behavior still unverified. It is not an integrated backend/controller, session publication, refresh/logout policy, vault persistence, or product acceptance. No SDK dependency or Settings provider toggle exists; #52 and typed fetched-vault sync issue [#103](https://github.com/arcusis/browser/issues/103) remain open.

Issue [#99](https://github.com/arcusis/browser/issues/99) is closed by [merged PR #107](https://github.com/arcusis/browser/pull/107) (`a7538dc`); its scoped SDK source pin is `accepted=true` after independent native proof. Shared SDK key clearing does not prove caller-plaintext erasure, token logout, persisted-record deletion, or complete product lock. Typed sync and fetched-cipher retrieval remain open in #103.

Bitwarden distinguishes its [public Secrets Manager SDK](https://contributing.bitwarden.com/getting-started/sdk/) from its [internal Password Manager SDK](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/README.md), whose third-party use is unsupported and interface unstable. The internal UniFFI crate declares `GPL-3.0-only OR LicenseRef-Bitwarden-SDK`; retain the existing GPL component guard and notices, and get distribution review before shipping. This experiment accepts no SDK-specific terms on the company's behalf.

Bitwarden documents a [DuckDuckGo macOS partnership](https://bitwarden.com/help/duckduckgo-macos-browser-integration/) using the installed Bitwarden app and pairing approval. That documents DuckDuckGo support only; custom-browser trust/transport compatibility and a general vendor contract remain unverified. Apple [Credential Provider APIs](https://developer.apple.com/documentation/authenticationservices/ascredentialproviderviewcontroller) do not prove compatibility with embedded Chromium fields. The official [extension autofill flow](https://bitwarden.com/help/auto-fill-browser/) is separate compatibility evidence, not native-provider acceptance. Keep each provider behind a small boundary; do not claim generic vendor support.
