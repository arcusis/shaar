## Session lifecycle and actual boundary

1. **Client and token ownership.** Generated Swift `Client(tokenProvider:settings:managedSettings:)` requires `ClientManagedTokens`; its only callback is `getAccessToken()`. The provider owns access-token storage. It has no SDK callback to set/refresh/clear access or refresh tokens. `ClientSettings` sets identity/API URLs, not TLS roots or client identity. See [`lib.rs::Client::new`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-uniffi/src/lib.rs), [`auth_tokens.rs::ClientManagedTokens`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-core/src/auth/auth_tokens.rs), and generated `BitwardenCore.swift` / `BitwardenSDK.swift` in receipt output.
2. **Login result is not session install.** Callable Swift path: `Client.auth().login().getPasswordPrelogin(email:)`, then `loginViaPassword(request:)`; result is `LoginResponse.authenticated(LoginSuccessResponse)` or `.twoFactorRequired(TwoFactorChallenge)`. Success record carries access/optional refresh token, wrapped user/private and account crypto state, and decryption options. Patched [`uniffi::LoginClient::login_via_password`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-uniffi/src/auth/login.rs) delegates to [`bitwarden_auth::login::login_via_password`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-auth/src/login/login_via_password/login_via_password_impl.rs), which derives the password proof, sends Identity request, and returns parsed response. It does not call `InternalClient::set_tokens`, initialize `KeyStore`, or establish login state. Thus successful auth response alone is not usable vault session.
3. **Token plus user-key install.** A separate existing Rust-only route, [`bitwarden_core::auth::login::password::login_password`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-core/src/auth/login/password.rs), writes access/refresh tokens through `InternalClient::set_tokens`, unwraps the user key from master-password unlock data, calls `initialize_user_crypto_master_password_unlock`, then records login method. This is a legacy `pub(crate)` core flow, not the modern UniFFI `loginViaPassword` call. It is not a shortcut for the current Swift client: `ClientManagedTokenHandler::set_tokens` explicitly panics. The existing exported `CryptoClient.initializeUserCrypto(req:)` accepts typed `accountCryptographicState`, KDF/email/user identity and `InitUserCryptoMethod.masterPasswordUnlock(password:masterPasswordUnlock:)`; the SDK derives and unwraps keys and records login method. Host can compose these existing primitives from a coherent login response; that composition has not yet run through Swift. User/private/account keys live in SDK `KeyStore`; auth callback tokens live with host provider.
4. **Sync and organization keys.** Rust `bitwarden_sync::SyncClient::sync(request:)` fetches full sync response and dispatches handlers (`crates/bitwarden-sync/src/sync_client.rs`). No `SyncClient`/`sync` method appears in generated UniFFI Swift. Exported `Client.cryptoSyncHandler()` is only a handler accessor. `VaultClient.ciphers().list()` and `getAll()` read local state; they do not retrieve server vault. `CryptoClient.initializeOrgCrypto(req:)` is callable after user crypto initialization, but caller must obtain encrypted organization keys from sync; the SDK handles their decryption through `EncryptionSettings::set_org_keys`. Host must not reimplement that cryptography. So neither sync retrieval nor organization-key preparation is bridged as end-to-end session flow.
5. **Cipher decryption.** Generated Swift exposes `VaultClient.ciphers().decrypt(cipher:)`, list/decrypt helpers. They call SDK crypto and require initialized key state plus supplied cipher data; exposed `list()` reads local cache. No full-vault or fetched-vault claim follows from those APIs.
6. **Lock, unlock, disconnect.** `UserCryptoManagementClient` exports PIN/key-management helpers; `CryptoClient.reinitUserCrypto` handles a specific synced v2 upgrade case. Generated top-level API has no session lock/logout/token-clear/disconnect operation. Existing `initializeUserCrypto` supplies master-password/PIN/decrypted-key initialization primitives; a complete host unlock sequence remains unverified. Rust `PasswordManagerClient::unlock()` exposes a separate rehydration/session-key flow that is not a general master-password shortcut. Dropping top-level `Client` is not proof: retained subclients may still reference shared key state. Source inspection cannot establish key zeroization. A host lock must clear shared SDK key state and host plaintext/fill state; it need not mean logout or erase encrypted account data. SDK `KeyStore::clear` exists in Rust, but is not exposed by the inspected Swift crypto client. Disabling/disconnecting also needs explicit host token and persisted-state policy; retained handles must not regain permission to fill or install a late login result. Do not represent a Settings toggle as disabling a live session safely.

## Trust boundary

At actual native HTTP boundary, [`bitwarden-api-base/src/client.rs::new_http_client_builder`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-api-base/src/client.rs) configures reqwest with rustls platform certificate verifier; release builds also set `https_only(true)`. [`ClientBuilder::build`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-core/src/client/builder.rs) constructs identity/API clients from that builder. Inspected boundary provides no custom root-certificate or client-certificate/identity hook, and generated `Client` constructor offers none. Platform-trusted HTTPS is the existing path, including a self-hosted instance with a trusted certificate; actual server interoperability has not run. Explicit custom test-CA injection and mTLS identity configuration are separate unexposed/unverified capabilities, not prerequisites for ordinary Bitwarden HTTPS. Chromium fixture CA trust does not configure reqwest/rustls; do not infer SDK trust from fixture HTTPS.

## Next implementation slices

First compose existing Swift exports: keep a host token provider scoped to the chosen vault/account and origin; use modern login result plus coherent KDF/wrapped account-key fixture to construct `InitUserCryptoRequest`; initialize user crypto and decrypt a synthetic cipher. Auth request/response parsing alone is insufficient: current auth mock keys were selected for parsing, not proven to match the prelogin password/salt. This step should identify exact missing fields before adding another auth facade. Keep disabled/abandoned attempts behind a generation guard so a late SDK result cannot install tokens or keys. Pinned generated Swift futures do not propagate Task cancellation; host cancellation semantics require their own proof.

Then add the smallest missing SDK operation at each boundary: a typed Swift sync entry delegates existing Rust `PasswordManagerClient::sync()` and registered handlers; a scoped clear-keys export delegates the shared `KeyStore::clear` rather than replacing SDK cryptography. Verify retained crypto/cipher subclients fail to decrypt after clear, and an independent client remains usable; unlock via existing initialization restores expected operation. Token refresh, safe persistence and disconnect follow with explicit ownership and failure behavior. No inert Settings toggle before this backend works.

**Synthetic acceptance:** exact pin/patch/bindings; host token callback supplies token only for the intended account/origin; existing Swift crypto initialization decrypts a coherent sentinel; real sync fetch reaches owned Identity/API fixture and loads user/organization ciphers; locked retained handles reject decryption; explicit unlock restores it; late successful login after disable is discarded; disconnect clears configured host tokens and repositories. These are separate observable stages. Do not claim erasure of caller-owned plaintext copies or key zeroization without direct evidence.

Use existing platform trust for normal HTTPS. If the owned HTTPS fixture needs a private CA, add and verify a client-scoped trust hook without changing laptop trust; reject unrelated CA and HTTP in a release-targeted proof. mTLS is deferred unless a concrete provider/company requirement needs it. No company account, browser embedding, provider UI or distribution acceptance follows from this source note.
