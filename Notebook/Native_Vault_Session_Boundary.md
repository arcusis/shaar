# Native vault session boundary

Current evidence is an isolated technical experiment against pinned, unsupported Bitwarden Password Manager SDK internals. Issue [#52](https://github.com/arcusis/shaar/issues/52) remains open. [PR #97](https://github.com/arcusis/shaar/pull/97) and [PR #102](https://github.com/arcusis/shaar/pull/102) are merged. PR #102 source [`f7c24fd`](https://github.com/arcusis/shaar/commit/f7c24fd306d35af592918188ce89c9d54b2d32cf) passed both CI runs and merged as `41ebd852c09e81f437320d80b157cc9a7a889b4d`. No SDK dependency is bundled in the browser.

## Token persistence component

[PR #109](https://github.com/arcusis/shaar/pull/109) at source [`0e9a4ec`](https://github.com/arcusis/shaar/commit/0e9a4ec0970b63bf761cef2d6012c54e083ba719) is merged as `63c113eb52356d4d39a3bd151c4bfb46c84b2e8c`; issue [#106](https://github.com/arcusis/shaar/issues/106) is closed. It adds Profile/vault/account/authority-bound `PasswordCredential` records with access token, optional refresh token and expiry, through `PasswordCredentialStore` read/write/delete APIs. Keychain generic-password queries use a fixed application-owned service plus exact binding-derived account, disable synchronization to iCloud, and prohibit interaction via `LAContext`; records are versioned and size-bounded.

PR #109 records a parent-run native probe that created, read, updated and deleted synthetic records in its random app-owned namespace without prompts or iCloud; 17 focused behavior/ownership tests and one native test are reported. Runtime was arm64 macOS 27.0.1; macOS 26 runtime and signed-distribution behavior remain unverified. This is a token-persistence component only: no SDK dependency, integrated backend/controller, session publication, Settings provider toggle, refresh/logout policy, or product acceptance. Fetched-cipher sync has scoped acceptance in merged [PR #113](https://github.com/arcusis/shaar/pull/113), which closed [#103](https://github.com/arcusis/shaar/issues/103); composed fixture lifecycle is accepted in merged [PR #127](https://github.com/arcusis/shaar/pull/127), closing [#114](https://github.com/arcusis/shaar/issues/114). Product controller integration remains open.

## Verified native behavior

- PR #97 ran actual generated Swift auth calls for prelogin, MFA challenge/retry, invalid MFA and malformed challenge against an owned loopback HTTP mock, checking device identity and SDK-derived hash. PR #102 added the real delayed-success publication check. [Committed auth proof](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenAuthSpike/SwiftAuthProof.md).
- PR #102 composes generated Swift password login, typed `initializeUserCrypto`, and synthetic cipher encrypt/decrypt. Wrong password and malformed wrapped-key setup leave no published token or usable candidate key; separate client remains locked. [Committed session proof](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/NativeBitwardenSessionProbe/main.swift) and [README](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenSessionProbe/README.md).
- MainActor `PasswordAuthenticationGate` binds publication rights to Profile, vault, account and authority; it rejects superseded/disabled/rebound attempts and consumes ownership before publication. It prevents stale host publication, not SDK task cancellation. [Gate source](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Sources/BrowserCore/PasswordAuthenticationGate.swift) and [tests](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/BrowserCoreTests/PasswordAuthenticationGateTests.swift).
- PR #102 reports combined-tree results: 14 auth Python tests, 5 session Python tests, 7 Swift ownership tests and both native proofs passed. Runtime host was arm64 macOS 27.0.1; artifacts target macOS 26.0. macOS 26 runtime remains untested; native Swift `Task` cancellation remains unsupported. [Validation record](https://github.com/arcusis/shaar/pull/102).

## Fetched-cipher sync and next boundary

Merged [PR #113](https://github.com/arcusis/shaar/pull/113), source [`417b806`](https://github.com/arcusis/shaar/commit/417b806f8bf3d62d5f3390e0c0b5b615da69362e), uses a typed generated-Swift sync entrypoint, SDK HTTP/token path and registered sync handlers against owned loopback mocks. It fetched and decrypted one synthetic cipher, preserved the previous encrypted snapshot after unauthorized and malformed responses, and left an independent client unchanged. This is atomic publication for the client-scoped cipher snapshot only; earlier handlers may mutate their own state before a later failure. It does not prove full-vault rollback, organizations, TLS or real-server compatibility. [Probe](https://github.com/arcusis/shaar/blob/48b0ac186eca6e5e1d2960e38fd7166399b1fd7d/Tests/NativeBitwardenSyncProbe/main.swift), [runner](https://github.com/arcusis/shaar/blob/48b0ac186eca6e5e1d2960e38fd7166399b1fd7d/scripts/test-native-bitwarden-sync.py), [PR validation](https://github.com/arcusis/shaar/pull/113).

Merged [PR #127](https://github.com/arcusis/shaar/pull/127), source [`5d3d891`](https://github.com/arcusis/shaar/commit/5d3d8911a18e261b9aca7998e10033efdb23c546), composes the auth, shared-key-clear and sync patches in one pinned 22-path SDK source tree and matching generated Swift bindings. Its fresh source build passed 13 Rust regressions and 30 native lifecycle stages: login, crypto initialization, gated token/Keychain publication, authenticated fetched-cipher sync/decryption, lock and retained-handle rejection, explicit unlock, stale login after disable/rebind, denied-store cleanup, independent client/record survival and disconnect. Parent independently reconstructed the SDK tree, regenerated matching bindings and reproduced all 30 stages with its own mock/listener; exact request counts and credential/process/listener cleanup passed. Published pin modes, 13 Python boundary tests and exact-source CI passed. [Probe](https://github.com/arcusis/shaar/blob/5d3d8911a18e261b9aca7998e10033efdb23c546/Tests/NativeBitwardenLifecycleProbe/main.swift) and [runner contract](https://github.com/arcusis/shaar/blob/5d3d8911a18e261b9aca7998e10033efdb23c546/ThirdParty/BitwardenLifecycleProbe/README.md).

`accepted=true` applies to this owned fixture proof; `integration_ready=false` remains. The runner uses loopback HTTP and a synthetic HTTPS identity only for scoped local credential storage, so TLS authority binding, real service/organization/full-vault behavior and product availability remain unaccepted. Actual product controller, native Settings and origin-bound form fill/save/update remain [#52](https://github.com/arcusis/shaar/issues/52)/[#9](https://github.com/arcusis/shaar/issues/9). No SDK dependency or provider is bundled in the browser.

Private-window policy and implementation remain unaccepted; see [[Private_Window_Ownership_Plan]]. Native vault access stays unavailable there until an explicit isolated lifecycle is accepted.

## Ownership and unverified boundary

`ClientManagedTokens` supplies `getAccessToken()`; proof host publishes the synthetic access token only after user-crypto initialization succeeds. Host still owns integration, publication, refresh, logout and disconnect policy; `PasswordCredentialStore` was not wired into the historical PR #102 flow; PR #127 now composes the actual store and authentication gate in its owned native fixture. This still does not install a product session. Successful auth response alone is not an installed session. [SDK token callback source](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-core/src/auth/auth_tokens.rs) and [session proof](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/NativeBitwardenSessionProbe/Fixtures.swift).

The PR #102 proof encrypts and decrypts a local synthetic cipher; it does not fetch server vault data. PR #113 later proves one fetched encrypted item through SDK HTTP sync, within its narrow mock scope above. Do not claim TLS/real vendor compatibility, organization or full-vault behavior, usable product lock/logout, autofill, save/update, or product/distribution acceptance. Issue [#99](https://github.com/arcusis/shaar/issues/99) is closed by [merged PR #107](https://github.com/arcusis/shaar/pull/107) (`a7538dc`); its scoped SDK pin is `accepted=true` after independent native proof. That proves shared in-memory SDK key clearing through retained handles only; not caller-owned plaintext erasure, token logout, Keychain record deletion, or complete product lock. The committed auth proof explicitly reports `native_task_cancellation_supported=false` and `integration_ready=false`.

## Remaining SDK operations

Rust [`SyncClient::sync`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-sync/src/sync_client.rs) fetches a response and dispatches registered handlers. Generic [`PasswordManagerClient::new_with_client_tokens`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-pm/src/lib.rs) does not register the handlers used by the PR #113 sync proof; that proof composes a bounded handler set and does not claim full-vault or organization sync. Cipher `list`/`getAll` read local state. Existing `initializeOrgCrypto` accepts encrypted organization keys obtained from sync; SDK decrypts them, not host-written cryptography.

Existing `initializeUserCrypto` supplies master-password/PIN/decrypted-key primitives. Complete unlock and lock remain host integration work. Dropping a top-level client does not revoke retained crypto/cipher handles; shared SDK key state, host token policy and host plaintext/fill state need explicit lifecycle handling. #99 addresses only shared-key clearing, without a zeroization or complete product-lock claim.

Normal HTTPS uses the SDK's [reqwest/rustls platform verifier](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-api-base/src/client.rs); release builds enable `https_only(true)`. This ordinary platform-trusted HTTPS path is distinct from the Keychain store's HTTPS-authority binding check, and does not prove a network request or vendor compatibility. Client-scoped private-CA and mTLS identity hooks are absent at the inspected boundary. Neither is required for ordinary platform-trusted HTTPS. Chromium fixture trust does not configure SDK trust; a private-CA test must use a verified client-scoped hook, without changing laptop trust.

## Guardrails

- SDK pin: [`bitwarden/sdk-internal` at `5cf919837e83b71c2508bf99344ea57cf5f84e88`](https://github.com/bitwarden/sdk-internal/tree/5cf919837e83b71c2508bf99344ea57cf5f84e88); source pin record: [`pin.json`](https://github.com/arcusis/shaar/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenAuthSpike/pin.json). Internal SDK says third-party use is unsupported and interface unstable. Preserve notices and component guard; its GPL alternative and SDK-specific terms need distribution review before shipping.
- Same vault may intentionally span browser Profiles. Website cookies/storage remain Profile-isolated; do not silently rebind vault or merge website sessions.
- Do not infer SDK trust behavior from Chromium fixture HTTPS. Real TLS/server compatibility remains untested; do not spoof vendor/client identity.
- SDK `KeyStore::clear` from #99 is accepted for its scoped native experiment after independent proof; do not infer key zeroization, clearing caller-owned plaintext, token logout, Keychain deletion or complete product lock.
