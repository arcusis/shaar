# Native vault session boundary

Current evidence is an isolated technical experiment against pinned, unsupported Bitwarden Password Manager SDK internals. Issue [#52](https://github.com/arcusis/browser/issues/52) remains open. [PR #97](https://github.com/arcusis/browser/pull/97) and [PR #102](https://github.com/arcusis/browser/pull/102) are merged. PR #102 source [`f7c24fd`](https://github.com/arcusis/browser/commit/f7c24fd306d35af592918188ce89c9d54b2d32cf) passed both CI runs and merged as `41ebd852c09e81f437320d80b157cc9a7a889b4d`. No SDK dependency is bundled in the browser.

## Verified native behavior

- PR #97 ran actual generated Swift auth calls for prelogin, MFA challenge/retry, invalid MFA and malformed challenge against an owned loopback HTTP mock, checking device identity and SDK-derived hash. PR #102 added the real delayed-success publication check. [Committed auth proof](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenAuthSpike/SwiftAuthProof.md).
- PR #102 composes generated Swift password login, typed `initializeUserCrypto`, and synthetic cipher encrypt/decrypt. Wrong password and malformed wrapped-key setup leave no published token or usable candidate key; separate client remains locked. [Committed session proof](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/NativeBitwardenSessionProbe/main.swift) and [README](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenSessionProbe/README.md).
- MainActor `PasswordAuthenticationGate` binds publication rights to Profile, vault, account and authority; it rejects superseded/disabled/rebound attempts and consumes ownership before publication. It prevents stale host publication, not SDK task cancellation. [Gate source](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Sources/BrowserCore/PasswordAuthenticationGate.swift) and [tests](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/BrowserCoreTests/PasswordAuthenticationGateTests.swift).
- PR #102 reports combined-tree results: 14 auth Python tests, 5 session Python tests, 7 Swift ownership tests and both native proofs passed. Runtime host was arm64 macOS 27.0.1; artifacts target macOS 26.0. macOS 26 runtime remains untested; native Swift `Task` cancellation remains unsupported. [Validation record](https://github.com/arcusis/browser/pull/102).

## Ownership and unverified boundary

`ClientManagedTokens` supplies `getAccessToken()`; proof host publishes the synthetic access token only after user-crypto initialization succeeds. Host therefore owns access-token storage/publication and any refresh, persistence, clear or disconnect policy. Successful auth response alone is not an installed session. [SDK token callback source](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-core/src/auth/auth_tokens.rs) and [session proof](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/Tests/NativeBitwardenSessionProbe/Fixtures.swift).

The proof encrypts and decrypts a local synthetic cipher; it does not fetch server vault data. Generated Swift has no complete sync trigger. Do not claim fetched-vault behavior, TLS/real vendor compatibility, organization handling, usable lock/logout/key clearing, autofill, save/update, or product/distribution acceptance. Swift-side key-clear candidate [#99](https://github.com/arcusis/browser/issues/99) remains open and unaccepted; it is not proof of working clear behavior. The committed auth proof explicitly reports `native_task_cancellation_supported=false` and `integration_ready=false`.

## Remaining SDK operations

Rust [`SyncClient::sync`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-sync/src/sync_client.rs) fetches a response and dispatches registered handlers. [`PasswordManagerClient::new_with_client_tokens`](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-pm/src/lib.rs) does not register the handlers in `new_with_sync`; even that constructor leaves further handlers as TODOs. Cipher `list`/`getAll` read local state. [#103](https://github.com/arcusis/browser/issues/103) must prove actual fetched encrypted-cipher retrieval, not only a boolean sync export. Existing `initializeOrgCrypto` accepts encrypted organization keys obtained from sync; SDK decrypts them, not host-written cryptography.

Existing `initializeUserCrypto` supplies master-password/PIN/decrypted-key primitives. Complete unlock and lock remain host integration work. Dropping a top-level client does not revoke retained crypto/cipher handles; shared SDK key state, host token policy and host plaintext/fill state need explicit lifecycle handling. #99 addresses only shared-key clearing, without a zeroization or complete product-lock claim.

Normal HTTPS uses the SDK's [reqwest/rustls platform verifier](https://github.com/bitwarden/sdk-internal/blob/5cf919837e83b71c2508bf99344ea57cf5f84e88/crates/bitwarden-api-base/src/client.rs); release builds enable `https_only(true)`. Client-scoped private-CA and mTLS identity hooks are absent at the inspected boundary. Neither is required for ordinary platform-trusted HTTPS. Chromium fixture trust does not configure SDK trust; a private-CA test must use a verified client-scoped hook, without changing laptop trust.

## Guardrails

- SDK pin: [`bitwarden/sdk-internal` at `5cf919837e83b71c2508bf99344ea57cf5f84e88`](https://github.com/bitwarden/sdk-internal/tree/5cf919837e83b71c2508bf99344ea57cf5f84e88); source pin record: [`pin.json`](https://github.com/arcusis/browser/blob/f7c24fd306d35af592918188ce89c9d54b2d32cf/ThirdParty/BitwardenAuthSpike/pin.json). Internal SDK says third-party use is unsupported and interface unstable. Preserve notices and component guard; its GPL alternative and SDK-specific terms need distribution review before shipping.
- Same vault may intentionally span browser Profiles. Website cookies/storage remain Profile-isolated; do not silently rebind vault or merge website sessions.
- Do not infer SDK trust behavior from Chromium fixture HTTPS. Real TLS/server compatibility remains untested; do not spoof vendor/client identity.
- SDK `KeyStore::clear` candidate #99 is separate and not accepted. Do not infer key zeroization, clearing caller-owned plaintext, token logout, persistence deletion or retained-handle behavior.
