# Native window and tab ownership

The native bridge supports distinct window identities with window-owned tab selection, Find sessions, extension popups, and close state. Live tabs bind both their profile and native window; implicit reassignment and unknown-window fallback are rejected. One shared runtime dispatcher routes events to window-specific application clients. Profile library/download events reach every registered client using that profile; tab, popup, Find, and consent events retain their owning window. The native host restores saved window models and supports Command-N for a new managed window. File/Edit/Tabs actions resolve the actual key browser window, its sheet parent, or an explicitly owned extension popup; unknown key windows cannot fall back to another account. Modal state disables underlying page actions. Shift-Command-W closes the owning window; Command-W closes the selected tab or an empty window. Physical shortcut/focus and native close-cancellation acceptance remain open.

Engine-created normal-profile windows now enter the managed native host. Page `window.open` popups use the public adoption API after insertion notification unwinds; extension `chrome.windows.create` uses a fresh empty host before Chromium attaches its browser. The pinned engine reports extension popup browsers as `app`; that category also receives a managed context. Requested profile and known opener determine account/Space placement. Opener messaging survives page-popup adoption, background extension requests retain saved focus, and confirmed last-tab closure retires an engine-created empty window. An extension attempt to move an existing live tab into another window is returned to its original owner with its document, ordering and selection retained; user-facing cross-window tab transfer is not implemented. Declined requests use an unseen, unsaved internal host which closes immediately, avoiding Chromium's stock-window fallback. Private-session support, real vendor/OAuth window flows, popup-specific geometry/appearance and complete window-type coverage remain separate gates.

Tab-selection changes reported by Chromium update the owning window's model and saved selection. Activating an existing tab in another Space using the current profile reveals its Space and folder without moving or duplicating the page. Stale Find/consent/popup context is canceled. Engine activation in an inactive profile does not switch the displayed account. Host-created background tabs and host profile/ordering operations retain the application's selected tab. Model selection updates during the engine notification; tab-strip reconciliation waits until that notification unwinds.
