# Project scope and acceptance

Shaar ([[Product_Identity]]) is a native macOS 26+ internal Arc replacement: SwiftUI/AppKit chrome, pinned Chromium, arbitrary Spaces with per-Space pins/folders/saved tabs, simultaneous isolated accounts and explicit profile sharing, page-centered Command-T, Library/downloads and native dragging. Bitwarden is the first optional password-manager integration, controlled in native Settings; supported native backend is under review. Surfshark excluded. Google Workspace/Meet and Cloudflare Access remain company acceptance gates.

Native Settings has General, Profiles, Shortcuts and optional Bitwarden connection controls, unused isolated profile creation, profile renaming, per-Profile launcher search engines and a new-window sidebar preference. Bitwarden connection, supported MFA, lock and personal-vault metadata sync are published in [#136](https://github.com/arcusis/shaar/pull/136), with the local SDK dependency explicitly enabled for development builds. Full Settings parity remains [#51](https://github.com/arcusis/shaar/issues/51); complete native password-manager workflows and provider acceptance remain [#52](https://github.com/arcusis/shaar/issues/52). Further extension-specific integration is paused during native integration.

The [first milestone](https://github.com/arcusis/shaar/milestone/1) remains open. GitHub issues own live task state; this note records acceptance boundaries, not session activity.

- Native shell, profile/Space models, launcher, sidebar organization, Library and browser essentials are published on `production`.
- Lazy tab restoration avoids loading every saved page. Sidebar indexing removes repeated sibling scans; model/CPU checks do not establish total-process performance with hundreds of live pages.
- Synthetic extension login/lock/unlock/restart control passes in two separate profiles and an explicitly shared-profile Space. Native SDK fixtures and the optional development integration establish their stated source, crypto and memory-store boundaries. Organization-key replacement is published as an SDK candidate in [#143](https://github.com/arcusis/shaar/pull/143): empty snapshots revoke organization keys, replacements serialize, and strict clients require fresh sync before restoring organization access. Package/application integration, full fill/save/update, supported URI matching, restart recovery and real-service compatibility remain [#52](https://github.com/arcusis/shaar/issues/52) and [#9](https://github.com/arcusis/shaar/issues/9). Fixture and component success do not establish those workflows.
- Original chrome corrections are closed in [#24](https://github.com/arcusis/shaar/issues/24), including user confirmation that top-bar dragging works. Broader physical keyboard/pointer/trackpad, drag/drop, native focus and close cancellation remain [#4](https://github.com/arcusis/shaar/issues/4), [#5](https://github.com/arcusis/shaar/issues/5), [#21](https://github.com/arcusis/shaar/issues/21) and [#37](https://github.com/arcusis/shaar/issues/37).
- Product private-engine APIs and transient private UI are published in [#131](https://github.com/arcusis/shaar/pull/131) and [#137](https://github.com/arcusis/shaar/pull/137). The actual native close callback is observed after quit cancellation in [#141](https://github.com/arcusis/shaar/pull/141); owned initial/restart fixtures pass all 64 private checks, preserve normal history/workspace state and retire private windows/contexts. [#124](https://github.com/arcusis/shaar/issues/124) is closed on that scope. Physical input and broader native interaction acceptance remain separate.
- Real company Workspace/Meet/Cloudflare Access compatibility remains [#1](https://github.com/arcusis/shaar/issues/1), [#3](https://github.com/arcusis/shaar/issues/3) and [#6](https://github.com/arcusis/shaar/issues/6).
- Command-T folder lookup and tab traversal cost is reduced in [#132](https://github.com/arcusis/shaar/pull/132); pure search benchmarks do not establish keystroke latency or whole-process performance. Realistic process performance, engine update/provenance and signed/notarized distribution remain [#8](https://github.com/arcusis/shaar/issues/8) and [#19](https://github.com/arcusis/shaar/issues/19).
- Archive comparison now accepts narrowly validated signing-envelope changes in [#133](https://github.com/arcusis/shaar/pull/133): all 547 members of the retained development preview match, including independently verified Mach-O payloads. Source-to-binary attestation remains unverified; matching archive bytes and ad hoc signatures do not close release acceptance. Per-Profile download-directory support still requires a new engine build in [#75](https://github.com/arcusis/shaar/issues/75).

Source CI, authored screenshots and hidden native fixtures each prove their own scope. None establishes physical input, company-site compatibility or release acceptance. Company daily use is not accepted yet. Development bundles are ad hoc signed, not notarized releases.
