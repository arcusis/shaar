# Shared extension home (#287)

The extensions module (`SHAAR_MODULE_EXTENSIONS = 1300`) treats an approved Web Store install as one browser-wide *intent*. A browser-owned catalog records its ID and approved version. Each regular Chromium profile still gets its own installed instance. Reconcile the catalog when a profile opens, and retry failed profiles without repeating consent. A missing instance is queued through Chromium's pending extension manager with the Web Store update URL and approved version. The response distinguishes installed, queued, and failed profiles; a queued update is not an installed extension. A profile switch changes only that profile's enable state. Spaces inherit the profile's state. Private sessions do not own installs and require their existing explicit extension access grant.

Keep package identity, updates, permissions, and install policy in Chromium's extension service. Do not share an extension directory, `Profile`, cookies, or all `chrome.storage.local` data across profiles. A shared extension context cannot directly run content scripts in tabs belonging to another Chromium profile. Single sign-in is possible only when the extension or its identity provider explicitly supports a cross-instance handoff: for example, an OAuth flow with a documented account-scoped token exchange, or a native-messaging contract that accepts a scoped credential in each profile. Such a broker would require extension ID allowlisting, explicit user consent, protected credential storage, revocation, and a security review. If the extension provides only its own private session storage, each profile must sign in separately. Account sync of settings or vault data does not establish a shared signed-in session. No generic sign-in broker is enabled by this change; in particular, password-manager vaults and arbitrary extension storage must never be copied.

The native installer is an asynchronous queue: it can fail later if policy, version, permissions, or network conditions change. Its pending state must remain visible in Settings until a profile list confirms installation. The catalog checks that at least one regular profile already has the exact version installed from the Web Store before it saves the shared intent. The initial approval still needs an engine-issued Web Store request bound to its tab, page, profile, extension ID, version, and permissions. The current app entry point still starts Ardia; the shared Settings model is injectable but not constructed by that entry point. Native compilation and a two-profile runtime probe remain pending until the integration build is available. The manager page is loaded only from the app bundle, and popup views are borrowed for their native lifetime. See [[Engine_Module_extensions]] and [[Profile_Space_Isolation]].
