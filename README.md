# Arcusis Browser

A native macOS 26+ browser project with an Arc-style sidebar, spaces assigned to profiles, and a Spotlight-style Command-T launcher. Browser controls use SwiftUI and AppKit.

## Current state

The development app uses a SwiftUI/AppKit interface and a pinned ArdiaCore Chromium framework through a direct Objective-C++ bridge. It does not use the upstream React Native or Expo adapter. The native shell includes spaces, profiles, tabs, pinning, session persistence, and command search across tabs and spaces.

Each profile has its own persistent engine directory. A new space defaults to a separate profile; explicitly sharing a profile also shares its accounts. Changing spaces retains live tab objects and moves the selected native view. Tabs cannot silently switch to a different profile, and an unknown profile never falls back to the default profile.

The native bridge supports distinct window identities with window-owned tab selection, Find sessions, extension popups, and close state. Live tabs bind both their profile and native window; implicit reassignment and unknown-window fallback are rejected. One shared runtime dispatcher routes events to window-specific application clients. Profile library/download events reach every registered client using that profile; tab, popup, Find, and consent events retain their owning window. The native host restores saved window models and supports Command-N for a new managed window. File/Edit/Tabs actions resolve the actual key browser window, its sheet parent, or an explicitly owned extension popup; unknown key windows cannot fall back to another account. Modal state disables underlying page actions. Shift-Command-W closes the owning window; Command-W closes the selected tab or an empty window. Physical shortcut/focus and native close-cancellation acceptance remain open.

The native host uses a managed workspace format and writer. They share Space/profile/folder metadata and original pin definitions, while each window retains distinct tab IDs, current navigation, selection, folder collapse, and closed-tab recovery. New windows copy no ordinary pages; shared pins receive separate local identities and load only when selected in the managed engine clients. Removing a shared pin preserves another window's existing page as an ordinary tab. Shared metadata changes retain existing native documents. This follows Arc's [window-local unpinned/shared-pin model](https://start.arc.net/release-notes), but does not establish complete Arc feature parity. Normal startup holds an OS workspace lock before loading models or profiles. Confirmed ordinary closure removes that window record; engine quit retains open records for restoration. Bounds and focused-window identity persist, and offscreen bounds clamp to current screens. Shared-Space deletion explains its cross-window impact. Real focus/input and cancellation dialogs, and primary/last-engine-window macOS reopen policy remain unverified.

Engine-created normal-profile windows now enter the managed native host. Page `window.open` popups use the public adoption API after insertion notification unwinds; extension `chrome.windows.create` uses a fresh empty host before Chromium attaches its browser. The pinned engine reports extension popup browsers as `app`; that category also receives a managed context. Requested profile and known opener determine account/Space placement. Opener messaging survives page-popup adoption, background extension requests retain saved focus, and confirmed last-tab closure retires an engine-created empty window. An extension attempt to move an existing live tab into another window is returned to its original owner with its document, ordering and selection retained; user-facing cross-window tab transfer is not implemented. Declined requests use an unseen, unsaved internal host which closes immediately, avoiding Chromium's stock-window fallback. Private-session support, real vendor/OAuth window flows, popup-specific geometry/appearance and complete window-type coverage remain separate gates.

Tab-selection changes reported by Chromium update the owning window's model and saved selection. Activating an existing tab in another Space using the current profile reveals its Space and folder without moving or duplicating the page. Stale Find/consent/popup context is canceled. Engine activation in an inactive profile does not switch the displayed account. Host-created background tabs and host profile/ordering operations retain the application's selected tab. Model selection updates during the engine notification; tab-strip reconciliation waits until that notification unwinds.

Spaces can be renamed, recolored, and removed; removing a shared space closes its tabs across windows, retains the profile's data, and cannot remove the last space. The editor and confirmation show the affected window/tab count. Normal tab closure waits for the engine's beforeunload decision. Profile IDs persist before navigation.

The sidebar supports native drag/drop and context-menu ordering for tabs and spaces. Drop a tab before another row, into the Pinned/Tabs section, or onto a space using the same profile. Moving the selected tab follows it into its destination space; moving an inactive tab preserves the active document. Moving a live tab to a different profile is rejected. Space controls also offer Move left/right; tab menus offer Move up/down and Move to Space. Ordering, pins, and per-space selection persist. Chromium's profile-local tab strip follows the same order and pin state, retaining existing native tab objects. Transfer payloads contain local IDs and a per-launch token, with process-only visibility. Live native drag/menu input still requires interactive acceptance.

Pinned tabs can be grouped in nested, per-space folders. The sidebar offers native folder creation/editing, collapse, reordering, and moves between spaces sharing the same profile. Dropping a tab into a folder pins it; unpinning removes its folder membership. Removing a folder keeps its pages and promotes its immediate contents to its parent. Collapsing folders retains live documents and engine ordering. Command-T searches folder paths and hidden tabs; selecting a result reveals its ancestors. Folder moves reject ancestry cycles and different profiles.

Closed tabs can be reopened with Shift-Command-T, the File menu, the New tab context menu, or Command-T search. Recently Closed shows the last 25 tabs for the selected space; even spaces explicitly sharing a profile keep separate recovery lists. Entries are recorded only after confirmed native closure and saved atomically with live tabs. Reopening restores the URL, title, pin, available folder, and position in the original profile, using a fresh native document and tab ID. A removed folder restores at the pinned root; removing a space discards its recovery entries. Clearing the list affects only that space. Back/forward history, unsaved forms, JavaScript state, and sessionStorage are not restored by this URL-based recovery path.

The profile-scoped extension menu lists installed extensions and hosts action popups in native popovers. Native installation consent displays the engine's requested permissions, extension ID/version, source site, and destination profile. Switching profile/tab or navigating away cancels stale consent; popup views close on context changes and never enter saved tab lists. Unknown or unbound requests are denied. Extension side panels are not implemented.

Camera and microphone requests use native consent bound to the requesting origin, selected page, and profile. Grants last for the current visit. Extension installation and media requests share one consent queue; unseen or stale requests cannot be granted. A toolbar indicator lists capturing tabs across spaces and returns to the owning tab. Switching spaces retains active calls. Screen-sharing selection and other website permission types are not implemented; unsupported permission requests are denied.

Find in Page uses a native bar and Chromium's find API for highlighting, counts, and previous/next matches. Its query belongs to the selected document and is excluded from saved sessions. Changing tab/profile, navigating or reloading, opening consent, or closing the bar clears the search. A different tab starts with an empty query even when its space shares the same profile. The browser does not use a shared Find pasteboard or page scripts to perform matching.

Renderer termination shows a native recovery panel while retaining the live tab, space, and profile. Reload page, the toolbar, and Command-R use the selected owning profile; stale controls cannot reload another tab or a replacement document. A committed replacement document clears the panel. Failed-page find state and pending consent are canceled. Background failures preserve the current selection and launcher. Failure metadata is transient; relaunch opens the saved page URL normally. Recovery can lose unsaved forms and JavaScript state. The strict abrupt-process probe described below currently fails for cookies that have not reached disk.

Downloads use Chromium's authenticated transfer pipeline and a native profile-scoped panel (Shift-Command-J). It shows progress, pause/resume/cancel, completed-file actions, and removal from the list. Transfers continue across space switches; engine history owns their persistence. Normal files use the engine's Downloads directory. File actions require the selected owning profile, a completed non-blocked record, and an existing regular file. Blocked-file approval is not implemented. Closing with active downloads asks before cancellation. Interactive file opening, Finder, and close-dialog behavior still require native-window acceptance.

Bookmarks and History use native panels backed by Chromium's profile databases. Command-D adds or edits the current page; Command-Y opens History. Bookmarks support folders, editing, moves, and deletion. Deleting a bookmark folder also deletes its saved descendants; open tabs stay open. Spaces sharing a profile share its bookmarks/history, while separate profiles keep separate libraries. Command-T searches the selected profile's cached bookmarks and loaded history. History initially loads 500 recent unique addresses; Load more expands that scope, and search covers the loaded rows. Removing a history entry deletes all visits to that address in the owning profile. Existing unsupported bookmark addresses remain available for editing/deletion, but only HTTP(S) addresses can be opened here. Library data is not duplicated in the session JSON. Import, sync, all-history clearing, and private browsing are not implemented.

**This is not ready for company daily use.** Disposable fixtures prove account and MV3 extension storage isolation and restart recovery. A real Chrome Web Store probe reaches native consent and registers Bitwarden 2026.10.0 as an enabled `FROM_STORE` extension. Its setup/welcome UI renders, and the email login form was verified after restart. The fresh-install probe still fails to advance from onboarding to that form; the overall gate remains red while the probe's interaction flow is investigated. This does not establish full Bitwarden support. Google Workspace authentication and exports/uploads, real Meet devices and screen sharing, live library/drag/menu behavior, trackpad switching, live multiwindow focus/close cancellation, live file dialogs, signing/notarization, real keychain integration, and engine security updates remain release gates. Evidence and the compatibility matrix are tracked in [issue #1](https://github.com/arcusis/browser/issues/1).

## Build and run

Requires macOS 26+ and Xcode 26+ with Swift 6.2 or newer. The pinned development engine supports Apple silicon. The shell and unit tests build without downloading it.

```sh
swift build
swift run ArcusisBrowser
```

To build the browser with its engine (requires `curl`, `jq`, and `rg`):

```sh
bash scripts/bundle-app.sh --with-engine
```

The script verifies the engine archive's pinned SHA-256, embeds its framework/helpers/resources, signs nested code inside out, and verifies the local bundle. The result is `build/Arcusis Browser.app`, signed ad hoc for development. It is not a notarized release or registered as a default browser. Engine inputs and upstream notices are in [ThirdParty/ArdiaCore](ThirdParty/ArdiaCore/README.md).

`bash scripts/bundle-app.sh` without `--with-engine` builds `build/Arcusis Browser Shell.app`, a separate UI-only preview. `swift run ArcusisBrowser` also runs that preview without webpage rendering.

Command-N creates a new engine-backed window sharing Space/profile/pin definitions, with no copied ordinary tabs. Shift-Command-W closes the focused window. Command-T / Command-L opens the launcher. Command-S toggles the sidebar. Control-Option-[ / ] switches spaces. Arrow keys select launcher results, Return executes, and Escape dismisses. Opening or dismissing the launcher creates no tab.

Command-F opens Find in Page. Command-G / Shift-Command-G selects the next/previous match; Return in the find field also selects the next match. Escape or Done closes find and requests focus for its owning page. Live native keyboard/focus behavior still requires an interactive acceptance check.

Normal engine-backed sessions live in `~/Library/Application Support/Arcusis Browser/workspace.json`. The version-1 workspace includes a shared catalog, validated per-window schema-v3 snapshots, optional geometry, and focused-window identity. Saved data includes profile/Space/tab IDs, URLs, titles, pins, selection, folder hierarchy/membership/collapse state, and window-local closed-tab recovery. Engine data remains in `Chromium/Profile <profile UUID>` below the same support directory. Real profiles use the OS keychain; the mock keychain is restricted to marked disposable tests. No existing Chrome or Arc profile is imported.

When no workspace exists, `WorkspaceFile` reads legacy `session.json` (v1/v2/v3) without rewriting it or changing identities. Native startup saves the managed snapshot before restoring pages. Existing malformed or unsupported workspace data never falls back to a stale legacy session; both files remain preserved and temporary windows report that changes will not be saved. Valid unsaved state survives IO failure for retry. A mode-0600 `workspace.lock` is held with an exclusive OS lock until engine shutdown, preventing another app process from writing the same workspace; the lock file is retained after release. The UI-only SwiftUI preview uses in-memory sample data and does not modify the workspace or legacy source.

## Verification

```sh
swift build
swift test
xcrun swift-format lint --strict --recursive Package.swift Sources Tests
bash scripts/test-engine.sh
```

Generate native view previews without opening a window or capturing the desktop:

```sh
.build/debug/ArcusisBrowser --render-preview /tmp/arcusis-shell.png
.build/debug/ArcusisBrowser --render-preview /tmp/arcusis-command.png --command
.build/debug/ArcusisBrowser --render-preview /tmp/arcusis-compact.png --command --compact
.build/debug/ArcusisBrowser --render-preview /tmp/arcusis-space-editor.png --space-editor
.build/debug/ArcusisBrowser --render-preview /tmp/arcusis-extension-consent.png --extension-consent
```

The engine test starts an authored HTTP fixture on an ephemeral loopback port and runs the bundled engine twice. It exercises the real native store/space integration with two independent profiles and a third explicitly shared space. A component-loaded MV3 fixture checks per-profile extension storage, service workers, long-lived ports, offscreen documents, content scripts, scripted autofill into disposable fields, active-tab targeting, popup disposal, and restart recovery. Component loading is restricted to the marked temporary probe root and does not prove normal store installation. The fixture's manifest contains a public test key only; no private key is distributed.

The MV3 fixture also checks callback-based storage writes/reads, area-local and global change notifications for popup and worker writes, and serialized payload preservation. Per-profile JSON reports include observed event/callback order; the test requires delivery without imposing a relative ordering guarantee.

Media checks use Chromium fake camera/microphone devices and its simulated system-permission backend, restricted to marked disposable probe profiles. They verify separate-profile consent, temporary grants, denial, cancellation on context change, call continuity across space switches, and capture indicators. They never request physical hardware or change real macOS permissions. These checks do not establish Google Meet compatibility or real camera/microphone, screen-sharing, or macOS privacy-prompt behavior.

Find checks search authored fixture text through the real engine, including case-insensitive matching, forward/backward wraparound, rapid query replacement, profile/tab ownership, clearing, and same-URL reload cleanup. The runner also captures native find layouts at normal and minimum window sizes, and captures engine highlights separately. These checks do not prove Find behavior in every web app, PDF, canvas editor, or live native keyboard interaction.

Download checks use real engine transfers from authenticated loopback fixtures into the marked temporary directory. They verify account-specific file bytes, pause/resume/cancel, background completion across space switches, profile-scoped actions/history, removal without deleting the file, and restart restoration. Links receive trusted in-process renderer input, without a debugging socket or permission bypass. The runner supplies `ARDIA_DOWNLOADS_DIR` only to its disposable child processes. It does not open downloaded files, launch Finder, or display native dialogs. Real Workspace exports/uploads, interrupted-download recovery, blocked-file approval, and native file/quit interactions remain separate acceptance checks.

Ordering checks move existing live tabs between explicitly shared spaces and reject different-profile moves. They compare native tab IDs, document instances, cookies, and storage before/after moves; query the authored MV3 fixture's `chrome.tabs` ordering/pin/active state; exercise bulk pin/unpin transitions; and verify saved order after restart. Native sidebar layouts are captured at normal and minimum window sizes. These checks exercise the model and native engine integration, not actual pointer drag gestures or context-menu input.

Folder checks exercise the native store's drop handlers with real Chromium tabs: nested membership, collapse, path search, subtree moves, cycle/profile rejection, removal without closing pages, extension-visible tab order, and restart restoration. Unit tests cover v1 migration, malformed v2 preservation, stale editor/consent ownership, and deeply nested trees. Offscreen captures cover expanded/collapsed sidebars, compact layout, command search, and the folder editor. Actual native drag, menu, and dialog interactions remain separate acceptance checks.

Closed-tab checks wait for real engine closure, reopen pages in their owning profiles, verify cookies/local storage and fresh tab sessions, compare unrelated live documents, inspect extension-visible ordering, and restore archived entries after restart. Unit checks cover canceled/pending closure, late duplicate callbacks, stale context, consent protection, limits, clearing/removal, v1/v2 migration, and malformed v3 preservation. Native recovery-panel light/dark/empty layouts and compact launcher results are captured offscreen. Actual shortcut/menu input, native beforeunload dialogs, back-stack restoration, and abrupt-process recovery remain separate acceptance checks.

Library checks create, edit, move, and delete real Chromium bookmarks, visit and close authored pages, and verify bookmark/history persistence without revisiting those closed pages after restart. The MV3 fixture reads native entries, writes bookmarks, and triggers native library refresh through engine events. Checks cover profile isolation, explicit profile sharing, unknown-profile rejection, foreign bookmark IDs, permanent-root/cycle protection, bounded history queries, URL-specific deletion, and preservation of live tabs/accounts. Unit checks cover malformed responses, stale reads and actions, coalesced events, history loading, and late acknowledgements. Native bookmark light/dark, history, editor, and compact launcher layouts are captured offscreen. Actual native shortcut/menu/dialog input, large-library performance, and private-session behavior remain separate acceptance checks.

Renderer recovery checks intentionally terminate an authored localhost renderer through in-process CDP, with no debugging socket. The crash hook is restricted to disposable probe runs and dedicated loopback fixture paths. Checks verify real termination callbacks, retained tab identity/profile, reload into a fresh document with the same cookies/local storage, resumed Find, stale/foreign/background reload rejection, and preservation of unrelated live account documents and launcher state. A failed background tab is left for graceful browser restart to verify normal restoration from its saved URL. Native recovery light/dark layouts are captured offscreen. Unit checks cover consent cancellation, stopped/rejected reloads, and exclusion of failure state from session persistence. These checks do not establish recovery from browser-process crashes, physical memory pressure, every extension renderer, or actual native input.

Native-window checks create a second hidden engine window with shared-profile and separate-profile tabs. They verify distinct real Chromium window IDs, window-owned native views, profile/account retention, rejection of implicit moves and foreign ordering, simultaneous Find tokens/counts, separate extension popups, and extension-visible owning window/profile storage. Clearing or closing one window cannot retire another window's selection or stop normal tab close/recovery recording there. Confirmed closure releases the owning tabs/popup and retires its native window ID; original account documents remain live. These checks use the low-level native API, not a second application store, and do not verify Command-N, per-window menus/persistence, generated-window routing, live focus/input, or close-cancellation dialogs.

Window-client checks exercise two independent application stores and engine clients using the same runtime dispatcher and an explicitly shared profile. They verify page/Find/popup routing, shared bookmark/history/download updates, profile membership filtering, owning-store closed-tab recovery, and continued primary callbacks after secondary closure. Router unit tests reject duplicate/retired clients, cross-window tab/context reassignment and consent resolution, duplicate close delivery, and stale native ownership. The fixture's second store is temporary and does not use a shared session file or prove saved-window coordination/restoration. Both windows remain hidden; native menus, focus/input, and company accounts remain separate acceptance checks.

Activation checks use the authored MV3 service worker's real `chrome.tabs.update` calls, scoped to loopback pages in the requested native window. Worker completion is recorded in profile-local extension storage and observed through the authored content script, independently of the popup that activation may close. Checks cover same-profile Space/folder selection, rapid final-target retention, cross-window routing, inactive-profile protection, saved selection, stale Find/popup disposal, and live account/document retention. Light/dark captures show the selected owning Space after activation. These do not establish physical input/focus, new-window routing, every extension activation path, or activation calls that cause no native selection-change notification.

Managed-workspace checks restore two application clients from one workspace across runner launches. They verify unchanged legacy bytes, stable model ownership and per-window selection/recovery, lazy pin materialization, window-local pin navigation with a shared original address, separate native documents with shared/isolated accounts, catalog propagation without document replacement, folder-collapse independence, and preservation of unrelated live pages. The fixture deliberately retains managed records while closing its hidden native windows for the next launch; it does not exercise production quit/close policy. Unit checks cover migration/round trips, malformed/future/aliased data, account and ID conflicts, shared pin/folder changes, the last-window catalog, reentrant metadata callbacks, failed writes/retry, and retired stores. The production-host fixture below separately covers host integration; these lower-level checks alone do not prove native startup or menu behavior.

Native-host checks use the production host class with hidden windows. Real NSMenu target actions create windows, search/find/reopen in the selected owned context, close ordinary/empty windows, and respect modal/foreign-key boundaries. Injected owned key-window identity and notifications make routing deterministic without OS input. The fixture restores saved models/geometry across launches, captures native layouts, and leaves windows open for the runner's actual engine quit. After the engine loop exits, an audit requires quitting closure callbacks and unchanged retained models. A separate parent process verifies that the active OS workspace lock cannot be acquired. Physical key dispatch/focus, native beforeunload/quit cancellation, and actual first/last-engine-window reopen behavior remain separate acceptance checks.

Engine-requested-window checks exercise a user-gesture page popup, origin/source-bound opener `postMessage`, script closure, MV3 normal/popup creation, extension-visible window/tab IDs, background focus retention, rejection of an existing-tab transfer without replacing its document, and a deliberately declined real engine request. A retained extension-created normal window restores in its original account on the next runner launch. The fixture asserts that every in-process native window remains hidden, including any unmanaged window; screenshots remain offscreen native views. These checks cover authored normal-profile requests, not Google authentication, full Bitwarden window flows, private-session isolation, popup geometry, or every browser type.

An opt-in abrupt-process test waits for an authored-fixture checkpoint, verifies its child PID/process-group ownership and saved session bytes, then sends SIGKILL to that disposable group. It confirms group termination through read-only process inventory before relaunch. Startup compares the complete saved model before loading profiles, then verifies live native identities and profile/account data. Missing, changed, malformed, foreign, or aliased checkpoint data fails the test; the checkpoint never repairs the session.

```sh
bash scripts/test-engine.sh --abrupt-restart
bash scripts/test-engine.sh --abrupt-control
```

Earlier strict runs returned nonzero: session JSON, Spaces, tabs, folders, ordering, and closed entries restored, but newly created account cookies were missing while localStorage survived. Abrupt mode has not been rerun at the current native-host checkpoint; added fixture work changes the elapsed time before termination, so no current strict result or stronger durability is claimed. The pinned [Chromium cookie store](https://github.com/chromium/chromium/blob/155.0.8059.84/net/extras/sqlite/sqlite_persistent_cookie_store.cc) batches pending cookie operations on a 30-second timer or a size threshold. Those failing fixtures terminated within that window. The separate control adds a 35-second idle interval before SIGKILL; its receipt is explicitly marked `controlOnly`, and it cannot establish strict crash-recovery acceptance. `abrupt-recovery-summary.json` derives `strictAcceptancePassed` from the requested mode, fault receipt, and restart result while preserving both raw reports. Neither test exercises power loss, termination during an incomplete session write, real keychain behavior, or company accounts. Whether to accept Chromium's commit window or require stronger durability is a pending product decision.

After the engine script creates `.venv`, `.venv/bin/python -m unittest discover -s Tests/EngineFixtureTests` runs the parent runner's checkpoint, PID/group, cleanup, and control-label rejection checks.

The runner writes JSON reports, logs, and offscreen native/page/popup images to a fresh temporary directory. It never opens an existing browser profile, orders a window onscreen, enables a debugging socket, changes VPN/DNS/network settings, or signs into real services. Chromium helpers retain their sandbox. Disposable test profiles enable extension error diagnostics and use a mock keychain; they do not verify release keychain/signing behavior.

An additional opt-in integration test uses the actual Chrome Web Store and a separate empty disposable profile:

```sh
bash scripts/test-engine.sh --bitwarden
```

This test downloads and installs the signed store extension through the real native consent handler, then follows onboarding toward its email login form and checks installation recovery after restart. It skips the optional browser-password-manager settings change. It never enters credentials or alters an existing Bitwarden vault. Failed stages return a nonzero exit status and write diagnostics; an initial failure is preserved even when the restart phase passes. Route/input transitions are recorded. Only after readiness has failed does a separate diagnostic try a second ordinary Log in click; its result cannot change the failed gate. Diagnostic API reads and extension-error inspection follow that second click. The fresh-install onboarding-to-login failure currently keeps this gate red; successful component-fixture checks do not override it. Bitwarden unlock, real autofill/save/update, passkeys, native messaging, Touch ID, side panels, and company authentication remain unverified.

Offscreen SwiftUI/AppKit images verify native layout. Chromium's remote rendering surface may be absent from an AppKit bitmap; the test captures the authored page separately through the engine's in-process API. These images do not verify live keyboard focus, window shortcuts, Google Workspace, Bitwarden, Cloudflare Access, or a signed company installation.
